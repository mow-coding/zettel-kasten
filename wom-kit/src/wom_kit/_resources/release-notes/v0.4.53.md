# WOM-kit v0.4.53 — session grants, backups and remaining cleanup after restarts (letter 177)

This release answers beta letter 177, sent from public v0.4.52. Three of its observations were product gaps that earlier releases had answered with diagnostics only; each is now reproduced in a test that failed before the fix. Installing the tool alone does not change a customer archive; every write still goes through the reviewed approval path.

## A session grant survives restarts, like the desktop apps

The Codex and Claude desktop apps keep an "allow" decision as a durable record in the user's account; restarting or updating the app never resets it. A WOM grant is now the same kind of record on this conversation's work session: any new process of the same conversation that presents its three session refs uses the grant without a window, also after an app restart or a WOM update, until `set-permission-mode manual`, `recover`, pause, handoff or completion ends it. The grant no longer depends on a secret held by the approving process, and `set-permission-mode` no longer returns a token. Another conversation's route still cannot use it, and every grant claim still records which process used it.

## The session Git backup no longer stops on other activities' receipts

The session-scoped Git backup counted every changed receipt, including other activities' and sessions', against a fixed budget before checking whose it was, so a large archive failed with `work_session_git_receipt_limit`. It now reads each receipt's original session cheaply and proves only this session's receipts; others are excluded and counted as `other_session_hint_receipt_count`.

## Index snapshots stay out of Git

Every index run wrote search, relation and title snapshots under `db/`; a search snapshot is a full copy of the archive index. They appeared as Git changes and a large archive's general Git backup stopped at the file size limit. Each snapshot folder now ignores itself in Git, which also covers archives created earlier; new archives and doctor's recommended patterns list the folders and WOM's local lock files.

## Finishing remaining cleanup after a restart

Object-storage keys named with `env:` refs end with their process. `object-storage-credential-store <archive-root> --store-slug <slug>` now stores the access key id and the secret access key in the Windows Credential Manager through WOM's masked window (two windows, nothing in chat) and returns two `credential-manager:` refs that survive restarts and updates. `activity-cleanup --reconcile` accepts `--rebind-access-key-id-ref` and `--rebind-secret-access-key-ref` to use them for the unfinished items; only the two refs change, inside the new approval, and completed items are not reprocessed. Previews report `credential_refs_state`, and an unreadable pair is refused before the window (`activity_cleanup_credential_ref_unresolved`). Object-storage reads of the Credential Manager accept the exact target name only.

## Boundaries

Everything above was validated with synthetic archives, an injected approval window and a credential-store double. The customer's own run, the physical Windows windows and real R2 keys are not confirmed. The general Git backup's remote reference observation was not reproduced.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0453-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.53/wom_kit-0.4.53-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.53` from a new process, then follow the reviewed `project-version-update` flow for an existing project.
