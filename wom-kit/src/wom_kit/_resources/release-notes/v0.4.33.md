# WOM-kit v0.4.33 — Beta letter 164 ①③④: `object-storage-upload` reopened under the exact approval contract

v0.4.33 reopens the one writer the client has been waiting for since the
object-storage restore and offload shipped: `object-storage-upload`. It is
not a new upload adapter. It composes two writers that already existed in
the v0.4 line — the v0.4.13 emergency-preservation PUT (create-only,
whole-object GET re-hash before and after, manifest-bound provider-call
budget, private ledger, crash-safe resume) and the formal-adoption manifest
projection (one compare-and-swap rewrite under the manifest-index authority)
— under one native dialog, at the v0.3 content-addressed key, with the v0.3
execution receipt. Restore, offload, Doctor, backup-evidence and the gating
matcher accept the result without change.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.33-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0433-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.33/wom_kit-0.4.33-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.33` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## What changes

1. **The writer line comes first (letter 164 ③).** `object-storage-upload
   --dry-run` reports `writer_state` before anything else; when it is
   `unavailable` (`provider_unsupported` — only cloudflare-r2 and generic-s3
   have a live transport —, `store_ref_invalid`, `store_setup_missing`,
   `store_setup_mismatch`) the plan returns with `manifest_scanned: false`
   and zero counts, and `--approve` refuses without a dialog.
2. **Counts-only classification (③).** One manifest scan classifies every
   unique object in a fixed order — `conflicting_definition_count`,
   `excluded_byte_external_count` (prehashed-ledger rows are excluded before
   any compare), `excluded_already_uploaded_count`,
   `excluded_already_preserved_count` (adopt those with
   `--formal-adoption`), `excluded_offloaded_count`, `local_absent_count`,
   `local_size_conflict_count`, `local_path_ambiguous_count`,
   `excluded_by_filter_count`, `already_recorded_count`,
   `source_review_count`, `candidate_count`. Only candidates are hashed;
   `provider_calls_in_plan` is `0`; no credential is read. `--max-objects`
   now bounds the plan instead of refusing it.
3. **`--local-bytes-only` (③).** By default a manifest row that claims local
   bytes which are absent or the wrong size refuses the plan
   (`local_bytes_missing`, counts only, next step named); with the flag those
   rows are counted and the plan is built from the rows that have bytes.
4. **The write (①).** One dialog (`오브제 로컬 바이트 올리기`; always a
   dialog, never grantable to a session mode). Per object: local re-hash,
   whole-object remote query at `sha256/<2>/<digest>`; `verified_match` →
   `skipped_remote_same` without a PUT; size/checksum mismatch →
   `review_required` (never overwritten, no manifest location); absent →
   journaled create-only PUT, full-GET re-hash, private ledger row. Every
   transport failure is nonterminal and resumable
   (`--resume-approval-id` / `--resume-execution-sha256`). After the objects,
   one manifest projection adds a `wom_uploaded` location per verified object
   (`remote_key_verification: content_hash`) under the manifest-index
   authority (the generated index stays current), and only then the
   execution receipts are written under
   `receipts/providers/object-storage-executions/` with the v0.3 fields plus
   `exact_operation_manifest_sha256`, `receipt_state_sha256` and
   `remote_verification.verification_kind: get_rehash_whole_object`.
   There is no tier gate and no `--force-reupload`; the remote object is
   never deleted.
5. **Store-ref (④).** The registered store label is validated by the same
   rule at plan time, at record time (the `wom_uploaded` location builder) and
   by Doctor; the plan refuses an unregistered or unsafe label as
   `store_ref_invalid` / `store_setup_missing` before any read.
6. **Inventory.** `object-storage-upload` leaves the fixed-closed set:
   60 approval-available, 59 fixed-closed, 202 not-exposed paths. The legacy
   v0.3 service function still refuses direct approval. Removed flags:
   `--force-reupload`, `--skip-uploaded`, `--key-strategy`, `--key-prefix`,
   `--key-append-extension`, `--multipart-threshold`, `--multipart-part-size`,
   `--allow-tiny-parts`. Added: `--local-bytes-only`, `--progress`,
   `--expected-manifest-sha256`, `--resume-approval-id`,
   `--resume-execution-sha256`.

targets moved to v0.4.34); the select-all group for
`git-backup-reconcile-plan --approve`; a reviewed re-PUT operation for a

and the 8b same-generation index participation.

## Compatibility and privacy

- New operation kind `object_storage_bytes_upload`; new result schemas
  `wom-kit/object-storage-upload-plan/v0.1`,
  `wom-kit/object-storage-upload-result/v0.1`,
  `wom-kit/object-storage-upload-verification/v0.1`; the execution receipt
  keeps `object-storage-upload-receipt.schema.json` with additive fields.
- Behaviour changes to note: `object-storage-upload --approve` opens a native
  dialog and writes; the v0.3 flag set is gone; a differing remote copy is
  reported, never replaced.
- No path, remote key, bucket, endpoint host, credential ref or value,
  reviewer id or object id is introduced into results, receipts, progress
  lines, dialog contexts, tests or release artifacts.

## Verification boundary

The release candidate must pass the v0.4.33, v0.4.32 and v0.4.31 test
modules, the preservation / restore / offload cohorts, the letter-137
boundary modules, the inventory and coverage pins, the pin sweep and the full
supported-platform CI. The exact reviewed merge commit must be tagged, and
the public wheel must be downloaded anonymously, rehashed, installed in a
fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result.
