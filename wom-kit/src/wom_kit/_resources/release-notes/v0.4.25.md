# WOM-kit v0.4.25 — Archive-Root Project Updates And Resume Failure Causes

v0.4.25 is a hotfix for beta letter 161 and the 2026-09-18 v0.4.24 resume
report. A `project-version-update` started from the **archive root**
(`archive project-version-update <archive-root> ...`, the README form) failed
after the native approval with `project_version_update_approved_snapshot_changed`,
and every later `--resume` died in `project-preflight` with
`project_version_update_directory_stability_unavailable`, both without a cause
in diagnostics. Both failures are reproduced on synthetic fixtures with the
released v0.4.18, v0.4.21 and v0.4.24 wheels and are fixed here. No approval
contract, plan digest, receipt schema or journal schema changes.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.25-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0425-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.25/wom_kit-0.4.25-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.25` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## The defect (letter 161 ③ and ⑤, 2026-09-18 report)

Preflight records the source mirror, every version pin and the update receipt
relative to the inspection root: `.zettel-kasten/...` when the project root is
given, `parent_of_archive/.zettel-kasten/...` when the archive root is given
(its parent is the project root). Those strings are bound into the private
plan and the transaction intent. Six consumers then joined them literally
onto the project root, producing `<project>/parent_of_archive/...`, a path
that does not exist:

- the post-approval snapshot guard re-resolved the pin specs that way, so an
  archive-root update failed right after the person approved
  (`approved_snapshot_changed`, wrapped as `exact_human_approval_state_unknown`);
- `--resume` reopened the transaction with that mirror path, so the
  directory-stability guard could not hold it
  (`directory_stability_unavailable`) before `--abandon-started-approval` was
  ever evaluated; the dry-run kept pointing at `--resume` and `--resume` kept
  dying, the loop the report describes.

Updates started from the project root never took the labelled form, which is
why the v0.4.22 reproduction (project root) updated cleanly and the client's
runs (archive root) did not. `marker.json` `state: reserved` is a constant of
every transaction and does not mean "before the dialog"; the letter-161 claim
lives in the archive's claim store and is `started`.

## The fix

- One resolver, `wom_kit_project_update_logical_relative_to_project_root`,
  maps a recorded location onto the project root (stripping the
  `parent_of_archive` label; absolute, empty or traversing locations resolve
  to nothing). Every consumer uses it: the reopen of a transaction (mirror
  and component paths), the post-approval snapshot guard (pin specs), and the
  terminal-original checks (mirror, regular components, active pin). Nothing
  recorded changes: existing transactions, plans, intents and receipts keep
  their bytes and the fixed transaction created by v0.4.21 reopens as is.
- A failure the service raises directly before any result — during resume
  preflight, reopen or cleanup classification — now carries its fixed code
  as `cause_code` and the journal stage it was in as `cause_stage`
  (`project-preflight`, `verify-release`, ... or `unknown`) in the redacted
  diagnostics artifact and on stderr (`Project version update inner reason
  (fixed code): <code> at <stage>.`), exactly as the v0.4.22 post-approval
  causes do. Only code-shaped tokens of the `project_version_update_`,
  `project_update_`, `project_runtime_`, `project_git_`,
  `exact_human_approval_` and `operation_` families cross; free text never
  does, and the journal schema is unchanged.

## Recovering the letter-161 transaction

With the v0.4.25 bootstrap, from the same archive root:

1. `project-version-update <archive-root> --resume --abandon-started-approval
   --affirm-external-writers-quiescent --format json` closes the `started`
   claim after human review and releases the reservation; the expected result
   is `preapproval_scaffold_cancelled` (lock removed, pin unchanged).
2. `project-version-update <archive-root> --target v0.4.25 --dry-run --format json`,
   then `--approve --reviewed-by <id> --affirm-external-writers-quiescent`.

A plain `--resume` without the abandon flag rediscovers the started claim
and revalidates the old v0.4.21 target under the v0.4.25 runtime policy,
which refuses (`approved_snapshot_changed` with the cause on stderr) and
leaves the claim `started`; the abandon route above is the one to use.

## Not in this release

The pre-dialog `failed_rollback_incomplete` result still reports its blocker
as text without a fixed code; the public `files_written` list still shows
locations in their recorded (labelled) form; a `--resume --dry-run` read-only
preview does not exist. These carry to a later release.

## Compatibility and privacy

- Existing plans, intents, claims, receipts, journals and schema ids keep
  their exact bytes and validators; the resolver only changes how a recorded
  location is turned into a path, and the direct cause is an additive field
  of the redacted diagnostics artifact.
- No path, label, reviewer id or archive content is introduced into results,
  diagnostics, tests or release artifacts.

## Verification boundary

The release candidate must pass the focused project-update, transaction,
approval, privacy, package-resource, installed-wheel and full
supported-platform CI checks. The exact reviewed merge commit must be tagged,
and the public wheel must be downloaded anonymously, rehashed, installed in a
fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result.
