# WOM-kit v0.4.9 — Finish the Safe Single-File Path

v0.4.9 turns three reported dead ends into usable, truthful operations. It
does not loosen approval or ask a person to count archive rows. WOM derives the
exact effect and verifies it; the person decides only whether to perform that
clearly described effect or cancel.

## What changed

- **A new local file can enter the complete safe capture chain.**
  `source-intake-record` now creates one canonical intake receipt through an
  exact create-only manifest, one native decision, durable checkpoints, fresh
  input re-derivation, and independent read-back. The existing exact selection
  and exact local capture commands can then preserve the selected bytes. The
  installed-wheel check proves all three steps; it no longer manufactures the
  first receipt inside the test harness.
- **Intake plans cannot smuggle extra archive content.** The record writer
  accepts only the known source-intake shape and rejects unknown members,
  duplicate JSON keys, non-finite values, excessive nesting or size,
  symlinks/reparse points, changing inputs, unsafe paths, and target collisions.
  Public results and progress contain hashes and counts, not the input path,
  filename, body, provider value, or archive payload.
- **Matching pre-existing bytes are not forged completion evidence.** If the
  exact receipt bytes were already present without a verifiable completion
  path, WOM leaves them unchanged and returns
  `source_intake_record_completion_evidence_required`; it does not bypass the
  expected-plan digest or claim independent verification.
- **Doctor findings declare their freshness.** The object-manifest stage parses
  one bounded stable byte snapshot and revalidates the same input at completion.
  A changed or unreadable completion snapshot makes the result stale or
  unverified and non-successful instead of presenting old duplicate findings as
  current.
- **Doctor suggestions report parser truth without overclaiming.** A suggestion
  such as `remint-reconcile --dry-run` can have valid bounded arguments and an
  exposed dry-run mode even when the later approval mode remains fixed closed.
  Doctor reports those facts separately, rejects shell-control syntax, and
  still does not execute the suggestion, substitute a template path, interpret
  a shell, or claim that archive-specific prerequisites passed.
- **Doctor stays observable.** Progress is visible by default and emits bounded
  content-free heartbeats during a long stage. `--no-progress` deliberately
  disables stderr progress, while verbose events and an explicit progress log
  remain available. A progress log must use a new path outside the archive so
  an observational artifact cannot truncate archive-owned evidence. The
  exclusively-created handle remains open for the run, preventing later path
  replacement from redirecting events.
- **Doctor result capture cannot overwrite the archive.** `--output` must name
  a new archive-relative file. Existing files and hardlink aliases are rejected
  before result publication.
- **Object-storage setup tells the truth at the command boundary.**
  `--profile-id` is visibly required and its help points to `profile-resolve`
  and `profiles/wom-profiles.yml`. The old `--write-local-profile` promise is
  removed from help; legacy invocations still fail before planning or archive
  access. The command does not create a profile registry, bucket, credential,
  or remote verification claim.

## Deliberate limits

The reported high-risk batch writers remain fixed closed. This
release completes the ordinary one-file path; it does not pretend that batch
capture is available. Doctor heartbeat and snapshot revalidation improve
operability and truthfulness, but they are not evidence that the reported
whole-archive runtime has been optimized. Performance needs separate profiling
and proof.

## Client execution boundary

Publishing or installing v0.4.9 does not modify a client archive. The client
installs the released wheel in that project's isolated runtime and runs the
project-scoped command. Development does not update a computer-wide executable
or write client recovery data on the client's behalf.

## Install contract

After the matching GitHub Release exists and lists the wheel, install that exact
public artifact in the client's isolated tool or project runtime:

```powershell
uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.9/wom_kit-0.4.9-py3-none-any.whl"
archive --version
```

The new process must report exactly `archive 0.4.9`. A version string or URL by
itself is not proof that the release asset was published and verified.
