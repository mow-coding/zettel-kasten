# WOM-kit v0.4.3 — Exact Recovery and Verified Git Backup

v0.4.3 turns the previous read-only recovery plans into a bounded execution
path.  It adds one reusable exact-operation foundation, reopens the project
updater and Git backup only behind native exact-human approval, and provides a
lossless Notion `source_properties` backfill for Letter 138.

This release is a tool capability, not by itself proof that a particular
private archive was repaired or backed up.  A private archive is complete only
after the released wheel is installed, the exact manifest is approved and
applied, interruption/resume and scoped revert evidence are checked, an
independent read verifies the result, and the resulting Git commits and remote
ref are re-queried.

## ExactOperationManifest v1

High-impact multi-item writers in this release share one execution contract:

- the manifest binds the exact target, field, before and after hashes, source
  snapshot, operation, and remote destination needed by the domain writer;
- native approval binds the manifest digest and a durable one-use approval
  claim before the first write;
- one archive-wide writer lock prevents two supported WOM writers from
  mutating the same archive concurrently;
- append-only hash-chained checkpoints support explicit, same-claim resume;
- replay, drift, missing checkpoint evidence, ambiguous approval state, and
  malformed or partially written checkpoint evidence fail closed;
- final field receipts and an independent verifier bind the result without
  returning private before/after values;
- revert authority is limited to the exact fields changed by the original
  operation, so an unrelated later field revision is not overwritten; and
- the first content-free progress state is emitted before expensive work and
  cooperative heartbeat output is emitted at least every ten seconds.

The file-backed checkpoint implementation validates existing JSONL once when
opening or resuming and performs bounded durable appends rather than repeatedly
re-reading the whole growing journal.  This keeps total checkpoint processing
linear in the final evidence size while preserving crash durability and strict
tamper detection.

Generic callback injection is not a public approval surface.  Every live
writer uses a reviewed domain adapter, the native approval workflow, and the
authenticated claim ledger.

## Letter 138: lossless Notion property backfill

The existing `archive migrate` command family gains the
`notion-source-properties` target.  Its read-only plan accepts an explicitly
selected preserved mirror, scans both supported mirror envelopes, normalizes
only UUID-equivalent source identifiers, and maps a page only to the one
canonical zet that declares the same `source_page_id`.

The source property envelope is lossless: supported modern properties retain
their typed JSON structure, while legacy property bytes whose modern meaning
cannot be proven remain opaque evidence instead of being guessed or discarded.
The canonical zettel schema recognizes this `source_properties` envelope.

The plan accounts for every source page as one of:

- `backfill` — one exact canonical target needs the bound field update;
- `already_equal` — the canonical target already contains identical source
  properties;
- `unmapped_no_canonical_target` — source evidence remains preserved but no
  target may be invented; or
- `human_review` — malformed, ambiguous, duplicate, over-limit, or otherwise
  indeterminate evidence blocks automatic mapping.

Approval binds each class count and deterministic set digest.  An unmapped page
is not a drop decision and is never reported as repaired.  Apply is available
only when the complete source snapshot and every populated property are
accounted and the unexplained omission count is zero.  A malformed canonical
file is excluded as a non-candidate only when strict UTF-8 decoding proves that
it cannot contain a source identifier; an unreadable file blocks the mapping.
Symlink, junction, reparse-point, containment, duplicate-target, source-count,
and source-shape drift also fail closed.

Apply, resume, independent verify, and field-scoped revert reuse the shared
exact-operation engine.  No provider credential or network request is needed:
the preserved local mirror is the source of truth for this recovery.

## Verified Git backup writer

The v0.4.2 Git plan remains the privacy-preserving selection and drift
boundary.  v0.4.3 adds its exact-approved writer without adding another
top-level command.

The writer:

- binds the reviewed repository, symbolic branch, selected paths, expected
  blobs, commit groups, parent commits, remote name, and exact remote ref;
- uses an isolated temporary index to prove each proposed tree before touching
  the real index;
- preserves pre-staged unrelated entries and commits only literal, bounded
  selected path groups;
- splits a large selection before the Windows command-line ceiling rather than
  truncating it or using an unreviewed wildcard;
- creates ordinary non-merge commits and performs only a non-force push;
- independently re-reads every created commit's parent, message digest, path
  set, and blob identities;
- re-queries the exact remote ref after push and binds that result into the
  receipt; and
- resumes safely after a staged, committed, or pushed interruption without
  duplicating a commit or treating an uncertain transport result as success.

The Git subprocess runner drains stdout and stderr concurrently, so a large
tree cannot deadlock because one pipe fills.  Planning uses bounded Git
projections and a metadata/CAS inventory for generic historical receipts;
tracked receipt contents remain bound by the Git tree and index instead of
being rehashed file-by-file twice.

Git transport evidence is still not a hosting-provider API receipt.  The
completion claim is limited to the exact remote Git ref observed after the
non-force push.

## Project update and Windows PATH diagnosis

`project-version-update` is reopened through the exact-human broker.  Its plan
binds the current project source, pin, target annotated tag and commit, package
resource integrity, and rollback state.  The v0.2 receipt permanently records
the matching approval reference; a historical update receipt cannot authorize
a replay.

The version inspection also reports content-free Windows executable-candidate
and source-candidate counts so an older PATH shadow can be diagnosed before an
operator mistakes the global CLI version for the project-local source version.
Installing a wheel and updating a project remain two separate actions.

One user-level `archive.exe` may be shared by several project folders and AI
sessions under the same Windows account. Replacing that executable is therefore
not a project-scoped update. `archive --version` proves only the running tool;
the project source, pin, and runtime alignment must be checked with `archive
version <project-or-archive-root> --format json`. v0.4.3 does not claim a
general-command per-folder sandbox. Release verification may use a dedicated
temporary virtual environment and explicit executable path so it does not
silently replace a beta client's shared PATH tool.

## Operator feedback revision lineage

`operator-feedback-compose` now permits a compare-and-swap revision only while
the same feedback record remains a draft.  The revision binds the previous
record digest and increments its revision.  A delivered or later record is
immutable; corrections must use a new feedback ID and an explicit supersession
reference.  Independent reports remain independent rather than being folded
into another tool's correction lineage.

This lifecycle records authorship and chronology.  It does not submit a letter
to an external recipient or prove that the reported product problem was fixed.

## Install

Use the exact wheel only after the matching public GitHub Release exists and
lists the asset:

```powershell
uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.3/wom_kit-0.4.3-py3-none-any.whl"
archive --version
```

Close older WOM processes first and require exactly `archive 0.4.3` from a new
process.  Then inspect the project-local version separately before proposing a
project update.

## Evidence boundary

The public release is validated only with synthetic archives and content-free
projections from private-scale acceptance.  It contains no private page value,
credential, remote URL, absolute user-profile path, private commit message, or
private archive identity.

v0.4.3 does not perform R2 byte preservation, repair local locator/link debt,
fetch missing Notion pages from the provider, decide relation quality, or
delete scratch/quarantine material.  Those remain the separately bounded
v0.4.4 through v0.4.7 recovery train.
