# v0.3.261 - Honest Search Coverage

`archive search` reported how many results it returned and nothing about how
many existed. A capped page was indistinguishable from a complete answer, so a
caller could read twenty rows and conclude the archive held twenty matches.
v0.3.261 makes the search surface state its own coverage on every surface it
has, without making search slower.

## What Changed

- `archive search`, its default text output, and the MCP `archive_search` tool
  now report `truncated`, `complete`, `returned`, `total_matches`,
  `total_matches_known`, `matches_by_type`, `limit_applied`, and
  `limit_ceiling`. The existing `count` field is unchanged and still reports the
  returned row count.
- Truncation is detected by reading one row past the requested limit, so every
  channel keeps its `LIMIT` and the search still stops early instead of scanning
  whole tables.
- An exact total is opt-in through `--count-total` (CLI) or `count_total`
  (MCP), because a leading-wildcard `LIKE` cannot use an index and an exact
  count costs a full scan of each searched table. When a result set is not
  truncated the total is already exact and is reported for free.
- The default text output no longer prints a bare `Found N result(s).` for a
  capped page. It states that more matches exist and how to get the number.
- The MCP tool description now names all five searched channels and states the
  limit and truncation semantics a host must check.
- The zettel filter's status list is generated from `ZETTEL_QUERYABLE_STATUSES`,
  and result rows and any count now share one read transaction.

## Why It Matters

WOM's node-first doctrine already forbids presenting a truncated read as
complete coverage, and the zet catalog enforces it with explicit `complete`,
`truncated`, and continuation evidence. Search was the one retrieval surface
without that contract, which is exactly where an operating AI is most likely to
stop early and report a wrong total.

Knowing *that* more matches exist is what prevents the wrong conclusion.
Knowing exactly *how many* is a separate, more expensive question, so the two
are now separated rather than bundled at the cost of every search.

## Privacy Boundary

Each channel's `WHERE` clause is defined once and shared by its result query and
its optional count query, so `total_matches` applies the same lifecycle and
redaction filter that selects the returned rows. A redacted zettel whose body
contains the query term is neither returned nor counted, and the totals cannot
disclose that suppressed content matched. A regression asserts this at a capped
limit, at an uncapped limit, and with `--count-total`.

## Compatibility And Migration

- No archive, zettel, index, receipt, or schema migration is required. The
  generated index is unchanged; no rebuild is needed for this release.
- `count`, `query`, and `results` keep their existing meaning and shape, so
  existing callers continue to work.
- Result ordering, matching behavior, the channel cascade, and the 100-result
  ceiling are unchanged. The ceiling is now reported rather than silent.
- `total_matches` is `null` when a result set is truncated and no exact count
  was requested. Check `total_matches_known` before using it as a number.

## Provenance And Verification

The gap surfaced while reviewing beta feedback about a large real archive. The
report concluded that the generated index could not answer a topic question and
asked for full-text search. Tracing the code showed something different:
`search_archive` already matches zettel bodies, so the reported shortfall came
from ad-hoc SQL against the `title` column rather than from this command. The
defect that did reproduce was this one — a truncated answer that looks
complete, which is how an operating AI reports a wrong total and then falls
back to scanning files by hand.

Four independent pre-release reviewers then rejected the first implementation.
It had reported exact totals on every truncated search, which turned a query
that previously stopped after one channel into five unindexed full-table scans,
on precisely the large archives the release targets. The same reviewers found
that the first implementation had fixed the JSON and MCP surfaces while leaving
the default text output printing the exact sentence the release exists to
remove. Both are corrected here.

Full-text search and a classification-path facet remain separately scoped. This
release changes only what search says about its own coverage.
