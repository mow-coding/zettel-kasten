# WOM-kit v0.4.34 — Beta letter 165: presenter-bound session grants, legacy identifier warnings, feedback compose under exact approval

v0.4.34 answers beta letter 165 in full. A session permission grant is no
longer usable by any process that presents the three work-session refs: it
is bound to the conversation that received the approve result and to a time
box, every write it covers records which presenter used it, and the operator
can see open grants at a glance. The pre-WOM Notion identifiers that kept
leaking into new records are named on every new-record surface, with counts
and line numbers only. The one v0.4 writer that still trusted `--reviewed-by`
alone, `operator-feedback-compose --approve`, now asks the dialog like every
other writer, and the path to revise a feedback body is announced where it
is needed.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.34-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0434-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.34/wom_kit-0.4.34-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.34` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## What changes

1. **Presenter-bound, time-boxed grants ([A]).** `work-session --action
   set-permission-mode --approve` for `limited` / `allow_all` mints a random
   presenter secret before its dialog; the reviewed plan binds
   `presenter_sha256`, `granted_at` and `expires_at` (`grant_hours` 1..24,
   default 8, an optional key of the request and of the `--dry-run` preview,
   which returns `would_box`), and the dialog shows the box. The secret is
   returned exactly once as `presenter_token`
   (`presenter_token_returned_once: true`); keep it only in that
   conversation's process (`WOM_WORK_SESSION_PRESENTER`); the draft and
   intake privacy gates refuse a pasted `WOM_WORK_SESSION_PRESENTER=` line.
   An MCP-hosted approve returns the token once through its envelope the
   same way (the writes that consume it run in the conversation's CLI
   process) and also holds it in the server process
   (`presenter_token_held_in_process`). A resume or re-review of the decision
   reports `presenter_token_available: false`.
2. **Refusals say why ([A]).** A write that presents the three refs without
   the secret, with the wrong one, after `expires_at`, or under a grant made
   before v0.4.34 (the two-key shape) opens the dialog and carries
   `session_permission_refused {reason_code, dialog_shown: true}` with one of
   `work_session_presenter_missing`, `work_session_presenter_mismatch`,
   `work_session_grant_expired`, `work_session_grant_legacy_shape`,
   `work_session_grant_unavailable`,
   `work_session_grant_warning_review_required`. Expiry is a resolve-time
   refusal; a running writer is never interrupted. Existing grants ask the
   dialog again until `set-permission-mode --approve` is run once more.
3. **Presenter evidence in every grant claim ([A]).** A claim decided by a
   session grant carries `session_presenter`: the presenter hash, the
   fingerprint state (`observed` — an HMAC of the first non-launcher ancestor
   process, keyed with the archive receipt key — or `unavailable`), how
   many other presenters used the session before it, and `scan_truncated`
   (the bounded, newest-first scan of the claims written since the grant
   hit its limit). Results carry
   `exact_human_approval.presenter` and, when another presenter already used
   the grant, `exact_human_approval.warnings:
   ["work_session_second_presenter_observed"]`. `exact-approval-claims`
   lists `mechanism_counts`, `presenter_unknown_count` (grant claims from
   before v0.4.34, which stay immutable) and per-row `presenter_recorded` /
   `session_presenter`. The fingerprint is evidence, never authority.
4. **Visibility and guidance ([A]).** `work-session --action list / inspect`
   rows carry `presenter_bound`, `permission_granted_at`,
   `permission_expires_at`, `grant_expired`, `grant_legacy_shape`; the
   session listing counts `non_manual_session_count`, `expired_grant_count`
   and `legacy_grant_count`. `ai-start-here` gains the registry-only
   `session_permission_attention` block (Markdown: `Session Permission
   Attention`), a warning and a `next_safe_steps` entry when a grant is open,
   and the guidance line that also appears in the approve result, the
   `work-session` help and the contract: the refs and the token stay in the
   granting conversation; another conversation continues a task through
   handoff / accept. Operator revoke: `set-permission-mode manual` in the
   granting conversation, `recover --approve` from any route of the same app,
   or the expiry.
5. **Legacy identifier warning ([B]).** One detector names a bare Notion
   `ZET<number>` page name or 32-hex / UUID page id in a new body, title or
   label (an identifier joined with `_` inside a WOM id is not flagged) with
   counts and line numbers only. `create-draft --dry-run` returns
   `quality_check.warning_explanations` and the bound warning
   `legacy_identifier_in_new_record`; `--approve` refuses with
   `create_draft_warning_override_required` before any dialog until
   `--allow-warnings` is given, and a session grant never covers such a draft
   (the dialog opens with `session_permission_refused.reason_code:
   work_session_grant_warning_review_required`; the fixed legacy codes stay
   literal next to the digested warning set of every CLI context, and
   `mint-zet-batch` folds an allowed item's code into the batch's bound set;
   the scan covers the body that is written, a verbatim source region too).
   `mint-zet --dry-run` adds the explanation only when it
   matches; `zet-revision-plan` raises the warning and the write binds the
   reviewed plan's warnings; `zettel-objet-link` warns
   `label_legacy_identifier_review`; `source-intake` warns
   `legacy_identifier_in_source_label`. A record that itself came from the
   Notion import gets the informational `legacy_identifier_in_migrated_record`.
   When the index holds migrated zets, the explanation and `ai-start-here`
   give the guidance: reference a migrated zet by its full WOM id (for example
   `zet_notion_db3_ZET0637`) or its title, and resolve an old number through
   `zettel-edge --target zet:notion:ZET<n> --dry-run` or `archive search`.
6. **Feedback compose under exact approval ([C]).** `operator-feedback-compose
   --approve` plans, checks `--expected-plan-sha256` and a `person:` /
   `human:` reviewer before any dialog (`feedback_compose_plan_changed`,
   `feedback_compose_reviewer_claim_invalid`), then opens the dialog under
   the new grantable operation `operator_feedback_body_write` (binding the
   request digest and the body digest; `feedback_body_revision` /
   `feedback_body_supersession` as warnings). Receipts become
   `wom-kit/operator-feedback-body-receipt/v0.2` (and the revision /
   supersession v0.2 forms) with an `exact_human_approval` envelope naming
   the claim; v0.1 receipts stay valid and `operator-feedback-body-check`
   reports `exact_human_approval_reference_present`. The emergency lane under
   `version-update.lock` keeps its text-flag path (`approval_mechanism:
   emergency_text_flag`, v0.1 receipt). The path was already
   approval-available, so the inventory stays 60 approval-available and 59
   fixed-closed.
7. **The revise path ([D]).** Every compose result and the body check's
   `feedback_record_binding_missing` branch list the five steps: record draft
   → body-check → compose `--intent revise --expected-body-sha256` → record
   update → body-check. `operator-feedback-compose --create-draft-record`
   creates the draft metadata record right after a created body, in sequence
   and outside the claim (`draft_record` on the result), so `--intent revise`
   works next; without the flag the existing sequence is unchanged.
8. **Revision-plan warning explanations ([E]).**
   `quality_review.warning_explanations` says which frontmatter field to fill
   (`document_type_missing`: the field and its allowed values) or which
   table(s) lack their parse review (`table_row_mapping_missing`,
   `table_structure_review_missing`: ordinal, header line, row count; cell
   text never echoed).

## Compatibility and privacy

- New operation kind `operator_feedback_body_write`; new schemas
  `wom-kit/exact-human-approval-presenter/v0.1`,
  `wom-kit/session-permission-attention/v1`,
  `wom-kit/operator-feedback-body-receipt/v0.2` (+ revision / supersession
  v0.2); optional request key `grant_hours`; new flags `create-draft
  --allow-warnings`, `operator-feedback-compose --create-draft-record`.
- Behaviour changes to note: a grant made before v0.4.34 asks the dialog
  again until it is set again; `operator-feedback-compose --approve` opens a
  dialog and requires a `person:` / `human:` reviewer; a create-draft whose
  body or title carries a bare legacy identifier needs `--allow-warnings`.
- No token, hash basis, path, process name, reviewer id, body text or label
  is introduced into results, receipts, progress lines, dialog contexts,
  tests or release artifacts; the presenter secret is a fresh value returned
  once, never stored.

## Verification boundary

The release candidate must pass the v0.4.34, v0.4.33 and v0.4.32 test
modules, the work-session / claims / feedback-body / objet-link / intake
cohorts, the inventory and coverage pins, the pin sweep and the full
supported-platform CI. The exact reviewed merge commit must be tagged, and
the public wheel must be downloaded anonymously, rehashed, installed in a
fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result.
