# WOM-kit v0.4.1 — Emergency Link Recovery And Global-CLI Escape

v0.4.1 is a narrow recovery release for the v0.4.0 beta line. It reopens one
structured Zettel–Objet link apply only after binding the complete single-write
effect set to native exact-human approval. It does not reopen link revert,
Objet capture, project update, or another compound writer.

This source note is not release evidence. The versioned install URL below is
usable only after all of these exist for the same commit: the `v0.4.1` tag, a
public GitHub Release, its exact wheel asset, successful CI, and an independent
fresh-install check of that asset.

## One exact Zettel–Objet link apply

`archive zettel-objet-link` (alias `zet-objet-link`) now supports one approved
apply from the local interactive Windows CLI. The preview and writer bind:

- one resolved zettel id, archive-relative path, and exact pre-write bytes;
- one exact `sha256:<64-lowercase-hex>` Objet with a complete, unique,
  strictly parsed manifest record set;
- the reviewed role and the SHA-256 of an optional label, without echoing the
  label;
- one deterministic link id, receipt generation, exact receipt path, and
  create-only or existing-exact pre-write snapshot;
- one deterministic canonical compare-and-swap transaction plus its bound
  `.zettel-objet-link.swap` and `.previous` archive-relative paths;
- the complete zettel/snapshot/receipt/compare-and-swap support-effect set; and
- one stable per-zettel control artifact, including its path, initial state,
  and exact byte digest.

The control artifact lives at:

```text
receipts/objects/zettel-links/.locks/<sha256-of-zettel-id-utf8>.lock
```

Its exact content is the single UTF-8 line
`wom-kit/zettel-objet-link-lock/v0.1`. On first use the approved plan binds the
artifact as absent; the writer creates that exact artifact and preserves the
approved initial state while it holds the control boundary. Later operations
require the existing artifact to be a regular file with the exact bytes. An
unexpected, malformed, or replaced control artifact fails closed.

Immediately before mutation, the writer reacquires the stable control boundary,
re-runs the strict plan, requires the same plan and target binding, and
reauthenticates the exact-human claim. It then creates or reuses the exact
snapshot, applies the one zettel update through an exact-byte compare-and-swap,
and publishes a v0.2 receipt containing the authenticated exact-human
reference, control-artifact binding, transaction digest, and both deterministic
swap paths. It reads back the zettel, snapshot, receipt, and control artifact,
proves both swap paths absent, and jointly revalidates the approved manifest
target plus the unique Zettel authority at the final success point. Existing
v0.1 link receipts remain readable; they do not grant new write authority.

The Windows swap uses retained handles and two `FileRenameInfo` moves with
replacement disabled. It never asks `ReplaceFileW` to overwrite a backup name,
because a file can appear at that name after an absence check. The canonical
name can be briefly absent between the two moves. A process exit there leaves
the exact old bytes at `.previous` and proposed bytes at `.swap`; reconciliation
can resume that pair. If another process creates the canonical name first, WOM
refuses and preserves that occupant plus both transaction files.

Before the first move, WOM verifies the exact held old and proposed files as
single-link, non-reparse regular files with the approved bytes and matching
security descriptors and semantic attributes. A handle-bound `BackupRead`
inventory permits only the unnamed default data stream. Alternate data streams,
extended attributes, object IDs, sparse-file data, another backup stream type,
or metadata that cannot be completely verified therefore fail closed before
the old canonical name moves; WOM never silently drops them during a text
update.

Only after the new canonical name, identity, bytes, supported metadata, and
complete namespace state verify does WOM remove `.previous`. On Windows that
removal uses `FileDispositionInfoEx` with `FILE_DISPOSITION_DELETE`,
`FILE_DISPOSITION_POSIX_SEMANTICS`, and
`FILE_DISPOSITION_IGNORE_READONLY_ATTRIBUTE`. It never falls back to ordinary
delayed deletion. If that immediate namespace-unlink contract is unsupported,
the new canonical bytes and exact old `.previous` bytes remain visible for
explicit reconciliation, and an immediate retry applies the same rule. An
already-open external handle may continue to access only the detached old file
object after a supported unlink; it cannot keep the `.previous` pathname
visible.

The two compare-and-swap paths are private transaction artifacts. During a
crash or ambiguous failure they can retain full before or proposed zettel
bytes. WOM never guesses that these residues, a created snapshot, or a created
receipt are safe to delete. Preserve them, treat the result as
`effects_state: unknown` with reconciliation required, and do not auto-retry.
A retained receipt by itself is recovery evidence rather than proof of a
committed link; active v0.2 history also requires the current canonical state,
exact snapshot, and exact manifested target.

The plan and result do not read Objet bytes, call a provider, check the network,
echo a label or zettel body, or disclose an absolute local path.

Both selectors enforce the same archive-wide identity rule. `--zettel-id` and
`--path` each perform a bounded, handle-bound scan of both `zettels/` and
`inbox/`; the selected Zettel id must occur exactly once, and a `--path`
selection must be that same file identity and exact bytes. A direct canonical
filename is not a shortcut around duplicate-id detection. WOM repeats this
uniqueness proof under the control artifact immediately before mutation and
again after canonical, receipt, control, and manifested-target readback. A
duplicate or target-identity drift at that final boundary enters the same CAS
rollback and retained-evidence reconciliation path instead of returning
success.

That proof is a stable namespace snapshot, not two unrelated directory lists.
On Windows, WOM arms a non-recursive archive-root name watch plus subtree
`ReadDirectoryChangesW` watches for existing `zettels/` and `inbox/` roots
before scanning. It holds every discovered directory, records the complete
entry inventory, and re-reads every Markdown file to verify identity, mode,
link count, size, modification/change timestamps, platform attributes, and
SHA-256. After a first revalidation it arms one archive-root subtree closing
guard, repeats the complete revalidation, cancels the earlier watches while
that guard remains active, and cancels the guard last. `CancelIoEx` and
`GetOverlappedResult` must prove a still-pending watch ended only by the clean
cancellation. A cross-root move, in-place rewrite, missing-root creation,
notification overflow, unsupported watcher, or ambiguous completion therefore
fails closed before the resolver returns. POSIX keeps the same directory file
descriptors open and repeats full directory and file version-token, inventory,
identity, and digest validation. An in-place change cannot pass merely by
restoring the former content bytes because the held file version token must
also remain exact. The archive-root inventory is captured before WOM probes
`zettels/` or `inbox/`, so a directory created immediately after an absence
result changes the retained root baseline instead of becoming an unscanned
part of it.

The final manifested-target proof is not a separate earlier check. While the
Windows archive-subtree closing guard remains armed, WOM holds the exact
manifest parent and single-link file, validates its identity, metadata, bytes,
and approved record set, revalidates the complete Zettel snapshot, and reads
the same manifest observation back unchanged. POSIX brackets that Zettel
revalidation with the same held parent token, file identity, metadata, and
exact-byte checks. This supplies one point where the manifest provenance and
unique Zettel authority are both valid; alternating a duplicate and a missing
manifest cannot compose two unrelated passing checks into success.

The archive identity is also approval-bound input, not ordinary configuration
convenience. Both the core operation and the live CLI approval boundary read
the held `archive.yml` bytes with the duplicate-key-rejecting approval YAML
loader, normalize one bounded acyclic JSON-safe value tree, and require the
exact-human archive-id grammar. Duplicate keys at any depth, aliases that form
a cycle, non-finite values, custom tags, or an invalid archive id block before
approval or mutation without echoing configuration content.

## Upgrade impact

v0.4.0 beta testers who need the single approved Zettel–Objet link apply, the
parser-derived approval inventory, or the common JSON error envelope should
upgrade. No archive migration is required, and the Zettel rules are unchanged.
Existing v0.1 link receipts remain readable; new successful applies emit v0.2
receipts.

This release adds `cli-error-v0.1.schema.json` and
`command-approval-status-inventory-v0.1.schema.json`. It changes
`operation-exact-human-approval-v0.1.schema.json` and
`zettel-objet-link-receipt.schema.json` to bind the reopened operation and its
complete recovery evidence. These schema changes do not authorize any other
writer.

## Operator workflow

Start with a fresh preview from the exact v0.4.1 process:

```powershell
archive zettel-objet-link <archive-root> `
  --zettel-id <zettel-id> `
  --object-id sha256:<64-lowercase-hex> `
  --role <reviewed-role> `
  --dry-run `
  --format json
```

After reviewing that content-free result, repeat the exact target, object,
role, and optional label with the returned `summary.plan_sha256` value:

```powershell
archive zettel-objet-link <archive-root> `
  --zettel-id <zettel-id> `
  --object-id sha256:<64-lowercase-hex> `
  --role <reviewed-role> `
  --expected-plan-sha256 <64-lowercase-hex> `
  --reviewed-by person:reviewer-id `
  --approve `
  --format json
```

`--path` may replace `--zettel-id`. `--label` is optional. Whichever selector
and label were previewed must be repeated exactly for approval. The native
dialog is authority; `--approve`, an actor string, an old receipt, or an old
plan digest alone is not authority. MCP exposes no exact-human writer.

If an approval claim remains `started`, the effect is uncertain, or the result
requires approval-claim reconciliation, do not retry automatically. Preserve
the evidence and inspect that exact claim first.

## Current approval visibility

`archive capabilities --machine` now includes a parser-derived approval-status
inventory. Each canonical command path is classified as:

- `approval_available`;
- `approval_fixed_closed`; or
- `approval_not_exposed`.

The inventory reports aliases separately and records whether `--dry-run` is
exposed. It describes the shipped parser only. It does not open an archive,
check prerequisites, call a provider, or prove that a command without
`--approve` is read-only.

The current canonical fixed-close inventory contains 78 commands. The only
change from v0.4.0 is removal of `zettel-objet-link`. The v0.4.0 release note's
exact 79-command inventory is historical and remains unchanged.

Covered CLI usage, validation, precondition, and fixed-policy failures now use
the content-free `wom-kit/cli-error/v0.1` JSON envelope when JSON output is
requested. Usage failures return exit code 2; policy and operational failures
return exit code 1. Failure output declares effect uncertainty conservatively
and never echoes private argument values.

## Still fixed closed

The following boundaries did not reopen:

- `zettel-objet-link-revert` remains preview-only;
- Objet capture enablement, selection, single capture, and batch capture remain
  preview/plan-only;
- `project-version-update`, collision mutation, and
  `project-bytecode-repair` remain preview/inspection-only; and
- all other v0.4.0 fixed-closed routes remain closed unless their own future
  release explicitly implements a complete operation-specific binding.

An exact snapshot being written for the newly approved link does not make the
revert writer approved. Historical capture, update, or revert receipts remain
evidence only.

## v0.4.0 to v0.4.1 global CLI bootstrap

After the matching public Release actually lists the exact wheel, replace an
existing `uv tool` v0.4.0 installation with:

```powershell
uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.1/wom_kit-0.4.1-py3-none-any.whl"
archive --version
```

Close older WOM processes first and require exactly `archive 0.4.1` from a new process.
This replaces only the isolated global Python CLI selected by `PATH`. It does
not update `.zettel-kasten/source`, a project pin, an archive, or an AI-host
Agent Skill installation. Because the project updater is still fixed closed,
an existing project-local v0.4.0 mirror remains v0.4.0. Do not hand-edit the pin
or claim that the project mirror was upgraded.
