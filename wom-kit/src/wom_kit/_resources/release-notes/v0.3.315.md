# WOM-kit v0.3.315

Letters 127-128 project-update preview parity and paired-batch recovery.

Status: v0.3.315 implementation and release scope. The source implementation
and local tests may be complete in this worktree, but this note does not prove
merge, external CI, exact tag, GitHub Release, packaged wheel publication,
fresh installation, real-project or real-archive execution, or human
acceptance.

## Project-update preview parity

- A locally available exact target now uses one shared materialization planner
  in dry-run and approval. The plan binds a
  `materialization_plan_sha256` and opaque entries such as
  `update-entry:0001`; an unfetched target remains explicitly deferred until
  approved fetch and verification.
- One cross-tree component comparison scheme covers NFKC, case-folding,
  HFS-ignored characters, Windows trailing-space/dot and reserved-name rules,
  `.git` aliases, and conservative Win32 8.3-looking names. Exact raw tracked
  membership is checked before canonical aliases. Ignored aliases and even an
  empty ignored descendant directory cannot silently become a target file.
- Approval rechecks the exact target/tree mapping, ignored state, HEAD and
  tracked-byte authority immediately before mutation. After the bounded
  planner finishes, the materializer compares the complete approved source
  snapshot one final time immediately before its first path write. A changed
  source is preserved, the owned lock is released, and a fresh dry-run is
  required instead of reusing the prior approval. A pre-HEAD exact
  verifier failure triggers bounded self-rollback when that rollback can be
  proved; otherwise the owned lock and evidence are retained for recovery.
- Public results return fixed codes, counts, and opaque references, not ignored
  local names, paths, bytes, byte hashes, or private identity values.

## Collision inspection and preservation

The alias-free CLI-only `project-version-update-collision` command can inspect
one bound collision or separately preview/approve `preserve-relocate`. Eligible
preservation is limited to one bounded, ignored, regular, non-reparse,
single-link obstruction. Windows retains the opened source and destination
identities and performs one same-volume no-replace rename; it does not delete
or overwrite the payload, copy as fallback, fetch a target, retry the updater,
or change a pin.

The private intent, relocated payload, and private completion receipt are
rechecked through exact handle-bound identity and bounded content reads. This
is `unauthenticated_private_state_internal_consistency`, not a MAC, signature,
ACL, or defense against a coordinated same-user rewrite. A terminal observation
does not pretend it evaluated a fresh updater plan. The final lock-absence fact
is reported only after release and a separate missing-path verification.
Unexpected approved-path exceptions use nullable relocation fields and
`writes: null` with `writes_may_have_occurred: true`; they never invent a
zero-write result. `operation-control` routes successful, blocked,
preview-only, restart-required, no-change, and unknown updater statuses
separately.

After any successful preservation, run a fresh updater dry-run and approve the
new updater plan separately.

## Paired multi-item objet capture

- `objet-capture-batch` now preserves the reviewed pairing fields instead of
  dropping the derived-text half when it builds the exact selection.
- The wrapper binds the exact reviewed request, generated selection, lower
  capture `selection_sha256`, and attempt-specific `attempt_sha256` receipt. A lower result
  must match the expected archive, item set, selection manifest id, selection
  SHA-256, item shapes, receipt route, and exact `files_written` delta before
  completion is claimed.
- Original and derived work have separate requested, written or ready,
  skipped, and blocked partitions. Approved completion requires each requested
  original and derived item to land in exactly one terminal partition.
- Staged original and derived sources use stable bounded reads with a 64 MiB
  per-file ceiling and revalidation. Derived metadata remains bound to the
  exact reviewed selection.
- Post-publication observation is tri-state: `verified_exact`, `not_written`,
  or `ambiguous`. This is distinct from result states such as
  `evidence_incomplete` and `recovery_required` and from the blocker code
  `batch_capture_outcome_unverified`. When an exception or publication
  ambiguity follows possible durable writes, WOM returns fixed safe next
  actions; it does not guess counters, claim atomicity, or automatically replay.

## Recovering a v0.3.314 partial pair

1. Keep the original reviewed batch request unchanged and run a fresh v0.3.315
   dry-run.
2. Review the new plan, then approve that exact plan. Exact existing originals
   converge as skipped while missing derived text can complete.
3. If original staging bytes are unavailable, use durable original capture
   receipts to obtain the source object IDs and finish through a separately
   reviewed `derive-text capture --from-manifest` request. Do not recopy an
   original merely to obtain its ID.
4. Treat `partial`, `evidence_incomplete`, `recovery_required`, and
   `batch_capture_outcome_unverified` as explicit review states. Follow only
   the fixed `next_safe_actions` returned for that state.

## Install and verify

1. Confirm that the exact v0.3.315 GitHub Release exists and lists the verified
   `wom_kit-0.3.315-py3-none-any.whl`.
2. Replace the isolated v0.3.314 tool environment with that exact artifact;
   updating repository files alone does not update an installed wheel.
3. Start a new process and run `archive --version` or `archive version`.
4. Run the relevant project-update or batch workflow as a fresh dry-run before
   any approval.
