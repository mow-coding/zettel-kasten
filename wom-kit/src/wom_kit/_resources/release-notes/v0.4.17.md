# WOM-kit v0.4.17 — Recoverable Terminal Cleanup Without Human Forensics

v0.4.17 closes a recovery loop left open by v0.4.16. A project-update preview
and its approval path now use the same bounded, read-only classification of the
private transaction namespace. Exact terminal control history no longer lets a
dry-run report `ready_for_approval` only for the matching approval to fail
before it can return a useful result.

The public command surface is unchanged. A person is not asked to count files,
compare hashes, find transaction identifiers, or decide which private control
artifacts are safe to delete. WOM verifies those facts. The person decides only
whether the project should be updated and affirms that other writers for the
same project are paused.

Approved project-update mutation, same-version repair, and mutation-bearing
resume remain Windows-only. POSIX supports preview and read-only inspection;
those mutation paths fail closed without writing.

## One preflight for dry-run and approval

Before a fresh update plan or native decision, both paths run the same
content-free cleanup preflight. The result is one of three public outcomes:

- ordinary absence or canonical proof-only history permits the normal fresh
  preview;
- exact terminal control history returns `terminal_cleanup_required` with
  `project_version_update_terminal_cleanup_required`; or
- partial, malformed, mixed, changing, ambiguous, or unsafe residue returns
  `terminal_cleanup_outcome_unknown` with
  `project_version_update_terminal_cleanup_outcome_unknown`.

`terminal_cleanup_required` is a useful blocked result, not a generic exception.
It reports no private paths, hashes, transaction references, approval
identifiers, or raw error text. Its `next_safe_actions` direct the operator to
the identifier-free `project-version-update --resume` command and explicitly
forbid a fresh approval until recovery has completed. The approval path applies
the same gate before opening native approval or entering the domain writer.

Unknown residue remains fail-closed. WOM does not guess which operation created
it, infer success or cancellation, loop automatic retries, or authorize manual
lock, pin, transaction-directory, tombstone, or proof deletion.

## Exact preapproval-abort history compaction

An update cancelled before intent seal deliberately leaves an exact durable
abort receipt. v0.4.16 could validate that receipt in one recovery path but the
fresh-update namespace classifier still treated the retained directory as an
unknown blocker. Repeating a normal preview and cancelling before approval
could therefore make every later fresh approval unusable.

v0.4.17 recognizes only the exact terminal abort form produced by WOM itself.
Identifier-free `--resume` binds its fixed file set, file identities, hashes,
reservation evidence, abort receipt, transaction-root identity, archive
identity, and cleanup authority into an identity-bound v0.4.17 cleanup plan. Cleanup first moves
the exact directory to a no-replace tombstone, removes only the plan-bound
members, and retains one canonical proof. Interruption at the original,
planned-original, tombstone, proof-link, or final-proof boundary resumes
idempotently from the same authority.

This compaction is private control-history reconciliation. It does not run the
project-domain writer, change the project source mirror, install a runtime,
change the version pin, alter archive content, or attribute a past update
success, and it grants no fresh approval authority. An unexpected member, unsafe file type,
identity change, link anomaly, changed byte, active lock, or namespace race
refuses cleanup and preserves the evidence.

Canonical cleanup proofs remain inert audit history. Proof-only state still
returns `no_resumable_project_update`, attributes no past success, independently
verifies no current project state, and requires a new preview and one fresh
approval for any new update.

## Effect truth after mixed or partial recovery

Recovery can compact one exact abort history before a later history refuses, or
can compact history while another authenticated resume also completes. The
public result therefore reports `terminal_abort_histories_compacted`,
`cleanup_proofs_written_or_verified`,
`terminal_abort_history_compaction_state`, and
`terminal_abort_history_compaction_incomplete`. `complete`, `partial`, and
`incomplete` remain distinct.

`files_written_scope: project_domain_only` means `files_written` names only
project-domain files. An empty list is not a claim that no private control
evidence changed. The content-free `effect_summary` separately reports
`private_control_mutation_performed_or_verified` and
`private_control_mutation_may_be_incomplete` without exposing paths,
transaction references, hashes, or cleanup authority.

## Terminal document and mixed-state hardening

Every authority-bearing terminal result is now read through a held parent
chain and an exact named file handle. The reader requires a regular single-link
file, bounded canonical bytes, stable identity, and the supported private-file
metadata. On Windows it also requires the default data stream only. A hard
link, reparse point, alternate data stream, filename substitution, or parent
namespace swap is rejected before terminal state can authorize replay,
delivery, acknowledgement, or finalization.

That exact terminal-document rejection is projected as
`project_version_update_terminal_cleanup_outcome_unknown` by the public recovery
gate, so it cannot fall back to a generic command error. Only the fixed internal
`project_version_update_terminal_handoff_invalid` code receives this projection;
other internal exceptions remain private and fail closed.

An exact active transaction is not permission to ignore its siblings. The
cleanup classifier now proves the active preapproval or authenticated state and
every other namespace entry together. A malformed tombstone, unknown name,
unsafe type, or other unresolved sibling returns
`project_version_update_terminal_cleanup_outcome_unknown` before recovery,
native approval, or domain-writer entry. Cleanup plans and canonical proofs use
the same Windows default-stream-only rule, so hidden stream data cannot ride a
valid proof into proof-only history.

## One held terminal authority boundary

The last read-only check is not treated as permanent authority. Fresh approval
and mutation-bearing resume acquire the project terminal guard, re-read the
exact active handoff under that guard, and keep the same guard held through the
native decision, claim checkpoints, domain writer, terminal publication, and
cleanup finalization. Nested terminal publications reuse only that exact bound
lease; a different transaction state cannot borrow it merely because it uses
the same project directory.

Terminal-ready replay holds the same guard while it revalidates the ready
document, reauthenticates the result, derives its delivery capability, and
performs exact cleanup. A `claim_succeeded_pre_unlock` handoff must correlate
with either its exact active transaction or the exact same transaction's
recoverable cleanup tombstone. An unrelated active transaction or tombstone is
unknown mixed state and authorizes no replay or cleanup.

At the CLI delivery boundary, WOM takes strict active-handoff snapshots before
and after operation-journal discovery. Absence becoming presence, presence
becoming absence, a state or digest change, or disagreement between the active
handoff and the discovered delivery candidate returns the same content-free
cleanup-unknown result. An unrelated operation-control error is still not
relabelled or exposed. These checks preserve an exact consumed or
display-pending delivery without letting discovery race a second session.

A stable active handoff may correctly have no complete delivery journal yet:
the process can stop before cleanup, and a cleanup-incomplete result cannot
claim a delivery proof. That exact unchanged state now proceeds to the held
authenticated replay instead of being mislabeled as unknown. The replay still
verifies the claim, postimage, transaction, and cleanup authority before doing
anything; changed, malformed, mismatched, or ambiguous state remains blocked.
Adversarial recovery tests start from a real process loss and independently
change the pending attachment binding, ready-record binding, and transaction
correlation; every case stops before writer or cleanup entry and preserves the
exact evidence without reflecting its private values.

Any fresh approval or resume that can create a new result output now holds the
same project terminal boundary before output capture begins and keeps it
through the service result, immutable output, completed operation journal, and
`active` to `display-pending` acknowledgement. A competing same-project process
loses before it can create another journal or enter a writer. After acquiring
that boundary, WOM repeats the complete strict delivery discovery, not only the
`active` file read. A newly appeared `display-pending` capsule, a newly complete
journal for the same still-active capsule, any changed handoff observation, or
any unsafe or ambiguous discovery therefore stops before output capture,
archive identity access, native approval, or project writing. Pending discovery
and the stdout-observed move to the hash-named consumed capsule happen after
that outer boundary is released. A boundary-close failure exposes no private
error and preserves the pending capsule for exact resume.

## Bounded Windows candidate settling

The first bytecode read of a newly owned preapproval runtime candidate may see
one short directory-generation change immediately after venv, pip, and owned
script mutations. WOM retries only the exact content-free
`project_runtime_tree_changed` result, at most three strict scans with short
increasing backoff. Every scan still requires the complete tree shape to match
before and after hashing, and no deletion begins before one stable inventory is
returned. Unsafe, unreadable, colliding, reparse, oversized, persistent, or
nonexact failures are not retried, and all later wheel, payload, receipt, seal,
and hard-link verification remains unchanged.

## Existing authenticated transaction recovery

If the namespace contains one exact authenticated transaction at its supported
terminal checkpoint, `--resume` continues the existing v0.4.16 terminal-handoff
and exact-cleanup contract. It reuses the existing succeeded claim and cleanup
authority, never opens a second native decision, and never reenters a completed
domain writer. The immutable `active` -> `display-pending` -> hash-named
`consumed` result handoff remains unchanged.

Exact completed abort histories may be compacted in the same recovery pass.
Fresh update planning becomes available only after every recognized control
history has converged to canonical proof-only history and no authenticated
transaction still requires resume.

The ordinary recovery command remains identifier-free:

```powershell
& <exact-v0.4.17-bootstrap> project-version-update <project-or-archive-root> `
  --resume `
  --affirm-external-writers-quiescent `
  --progress `
  --format json
```

After recovery returns a terminal result, run a new dry-run. If that preview is
ready, request one normal exact human approval. Do not reuse a stale preview or
approval and do not supply private recovery identifiers.

## Privacy-safe command failure evidence

Known cleanup gates are projected through a strict allowlist into a structured
v0.4.17 CLI failure result. The result and any bound diagnostic output preserve
the fixed reason code and actionable next step while explicitly reporting that
private paths, identifiers, values, and raw errors were not echoed.

`ArchiveServiceError` remains a private internal exception boundary. Arbitrary
exception messages, even code-shaped strings, are never reflected into public
JSON. Any failure outside the exact cleanup allowlist retains the generic
privacy-safe command-failure behavior.

## Updater bootstrap contract

After the matching GitHub Release exists and lists the exact wheel, create a new
external CPython 3.12 environment and invoke its real `python.exe -m pip`:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0417-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.17/wom_kit-0.4.17-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.17` from a new process. The versioned URL alone is
not proof that a release or asset exists. Publishing or installing v0.4.17 does
not inspect or modify a client archive, project source mirror, runtime, version
pin, credential, provider, or remote service. The client chooses whether and
when to run the separately reviewed recovery and project update.
