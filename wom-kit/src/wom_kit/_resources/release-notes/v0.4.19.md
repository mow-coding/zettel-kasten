# WOM-kit v0.4.19 — Runtime And Capability Truth

v0.4.19 makes `project-version-update`, runtime inspection, command availability, and
Windows process launching report one consistent operating truth. It does not
open a new archive writer. It fixes the shared evidence and dispatch boundary
that later recovery writers depend on.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed project update. The release is not evidence that a client runtime was
repaired; that requires the client-run result and a new-process verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0419-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.19/wom_kit-0.4.19-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.19` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## Four observation states

Runtime integrity evidence keeps its established boolean fields for older
readers and adds a content-free `checks` map. Every check now has one of four
states:

- `passed`: the check ran and the expected condition was observed;
- `failed`: the check ran and observed a contradiction;
- `not_reached`: an earlier prerequisite stopped this check from running; or
- `unavailable`: WOM attempted the check but could not obtain trustworthy
  evidence.

A false legacy boolean therefore no longer has to be guessed as an observed
failure. For example, if source inspection stops before origin inspection,
`origin_configured` remains false for compatibility while
`checks.origin_configured.state` is `not_reached`, not `failed`.

Live project-runtime payload inspection follows the same distinction. A
payload whose observed bytes differ from its bound receipt is `failed` with a
mismatch reason. A payload that cannot be read safely is `unavailable`; it is
not mislabeled as a mismatch. Legacy inspection maps without the new state
fields remain readable.

## Field-level runtime-preparation revalidation

The approved project updater no longer reduces its preparation revalidation to
one unexplained boolean. It compares the following dimensions without
returning their values:

- Git snapshot, trusted Git configuration, and local Git metadata;
- project version pins, target refs, and target evidence;
- runtime policy, dependency supply lock, and bootstrap evidence;
- runtime plan and launcher snapshot;
- materialization preflight and prepared-runtime payload; and
- the source branch when one applies.

The result records a state and fixed reason code for every dimension, lists
only the names of changed or unavailable dimensions, and explicitly excludes
expected transaction effects such as the durable reservation, update lock,
private prepared candidate, and progress observations. Paths, refs, labels,
digests, and compared values are not echoed.

An exact healthy same-version target remains a no-op: WOM verifies retained
wheel and dependency bytes, trusted interpreter startup files, package resources,
and a fresh runtime process before downloading or building any candidate. It
revalidates source, refs, pins, policy, supply, and launcher before returning;
it creates neither a second approval nor a new domain receipt. A
damaged same-version runtime remains an atomic repair with the established
checkpoint and forward-resume contract. A preparation drift aborts the
unsealed candidate and preserves the active runtime and pin.

The no-op closes only its own pre-approval reservation using that reservation's
validated abort receipt and the existing exact cleanup protocol. It does not
leave active control history that prevents the next ordinary preview. Partial
or interrupted cleanup remains an explicit incomplete result; a competing
writer's lock and bytes are preserved. Unavailable probes or a generation that
changes during observation do not grant permission to repair.

Runtime and source-mirror walks do not treat a directory's allocation size as
file-content evidence. A directory-size-only change cannot reject identical
files; actual membership, file identity, byte hash, replacement, or reparse
changes still fail their exact checks.

Waiting for another updater's reservation is reported as contention, not
evidence of damaged data. The wait is bounded, progress remains visible, and
busy or unavailable lock observation grants no takeover, repair, cleanup, or
replacement approval. Unsupported native legacy mutations fail explicitly on
other platforms; their read-only inspection and portable validation remain.

## One command-availability decision

`CapabilityAvailability v0.1` is the content-free decision shared by command
help, `capabilities`, Doctor suggested-command status, dry-run interpretation,
and CLI dispatch. It reports one of:

- `available`;
- `writer_unavailable`;
- `mode_unavailable`; or
- `not_requested`.

The decision is derived from the real parser action, requested mode, and the
fixed-closed writer inventory. An approval flag that is fixed closed is now
rejected as `writer_unavailable` before a handler, runtime guard, private
target read, provider call, or mutation can run. Existing operation-specific
fixed reason codes, lifecycle action identifiers, and command-specific JSON
defaults remain available for compatibility. Provider and archive
prerequisites are still evaluated by their domain guard after the command
surface itself is available.

Historical approval exposure is distinct from successful use. Nine previously
exposed paths now restricted by the exact-approval migration carry that history
in the same inventory instead of being described as never implemented. These
annotations do not reopen a writer or recommend an older-version workaround.
AI draft previews also distinguish valid draft input from current-index write
readiness, so an approval handoff cannot promise a write that its index
prerequisite would reject. Unreadable index evidence is not an instruction to
rebuild an index while another writer may be active.

## No transient console for background work

All production subprocess launch sites now declare their Windows visibility
policy through one helper. Noninteractive children receive
`CREATE_NO_WINDOW` on Windows and no extra flag on other platforms. The single
credential-vault unlock route that can require a person to interact with the
child remains explicitly visible. Native exact-human approval dialogs,
content-free progress, errors, and receipts are unchanged.

The source test inventories every direct production subprocess launch. It
requires each noninteractive launch to use the common policy and requires the
interactive exception to stay explicit, so a later child process cannot
silently reintroduce the flashing black console.

## Doctor generation reuse and progress

The `archive` and `wom` console entrypoints and project launchers for v0.4.19
onward enter a small startup module before loading the full implementation.
Existing progress-enabled commands can therefore report a content-free
preparation state during startup. A no-console helper keeps that heartbeat
independent of Python compilation and ends on parent loss, cancellation,
failure, or handoff to the actual command reporter. It receives no operation
arguments and performs no archive or provider work. Help, quiet modes, and JSON
stdout retain their contracts; the exact single `--version` invocation uses the
same version output without loading the full command implementation.

Older target versions keep their original project launcher. Direct
`python -m wom_kit.archive_cli` and MCP remain compatible, but the startup
timing improvement is verified through the new public console/project launcher,
not inferred from those legacy entrypoints. Installed-wheel verification times
the first status and every gap through process exit and pipe closure.

The archive-root boundary stage no longer obtains two filesystem observations
for the same directory entry. One `lstat` generation supplies its type and
identity projection while descriptor reads and completion revalidation remain
in place. Directory allocation size alone is excluded from root and inventory
identity; file size, directory identity/type/reparse state, timestamps, and the
observed member set remain bound. Doctor retains content-free start output and an independent
heartbeat no more than ten seconds apart. Operational Doctor keeps its existing
180-second per-run limit. The historical count-scale benchmark is retained,
and a separate mixed-payload fixture varies object and body sizes and uses
independent mint source/snapshot pairs. Reports name the profile and total
bytes. The historical 30-byte objects do not demonstrate client-scale byte
verification performance. Deep-byte throughput is reported separately, with an
explicit finite regression budget rather than a size-independent completion
promise. Generated fixtures have uncontrolled OS caches and are not advertised
as cold-cache client measurements.

Minted-draft twin diagnostics reuse Doctor's generation-bound observations of
the source, canonical target, and receipts. They no longer call a retirement
write planner that rereads the complete index for every draft. A diagnostic
match is not retirement authority: the actual planner and writer still enforce
their own current index and exact approval. Completed-inventory drift must
invalidate the diagnostic result rather than turn a stale snapshot into a
successful observation.

## Compatibility and privacy

Interrupted updates distinguish authenticated completed predecessor cleanup
from prewrite recovery. Resumed bootstrap comparisons retain the exact version,
tag, filename and wheel SHA-256 instead of comparing the sealed never-fetch URL
placeholder with the running public wheel URL. Public-origin verification and
the original claim/cleanup evidence checks remain mandatory.

Git backup validates and independently freezes selected observations against
their exact approved source, commit-message bytes and manifest before writing.
Changing a caller's nested observation dictionaries cannot replace approved
bytes. This reuses the historical private-bundle decoder; valid legacy bundle,
manifest and approval serialization is unchanged.

- The CLI command inventory is unchanged.
- Older runtime evidence readers can continue using the legacy booleans.
- New availability and revalidation records contain fixed names and states,
  never private compared values.
- Windows console suppression is limited to noninteractive child processes.
- No credential value, provider identifier, archive path, client label, or
  target content is introduced into public tests or release artifacts.

## Verification boundary

The release candidate is required to pass focused runtime, capability, Windows
process, interruption/resume, drift, privacy, package-resource, installed-wheel,
and full supported-platform CI checks. The exact reviewed merge commit must be
tagged, and the public wheel must be downloaded anonymously, rehashed, installed
in a fresh CPython 3.12 environment, and checked in a new process.

Those steps prove the public release. They do not prove a client result. The
client-side AI must use the project launcher and exact public bootstrap,
perform the reviewed update, start a new process, and verify the project pin,
launcher, source, and runtime evidence. A feedback record remains unresolved
until that durable client evidence exists.
