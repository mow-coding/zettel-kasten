# WOM-kit v0.3.288: Content-Free MCP Error Boundary

Release date: 2026-07-30

## What Changed

v0.3.288 closes a shared privacy gap in the local stdio MCP server.

Before this release, a failed MCP tool could copy an internal exception
message into both its human-readable `content` and
`structuredContent.error`. Depending on the failure, that message could
contain an archive path, archive id, zettel id, filename, frontmatter value,
provider detail, or other caller-controlled text.

Every failed MCP tool now returns one fixed envelope:

```json
{
  "content": [
    {
      "type": "text",
      "text": "Tool execution failed."
    }
  ],
  "structuredContent": {
    "error": "tool_execution_failed"
  },
  "isError": true
}
```

The envelope identifies the outcome without carrying the internal reason.
Successful tool results are unchanged.

## Fixed JSON-RPC Messages

Protocol-level failures now use only the standard fixed categories:

- `Parse error`
- `Invalid Request`
- `Method not found`
- `Invalid params`
- `Internal error`

Unknown method names, unknown tool names, validation details, exception text,
and request values are not interpolated into error `message` or `data`.
A valid JSON-RPC request id is still returned unchanged in the top-level `id`
field so the client can correlate the response required by the protocol.

## Stricter Request Shapes

The server previously used a falsey-value shortcut when reading `params` and
tool `arguments`. Values such as `false`, `0`, `""`, and `[]` could therefore
be treated like an empty object.

Only literal JSON `null` and `{}` now become an empty parameter object. Every
other non-object value is rejected as `Invalid params`.

## Stdio And JSON Validity

The stdio boundary now handles malformed transport input without printing a
Python traceback:

- invalid UTF-8 becomes fixed `Parse error`, and the next line can still run
  only when that error response was delivered; a failed stdout stops the
  server before any later tool request is handled;
- excessive JSON nesting becomes fixed `Internal error`, and the next line
  can still run;
- `NaN`, positive/negative `Infinity`, and overflowing JSON floats are
  rejected instead of becoming non-standard JSON-RPC values;
- request ids are limited to JSON `null`, strings, non-Boolean integers, and
  finite floats;
- escaped lone-surrogate strings are emitted through ASCII-safe JSON escapes;
  and
- a closed stdout ends the server quietly instead of writing internal paths or
  exception details to stderr.

If a successful tool result cannot be encoded as strict JSON, that tool call
is replaced with the same exact content-free failed-tool envelope. A
non-tool server response that cannot be encoded becomes fixed
`Internal error`.

## What Did Not Change

This release adds no:

- MCP tool or CLI command;
- archive write or migration;
- provider, model, credential-store, or network call;
- change to archive-service behavior;
- relaxation of allowed-root, dry-run, approval, or redaction checks; or
- beta-archive operation.

Detailed exception text can still exist inside the Python process for
debugging and exception chaining. The guarantee is narrower and testable:
those details do not cross the MCP wire boundary.

## Verification

Release verification is planned against:

- exact fixed-envelope equality for every tool failure;
- sentinel secrets in direct tool, service, unexpected-exception, unknown
  method/tool, and invalid-parameter failures;
- strict `params` and `arguments` type handling;
- unchanged successful initialize, ping, tools/list, and representative tool
  calls;
- retained no-write, approval, dry-run, allowed-root, and redaction checks;
- the complete source test suite;
- release-readiness and deterministic resource checks; and
- a clean wheel with four entrypoints, onboarding, and strict Doctor.

No test count, wheel SHA-256, remote CI result, tag, GitHub Release, public
artifact result, or beta validation is claimed before later evidence exists.
