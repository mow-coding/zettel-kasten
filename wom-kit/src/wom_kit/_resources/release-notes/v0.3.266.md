# v0.3.266 - Read-Only Abstract Recovery Decisions

v0.3.265 made interrupted abstract apply and revert batches observable.
v0.3.266 decides what each observed state means for a later recovery executor
without changing the archive.

## What Changed

Added:

```text
archive zet-abstract-backfill-recovery-plan <archive-root> --dry-run
archive abstract-backfill-recovery-plan <archive-root> --dry-run
```

The command reuses the bounded receipt, lock, journal, and canonical hash audit.
It returns one privacy-safe case per retained journal with:

- operation and basis SHA-256 case handle;
- observed participant state and counts;
- verified, absent, present-but-unverified, or unknown final receipt state;
- present, missing, unsupported, or unknown expected lock state;
- one fixed recommended action and reason code;
- the number of participant and receipt writes a future approved executor would
  require.

It never executes the recommendation.

## Recovery Decision Matrix

The fixed policy is:

- `prepared` -> `cleanup_unstarted_transaction_evidence` after fresh approval;
- interrupted apply -> `rollback_uncommitted_apply_to_before`;
- partial revert -> `resume_revert_forward_and_finalize_receipt`;
- fully reverted without a receipt -> `finalize_revert_receipt`;
- `stale_completed` -> `cleanup_verified_completed_evidence` only after the full final receipt
  lifecycle verifies;
- `divergent`, `invalid`, or a deterministic final receipt that exists but does
  not verify -> retain everything in manual forensic hold.

Apply rollback can reconstruct exact before bytes by removing the inserted
abstract and checking its hash. Revert rollback cannot generally recreate
removed private abstract text because journals and receipts intentionally store
only hashes. Finishing an approved revert forward remains reconstructible.

## No File Existence Shortcut

The planner distinguishes:

```text
verified
absent
present_unverified
unknown
```

A zero-byte, malformed, externally created, or current-state-diverged receipt
never becomes evidence that the transaction committed. It forces
`manual_forensic_hold`.

## Approval And Write Boundary

Every case says:

```text
fresh_recovery_approval_required: true
current_state_revalidation_required: true
execution_implemented: false
safe_to_execute_now: false
```

The command writes or deletes no canonical file, receipt, journal, or lock. It
does not automatically run on apply/revert startup. Cross-basis participant
serialization remains a separate concurrency design.

## Privacy

The basis SHA-256 is the same case handle already permitted by the older
receipt/lock audit surface. Output does not contain journal or receipt paths,
zet ids or paths, reviewer, proposal filename, body or abstract text, journal
digest, lock content, or absolute local paths.

## Compatibility

No archive, zet, receipt, journal, proposal, or index migration is required.
The command reads v0.3.265 journals and existing v0.1 receipt schemas. Older
WOM-kit versions ignore the new planner because it creates no archive artifact.

## Verification

Regression coverage includes:

- command and alias discovery plus strict `--dry-run`;
- empty archives returning `no_recovery_needed`;
- every apply state, verified completion residue, and unverified final receipt;
- partial and fully applied revert decisions moving forward without claiming
  private-text reconstruction;
- missing lock evidence;
- explicit bounded-case truncation;
- zero writes/deletes and no private metadata or text echo;
- unchanged v0.3.265 hard-exit and completed-journal audit classifications.
