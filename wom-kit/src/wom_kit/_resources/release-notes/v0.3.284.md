# WOM-kit v0.3.284: Activity-Group Membership Removal Write And Recovery

Release date: 2026-07-30

## Separate Approval-Gated Removal

v0.3.284 continues the read-only removal plan with a dedicated CLI writer:

```powershell
archive activity-group-membership-removal-write <archive-root> `
  --request .wom-scratch/private/activity-group-removals/reviewed.json `
  --expected-request-sha256 sha256:<request-digest> `
  --expected-review-plan-sha256 sha256:<review-plan-digest> `
  --dry-run --progress --format json
```

The approved form requires `--approve`, a safe `--reviewed-by` value, and
`--affirm-removals-reviewed`. The command also has the
`event-group-membership-removal-write` alias.

Addition and removal remain different authority lanes. An add request,
review-plan digest, journal, or receipt cannot authorize removal. Removal uses
its own request prefix, write/result schema, prepared journal schema, receipt
schema, and receipt directory.

## Exact Smallest Mutation

The writer reconstructs the reviewed removal plan and changes only
`frontmatter.facets.activity_group` for exact `ready_to_remove`
participants. It removes only the named event anchor while preserving:

- other membership ids, order, and list representation;
- every other facet and frontmatter meaning;
- the event anchor;
- body bytes and `updated_at`;
- UTF-8 BOM state; and
- newline convention.

Malformed or ambiguous membership data remains blocked rather than being
normalized.

`already_absent` rows stay in the human review and digest boundary but do not
enter mutation evidence. They receive no snapshot, mutation-journal item,
canonical write attempt, or receipt participant item. When every named
membership is already absent, the command reports `already_satisfied` without
creating transaction artifacts.

## Shared Lock, Separate Evidence

The add and removal writers share one global activity-group writer lock and
one bounded inventory across:

```text
.wom-scratch/private/activity-groups/
.wom-scratch/private/activity-group-removals/
```

Either operation is blocked by any retained add or removal journal. The scan
runs before lock acquisition and again under the lock before snapshots or
canonical mutation. It examines only direct children, is bounded to 5,000
entries across both roots, does not open journal content for discovery, and
fails closed when the inventory is unsafe or incomplete.

The removal prepared journal remains under the private removal root, and its
immutable receipt remains under:

```text
receipts/activity-group-removals/
```

This gives the two operations one serialization boundary without merging
their operation-specific evidence.

## Under-Lock Replanning And Exact Byte Safety

After acquiring the shared lock, WOM reopens the exact request and recomputes
the removal review plan, mutation candidates, and write-plan digest. Any
request, anchor, participant, row-state, or candidate drift blocks before the
first snapshot or canonical mutation.

For every mutation participant, WOM:

1. preserves exact complete before-file bytes in the local content-addressed
   object store;
2. records the snapshot before publishing the prepared removal journal;
3. publishes that journal before the first canonical write;
4. commits through an OS-level compare-and-swap;
5. verifies the complete final participant set; and
6. publishes the immutable removal receipt last.

Compare-and-swap preserves the exact name occupant at commit time. Forward
write, runtime rollback, and approved recovery replace only a known reviewed
state. Unknown concurrent bytes are never overwritten.

Handled failures restore exact prior bytes and remove only the exact evidence
owned by that attempt. A hard exit leaves deterministic private evidence
instead of triggering an automatic or inferred continuation.

## Dedicated Removal Recovery

The read-only recovery plan:

```powershell
archive activity-group-membership-removal-recovery-plan <archive-root> `
  --expected-request-sha256 sha256:<request-digest> `
  --dry-run --format json
```

classifies one retained removal transaction and binds its exact evidence into
`recovery_plan_sha256`. The separately approved executor:

```powershell
archive activity-group-membership-removal-recover <archive-root> `
  --expected-request-sha256 sha256:<request-digest> `
  --expected-recovery-plan-sha256 sha256:<recovery-plan-digest> `
  --approve --reviewed-by <safe-reviewer-id> `
  --affirm-recovery-reviewed --progress --format json
```

executes only the fixed reviewed cleanup or rollback. Both commands have
matching `event-group-*` aliases.

Recovery rebuilds the plan under the shared recovery guard. Exact snapshots
authorize rollback only from the known applied state to the known prior
state. Missing, foreign, malformed, mismatched, changed, or ambiguous evidence
remains non-executable `manual_forensic_hold`.

## Compatibility And Explicit Non-Goals

No archive migration is required. Existing activity-group addition request,
plan, write, receipt, journal, and recovery contracts remain unchanged.

v0.3.284 adds no:

- membership inference or automatic candidate selection;
- direct canonical-edit permission or general facet editor;
- MCP writer;
- provider, model, network, generated-index, database, or credential-store
  dependency;
- automatic hard-exit resume; or
- removal revert operation.

The recovery executor handles only interrupted v0.3.284 removal transactions.
A future deliberate compensation feature must define a separate review and
evidence contract.
