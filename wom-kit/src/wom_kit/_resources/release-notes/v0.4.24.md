# WOM-kit v0.4.24 — Session Permission Modes

v0.4.24 adds per-work-session permission modes — **manual**, **limited** and
**allow_all** — so a person who has claimed a work session can decide once how
the writes of that session are approved, the way the Codex and Claude desktop
apps offer a per-session permission level (beta letters 160 and 161). The mode
is itself one exact human decision on the session. A write the mode permits no
longer opens the native dialog, but it still publishes its own one-use claim
bound to its exact plan and target digests, that claim records that the
permission mode was the mechanism, and every receipt still names its claim.
Project updates, remote providers, the session lifecycle, repairs and overrides
always open the dialog, in every mode. No writer, plan digest, receipt schema
or resume path changes.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.24-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0424-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.24/wom_kit-0.4.24-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.24` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## Granting a mode

`work-session --action set-permission-mode --approve --client-app-ref <app>
--task-route-ref <route> --work-session-ref <session> --request-stdin` with
the private request `{"reviewer_claim": "<id>", "permission_mode":
"manual" | "limited" | "allow_all", "operations": [...]}` opens one native
dialog that shows the mode and, for `limited`, every granted operation kind
by its label, and states that project updates and credential writes still
ask. The decision is bound to the exact registry post-image, recorded on the
actor as a `human_session_decision`, and supports the same `--resume` and
`--approve --review-original` continuations as handoff, accept and recover.
`manual` clears the grant through the same dialog, so who changed the mode is
always on record. The grant lives only while the session is `claimed`: pause,
complete, handoff, the successor's accept and recover all clear it, and a new
claim starts manual. `work-session --action inspect` reports
`permission_mode` and `permitted_operations` (content-free).

Grantable operation kinds: drafts (`create_draft`, `promote_zet`, `mint_zet`,
`retire_draft`, `draft_discard`, `draft_discard_restore`), edges and links
(`zettel_edge`, `zettel_edge_revert`, `zettel_objet_link`), captures and
intake (`objet_capture`, `objet_capture_batch`,
`objet_capture_selection_record`, `source_intake_record`,
`source_intake_batch`, `source_intake_chain`,
`source_fidelity_session_evidence`), revisions (`zet_revision_write`,
`zet_revision_restore_write`) and the reviewed batches (`zettel_edge_batch`,
`zettel_edge_batch_revert`, `mint_zet_batch`, `retire_draft_batch`).
Always-dialog kinds that no mode can grant: `project_version_update`,
`git_backup`, `notion_property_backfill`, `notion_property_backfill_revert`,
`object_storage_setup_registration`, `object_storage_bytes_preservation`,
`object_storage_formal_adoption`, `work_session`, `integrity_repair`,
`duplicate_object_reconcile`, `local_recovery`, `local_recovery_revert`,
`warning_override` and `human_artifact_lifecycle`. Credential writers use
the Windows credential native path and are unaffected by construction.

## Writing under a mode

The AI client keeps the three refs it already retains and exports them as
`WOM_CLIENT_APP_REF`, `WOM_TASK_ROUTE_REF` and `WOM_WORK_SESSION_REF`; a
command that carries its own session refs (`create-draft` since v0.4.23)
uses those. At the single approval choke point the broker resolves the grant
read-only — the route must retain that session, the session must be claimed
under the same claim, and the row must carry the permission — and any doubt
opens the dialog as before. When the grant permits the operation the
decision is produced without a dialog, the dialog path's live target check
is reproduced when a target observer exists, the grant is re-resolved
immediately before the claim is published (a mode cleared in the meantime
fails closed as `exact_human_approval_permission_revoked`), and the claim
is minted with `interactive_intent.mechanism =
"work_session_permission_mode"`. Results carry it as
`exact_human_approval.approval_mechanism` with `live_dialog_shown: false`.
Resume, abandon and original-review paths never consult a grant.

## Truthfulness

A claim minted under a mode is not presented as a human-presence proof: the
two Windows task-dialog mechanisms remain the only live-dialog values, the
permission mechanism is a distinct fixed literal accepted by the claim
validator, and the `public_reference()` block embedded in receipts is
unchanged (the receipt names the claim; the claim states the mechanism).
Putting the mode literally inside receipt JSON would change eleven closed
schemas and is not part of this release.

## Not in this release

Session integration of the remaining pending writer paths (LR-06), MCP
exposure of the create-draft session refs, and a per-command runtime mode
report in `capabilities --machine` carry to later trains.

## Compatibility and privacy

- Existing registry generations, plans, intents, claims, receipts and
  schemas keep their exact bytes and validators; the session row's
  `permission` key, the `set-permission-mode` action's seventh request key,
  the claim's permission mechanism and the summary's `approval_mechanism` /
  `live_dialog_shown` are additive.
- The grant, the query projection and every result carry only fixed mode
  names and operation tokens; no label, reviewer id, path or archive content
  is introduced.

## Verification boundary

The release candidate must pass the focused session, approval, privacy,
package-resource, installed-wheel and full supported-platform CI checks. The
exact reviewed merge commit must be tagged, and the public wheel must be
downloaded anonymously, rehashed, installed in a fresh CPython 3.12
environment and checked in a new process. Those steps prove the public
artifact; they do not prove any client result.
