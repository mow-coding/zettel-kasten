# WOM-kit v0.3.320 — One-Use Credential Capability Broker

Release date: 2026-08-15

This source checkpoint hardens the existing approved Notion page-recovery
worker. It adds no new CLI or MCP command, no new popup, and no generic password
manager. Local source and tests do not prove merge, external CI, exact tag,
GitHub Release publication, wheel publication, fresh installation, live
credential registration, provider acceptance, durable production persistence,
completed page recovery, or human acceptance.

## What changed

After the human approves one unchanged `notion-page-recovery` plan, the parent
now issues a fresh secret-free `wom-kit/credential-capability/v0.1` document.
It binds a random 128-bit capability id to:

- provider `notion`;
- operation `notion_page_recovery_read`;
- consumer `wom:workflow:notion-page-recovery`;
- `GET` only;
- endpoint classes `retrieve_page` and `retrieve_page_as_markdown`;
- registered capabilities `read_content`, `retrieve_page`, and
  `retrieve_page_as_markdown`;
- the exact request digest, plan digest, reviewer, and selected authenticated
  receipt/lifecycle scopes;
- a default 900-second claim deadline;
- exactly one approved worker invocation;
- an exact bounded logical-provider-attempt budget.

One use means one spawned approved invocation, not one HTTP request. A selected
page may need bounded metadata, Markdown, child-block, and retry attempts; each
logical attempt spends the separate request budget.

The expiry is only the deadline to create the durable claim. A claim committed
before that deadline may finish its bounded invocation; expiry does not
interrupt it mid-run. The HTTP adapter performs exactly one transport attempt
per authorized call, so workflow retry must spend another authorization.

## Claim before credential read

The isolated child recomputes all caller-controlled bindings before credential
access. After acquiring only the exact archive authentication key, it
exclusively creates an HMAC-authenticated claim under the ignored local
`profiles/local/credential-capabilities/claims/` surface. That durable claim is
created before the first native Windows Credential Manager read.

Any existing leaf for the same capability id permanently spends it, including
malformed, partial, tampered, unfinished, succeeded, or failed state. A crash or
ordinary failure cannot make the same id reusable. Retrying the same reviewed
plan requires a new approved invocation and a fresh id.

Before every Notion transport attempt, WOM reauthenticates the claim,
revalidates the exact receipt/lifecycle authority, confirms all three registered
capabilities, verifies endpoint and selected scope, and atomically spends one
budget unit. The bearer remains in an owned mutable wrapper inside the worker
and is closed and wiped after the bounded group execution.

## Content-free reconciliation

Three different artifacts carry deliberately different safe projections:

- the HMAC-authenticated claim ledger records capability id/digest,
  `request_sha256`, `plan_sha256`, budgets, final status, and authorized-request
  count;
- the durable recovery receipt records only a
  `wom-kit/credential-capability-reference/v0.1` object with schema, capability id,
  and capability digest;
- the parent result records the
  `wom-credential-capability-use-summary/v0.1` with capability id/digest,
  claim-created state, one-use ceiling, authorized-request count, and fixed
  status.

The parent rejects or projects unknown child capability evidence that does not
match the exact capability it issued. Shared id/digest values link the three
artifacts; request/plan digests stay only in the authenticated claim rather than
being copied into the recovery receipt or parent summary.

This linkage supports crash or IPC-loss review without exposing an archive
authentication MAC, credential id, workspace fingerprint, backend target,
receipt path, page id, anchor UUID, provider URL/body, bearer value, or secret-
derived metadata. Claim-finalization ambiguity adds
`credential_capability_audit_finalize_failed` and cannot be projected as
success.

## Verified replay stays offline

When the plan proves all selected objects already exist with the expected
content hashes, `provider_pending_count` is zero. WOM creates no capability
claim, reads no credential, and calls no provider. The worker uses explicit
never-provider and never-broker sentinels so any later drift blocks instead of
silently escalating the invocation to live access.

## Upgrade

Install only after the exact v0.3.320 GitHub Release exists and lists the
verified `wom_kit-0.3.320-py3-none-any.whl`. A source checkout or versioned URL
alone is not publication evidence. Start a new process and confirm:

```powershell
archive --version
```

Discard recovery plan digests created by an older runtime and create a fresh
bounded dry-run before approval. An already-registered credential does not need
to be entered again when its authenticated receipt, lifecycle, native secret
fingerprint, provider, workspace, and reviewed scope remain valid. Do not put a
PAT in chat, argv, environment, ordinary stdin, or a file, and do not use the
synthetic popup helper for registration.

This upgrade does not itself open the popup, read or change a credential store,
call Notion, write recovery evidence, rewrite canonical zets, or operate on an
archive.
