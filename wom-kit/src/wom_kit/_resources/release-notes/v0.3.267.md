# WOM-kit v0.3.267

Release date: 2026-07-28

## Approval-Gated Abstract Recovery Executor

This release completes the next rung of the v0.3.265 transaction-journal and
v0.3.266 recovery-plan track. One retained non-forensic abstract transaction can
now be previewed and recovered through:

```text
archive zet-abstract-backfill-recover <archive-root> \
  --operation <apply|revert> \
  --basis-sha256 <case.basis_sha256> \
  --expected-plan-digest <plan.plan_digest> \
  --expected-action <case.recommended_action> \
  --dry-run --format json
```

Alias:

```text
archive abstract-backfill-recover
```

Approval additionally requires:

```text
--approve
--reviewed-by person:<reviewer>
--affirm-recovery-reviewed
--affirm-archive-quiescent
```

Exactly one of `--dry-run` and `--approve` is accepted.

## Exact Authority Binding

The executor never selects a recovery action by itself. It requires and then
freshly revalidates:

- the complete untruncated recovery-plan digest;
- one operation and basis SHA-256;
- the exact fixed action;
- final receipt state;
- expected lock state;
- every current participant before/after hash count;
- a safe reviewer;
- explicit review of the recovery direction;
- explicit confirmation that the old process stopped and the archive is
  quiescent.

`manual_forensic_hold`, a missing or divergent participant, an unsafe lock,
truncated evidence, stale plan/action, or an occupied but unverified final
receipt blocks before mutation.

## Executable Cases

- prepared apply or revert: remove only the matching basis lock and journal;
- interrupted apply: deterministically remove inserted abstracts only from
  participants at their recorded after hashes, verify every exact before hash,
  then clean matching evidence;
- partial revert: deterministically remove the abstract only from participants
  still at their recorded before hashes, verify every after hash, create and
  verify the deterministic text-free revert receipt, then clean evidence;
- fully reverted without receipt: create and verify the receipt without a
  canonical write, then clean evidence;
- verified completed residue: preserve the immutable receipt and clean only the
  matching lock and journal.

## Crash And Retry Semantics

The retained transaction journal is also the recovery progress record. Every
required target is materialized before the first write and each participant is
rechecked immediately before mutation. A successful write is verified against
its exact target hash.

If recovery fails or the process is forcibly terminated:

- already completed safe-direction recovery writes are not reversed;
- the journal and basis lock remain;
- the next plan derives a new digest from current hashes;
- another run requires fresh review and approval.

A new OS advisory guard serializes recovery executor processes and releases
automatically when a process exits. A missing matching basis lock is atomically
reacquired before canonical or receipt mutation.

The guard does not lock external editors, older WOM versions, ordinary
different-basis apply/revert writers, or other multi-zet writers. The explicit
archive-quiescence affirmation remains mandatory. This release does not claim
cross-basis ordinary-writer serialization or Windows sudden-power-loss
durability.

## Receipt Compatibility

Ordinary revert handles an in-process failure by restoring the applied state.
Recovery instead preserves successful safe-direction progress. A
recovery-produced revert receipt therefore records:

```text
mutation_contract.rollback_on_runtime_failure: false
```

The existing v0.1 revert-receipt schema now accepts a boolean for that field
instead of enforcing `true`. Existing `true` receipts remain valid.
v0.3.266 and older reject a new recovery-produced receipt, so v0.3.267 or newer
is required for later receipt audit after this executor creates one. This is a
one-way reader compatibility gate.

## Privacy

The executor may read private journal ids/paths/reviewer metadata, receipt
metadata, and canonical bytes for exact hash validation. Public output never
echoes journal or receipt paths, zet ids or paths, title/body/abstract text,
reviewer identity, proposal filename, journal digest, lock content, or absolute
local paths.

No model, provider, network, database, environment credential, or secret store
is used.
