# WOM-kit v0.4.16 — Durable Update Results And Truthful Safety Evidence

v0.4.16 preserves an authenticated project-update result across the boundary
that v0.4.15 intentionally left unsupported: transaction cleanup, owned-resource
close, Git-runner close, durable output publication, and terminal display can
now fail independently without erasing the already-proven update outcome.

This release also recognizes the canonical `python -m wom_kit.archive_cli`
launcher during project-runtime receipt binding, permits one narrow create-only
feedback path when runtime alignment itself is blocking ordinary writers,
reduces product-language false positives in the private secret gate while
keeping concrete credential shapes fail-closed, and reports caller-input safety
reads separately from source first-read provenance.

Approved project-update mutation, same-version repair, and mutation-bearing
resume remain Windows-only. POSIX supports preview and read-only inspection;
those mutation paths fail closed without writing.

## Authenticated terminal result handoff

Before update cleanup begins, WOM binds the exact succeeded approval claim,
completed transaction checkpoint, verified postimage, and delivery capability
into a private durable terminal handoff. The public result contains no private
path or approval, transaction, or archive identifier.

The `terminal_finalization` object reports separate booleans for:

- `update_result_verified_in_current_invocation` or
  `update_result_reauthenticated_from_durable_handoff`;
- `claim_succeeded_verified`, `transaction_completed_checkpoint_verified`, and
  `lock_absence_verified`;
- `transaction_cleanup_completed`, `service_resource_close_verified`, and
  `git_runner_close_verified`;
- `durable_terminal_handoff_ready`,
  `durable_terminal_handoff_replayed`, and
  `durable_result_delivery_acknowledged`; and
- `attention_required`, while `domain_writer_reentry_allowed`,
  `automatic_retry_allowed`, and `cleanup_proof_used_as_success_authority`
  remain false.

When cleanup or either close is not verified, the authenticated domain result is
still preserved and `post_update_attention_required` is true. WOM does not turn
a cleanup proof into success authority, rerun the approved writer, or expose a
private exception string. A later `--resume` reauthenticates the exact terminal
handoff and verified postimage before it returns the result; it does not replay
the domain update.

Approved and resumed updates always have a durable delivery target. If
`--output` is omitted before a result is bound, WOM chooses a private
project-scoped path under `.zettel-kasten/diagnostics/`. An explicit write-mode
output must use that same project-scoped prefix. Once the complete output,
immutable terminal journal record, handoff, and one-use delivery proof are
bound, recovery reuses those exact bytes and rejects a replacement `--output`.

The private handoff moves through three same-directory namespace states:
`active` -> `display-pending` -> hash-named `consumed`. The operation journal is
not extended with a later delivery or display event. If a process stops before
display completes, identifier-free `--resume` verifies the same bound output
and may display the identical result again. This is intentionally at-least-once
display: a crash after printing but before the final rename can produce one
duplicate, never a newly generated result. A consumed capsule is durable
history, not a replay candidate.

`durable_result_delivery_acknowledged: true` means that WOM verified the
authenticated durable output handoff. It does not prove that a person or model
actually saw, read, or understood terminal stdout. Neither a display retry nor
the final namespace rename reruns the approved domain writer.

v0.4.15 cleanup residue is classified without guessing. One complete cleanup
tombstone is recoverable only after its exact plan, complete file and directory
set, terminal checkpoint, succeeded claim, current postimage, and legacy
cleanup authority all validate. A canonical cleanup-proof-shaped file by
itself returns `no_resumable_project_update`, with
`past_update_success_attributed: false` and
`current_project_state_independently_verified: false`; it is inert history and
a new update requires a fresh preview and approval. Partial, malformed, mixed,
changing, ambiguous, or unsafe cleanup state remains
`terminal_cleanup_outcome_unknown` and fails closed. A proof alone never mints
a handoff, attributes past success, or authorizes cleanup or retry.

The ordinary recovery command remains identifier-free:

```powershell
& <exact-v0.4.16-bootstrap> project-version-update <project-or-archive-root> `
  --resume `
  --affirm-external-writers-quiescent `
  --progress `
  --format json
```

After a result is delivered, start a new process through the project launcher
and verify project alignment before an ordinary approved write:

```powershell
.\.zettel-kasten\bin\archive.cmd version <project-or-archive-root> --format json
```

## Canonical `python -m` runtime binding

The supported project launcher executes `python -m wom_kit.archive_cli`, where
Python registers the executing module as `__main__`. v0.4.16 accepts that alias
only when the import specification names the exact WOM entrypoint and its file
matches the specification origin. It then applies the existing expected-path,
real-component, installed inventory, size, and digest checks.

Runtime evidence now reports `core_module_bindings` for `archive_cli`,
`project_runtime`, and `package_origin`. Each entry says whether the module was
observed, matched the expected identity, had an inventory entry, and was bound
to receipt bytes, plus a bounded reason code. These diagnostics echo no
absolute paths and no hashes.

## Same-version project runtime repair

When the project pin and requested release already match but the project-local
runtime is missing expected bytes, has a damaged receipt, or is otherwise
invalid, the ordinary `project-version-update` command now treats that state as
a repair instead of requiring a separate manual rebind. Dry-run reports
`runtime_repair_required: true` and explains that an approved update will use a
private replacement with an exact private recovery preimage. A healthy same-version
runtime still returns `no_change`.

After the existing exact human approval, WOM builds and fully verifies a fresh
runtime beside the current one, preserves the exact old runtime only inside the
sealed update transaction, and promotes the replacement with atomic renames.
If the process stops between either rename, the public identifier-free
`project-version-update --resume` path recognizes the exact on-disk state and
continues without replaying an already completed writer. A later component
failure preserves the owned lock, sealed transaction, verified new runtime, and
exact private recovery preimage for authenticated forward resume; it does not
silently enter the legacy automatic rollback path. After the new process,
receipt, authenticated result handoff, and terminal checkpoint are all verified,
transaction cleanup removes the exact private recovery preimage. Cleanup uncertainty is
reported as durable finalization attention without erasing the proven update
result.

## Create-only feedback during runtime mismatch

If either project-update recovery or project-runtime alignment blocks ordinary
writes, the exact-approved `operator-feedback-compose --intent create` path may
still append one new feedback body and its body receipt. Its result identifies
the content-free trigger reason and distinguishes
`project_update_recovery_still_required` from
`project_runtime_alignment_required`.

This emergency lane remains append-only. It does not revise or supersede an
existing body, register lifecycle metadata, mark feedback delivered or
resolved, change a runtime or pin, release a lock, or authorize any other
writer. The bounded coordination artifact is not a domain record and contains
no feedback body.

## Product language and strict secret shapes

The source-fidelity safety gate no longer treats ordinary product vocabulary,
definitions, documented placeholders, or non-sensitive preference cookies as
credential values merely because they contain words such as “token”,
“password”, “secret”, or “credential”. Examples such as `token budget`,
`GCP Secret Manager`, `Password: must be stored in a password manager.`,
`Authorization: Bearer <token>`, `password: REDACTED`, and `Cookie: theme=dark`
remain eligible for the normal exact source-fidelity workflow.

Concrete credential assignments, private-key markers, provider token shapes,
JWTs, authorization values, session-bearing cookies, and suspicious structured
header collections still fail closed with `credential_secret_present`. The
rejected value is never echoed.

## Truthful caller-input safety reads

Draft results now separate two different questions:

- `input_privacy_check.scope: pre_write_caller_input_safety` truthfully reports
  `caller_supplied_input_read_for_safety: true` and
  `body_read_for_safety: true`, while `input_values_echoed` remains false; and
- `first_read_check.body_read_for_check` continues to describe only the later
  source first-read provenance check, so it can truthfully remain false when the
  body was read earlier solely for pre-write secret safety.

This removes an ambiguous “body not read” impression without exposing the body
or weakening the private-input gate.

## Updater bootstrap contract

After the matching GitHub Release exists and lists the exact wheel, create a new
external CPython 3.12 environment and invoke its real `python.exe -m pip`:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0416-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.16/wom_kit-0.4.16-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.16` from a new process. The versioned URL alone is
not proof that a release or asset exists. Publishing or installing v0.4.16 does
not inspect or modify a client archive, project pin, runtime, or remote service.
The client chooses whether and when to run a separately reviewed project update.
