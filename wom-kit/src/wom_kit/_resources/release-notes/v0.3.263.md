# v0.3.263 - Reviewed Title Remap Plan

v0.3.262 answered how many canonical zets carry an imported identifier where a
name should be. It deliberately did not fix any of them. v0.3.263 adds the next
rung: an operator supplies the names that already exist in their source export,
and this checks every one of them against the archive without writing anything.

## What Changed

- New read-only CLI `archive zet-title-remap-plan <archive-root> --proposal
  <private.jsonl> --dry-run`, with alias `title-remap-plan`. It reads the
  proposal and the canonical zets that proposal names, and writes nothing.
- Each row is bound to exact current bytes. A row carries `zettel_id`,
  `expected_file_sha256`, the replacement `title`, and a `basis`. If the zet
  changed after the operator built the proposal, that row blocks rather than
  silently planning against stale content.
- The command proposes no text of its own. Every replacement comes from the
  proposal file, and `basis` records where the operator got it —
  `source_export_property` or `human_written`.

## The Rule That Keeps This Narrow

A row is accepted only when the *current* title is **identifier-shaped**. A title
a human chose is refused with `current_title_not_identifier_shaped`.

Shape is the requirement, and stating it as "one the census would flag" was not
the same thing — a pre-release review found and reproduced the gap. The census's
`title_matches_external_id` signal fires whenever the title equals a registered
page-reference facet value, with no shape test at all. So a zet titled
`Weekly Planning Database` whose `external_id` facet repeats that same string
opened the gate, and worse, was reported `provenance_bound: true`, which
*suppressed* the warning telling the reviewer to look harder. The gate now
requires the shape signal itself.

This matters more than it looks. The same machinery that repairs 2,700 imported
identifiers would, without that check, rewrite any title in the archive from a
file. This release is a repair tool for a specific import failure, not a bulk
title editor, and the code says so rather than the documentation.

Two more refusals in the same spirit:

- A replacement the census would flag is refused — checked with the full census
  predicate against the target's own facets, not just for identifier shape.
  Swapping one identifier for another leaves the archive exactly as unbrowsable
  as before; so does a replacement that happens to equal the record's own page
  reference, which the shape test alone missed.
- A replacement that fails the promotion checklist's specificity rule is
  refused, so a remap cannot introduce a title that minting would not accept.

## Provenance Is Reported Separately

`summary.provenance_bound_ready_count` counts the ready rows whose old title was
provably that record's own imported identifier, as opposed to merely
identifier-shaped. When those two numbers differ, the report warns.

The distinction decides how much the reviewer has to trust. For a
provenance-bound row, the zet itself proves what was wrong with its title. For a
shape-only row, the claim rests entirely on the operator's source export, and a
human should look harder before approving.

## Privacy Boundary

Neither the old title nor the replacement appears in the output, and neither does
a digest or a length of one.

The digest point is the substantive one, and it is a correction. An earlier draft
of this command published a per-row `title_sha256` beside the exact
`title_char_count`, mirroring how the abstract backfill family handles reviewed
abstract text. That mirror does not hold: an abstract is paragraph-scale free
text, whereas this command accepts a title as short as four display units, and a
pre-release review recovered a two-syllable Korean replacement title from the
published digest and length alone in seconds. Salting would not have helped —
every candidate salt in the envelope is printed in the same report. Both fields
are gone, and `plan_digest` no longer carries a per-title digest either; the
proposal file's own `sha256` already binds every replacement collectively, and a
future approved write revalidates that hash.

`privacy_guards.replacement_title_values_echoed` is derived from what the
assembled payload actually contains rather than asserted as a literal, so the
flag cannot disagree with the report.

The proposal is an untrusted private file. It is read under a 64 MiB ceiling with
a 1 MiB per-row ceiling, must live under `.wom-scratch/title-remap/`, must be a
real file rather than a symlink, and no part of its content is reflected back
into the report. A row that cannot be parsed — including one nested deeply enough
to exhaust the JSON parser's recursion limit — degrades to a blocker code rather
than reaching the interpreter's default traceback, which would carry local
absolute paths.

What this command *does* read is wider than the census: it reads each named
canonical zet in full, body included, to hash it. `privacy_guards` says so
(`canonical_file_bytes_read`, `untrusted_proposal_text_read`) rather than leaving
a reader to infer the frontmatter-only boundary from v0.3.262.

A non-canonical target — including a redacted zet — is blocked without being
judged, so no title-derived fact about it reaches the report.

## Compatibility And Migration

- No archive, zettel, index, receipt, or schema migration is required.
- No existing command changes behavior, and no canonical zet is modified by this
  release under any flag.
- `--dry-run` is required and the command exits 1 without it. Unlike the
  readiness commands, a blocked row *is* a non-zero exit here: this is a plan
  that either fully validates or does not.

## What This Release Deliberately Does Not Do

It does not write. `approval_contract.approved_write_implemented` is `false`.

The approved write and its receipts are separate releases, staged the way the
abstract backfill family was. **The revert path is not merely later — it is an
unsolved design conflict, and calling it a scheduling matter would be
dishonest.** Abstract backfill can revert without storing any text because its
change is an insertion: delete the inserted line and the original hash returns. A
title change is a replacement, so reverting requires the previous title value to
exist somewhere — and this family's established privacy property is that receipts
never contain text. Those two cannot both hold as stated. That conflict is
recorded in the decision log and must be settled before the write rung ships, not
discovered during it.

It does not read the source export, call Notion, or infer a replacement title
from anything. If a name does not already exist somewhere a human can point at,
this release has nothing to offer for that zet — which is the correct answer
rather than a generated one.

It also does not fix the importer. The condition arose from a missing fallback
when a source record's title property is itself an identifier; adding that
fallback prevents recurrence and is tracked separately from repairing what
already landed.

## Provenance And Verification

The pilot archive that reported the condition asked whether the remap should be
done by this project or by a local script on their side. This release is the
answer: a local script rewrites canonical titles with no preview, no binding to
exact bytes, no receipt, and no revert, which costs the archive its ability to
say why a title reads the way it does.

Local verification covers the bound-and-ready path with provenance counted, the
refusal to touch a human-chosen title (including one whose facets repeat it,
which is the case that defeated an earlier gate), stale-bytes refusal,
identifier-shaped replacement refusal, refusal of a replacement the census would
re-flag, refusal to judge a redacted target, a hostile proposal line that would
otherwise escape to a traceback, and the no-echo guarantee over the old
identifier, the new title, and any digest or length of it — alongside the full
WOM-kit suite, the four hygiene checkers, and packaged resource synchronization.

A pre-release adversarial review across privacy, detection, and scope lenses
returned two NO-GO verdicts against the first implementation of this release. It
found the gate accepting human-chosen titles, the recoverable title digest, an
exit contract the command did not implement, a documented proposal row the code
rejected outright, redacted targets being judged, and tests whose privacy
assertions read hard-coded literals and therefore could not fail. Every one is
fixed here.
