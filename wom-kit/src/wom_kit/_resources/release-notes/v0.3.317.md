# WOM-kit v0.3.317

Visible credential enrollment and evidence-complete staged cleanup.

Status: v0.3.317 implementation and release scope. The source implementation
and local tests may be complete in this worktree, but this note does not prove
merge, external CI, exact tag, GitHub Release, packaged wheel publication,
fresh installation, live credential enrollment, beta-client success, or human
acceptance.

## Why this release exists

Two beta-use paths did not match the real human workflow closely enough.

First, credential enrollment needs one clearly visible black Windows window in
which the human types or deliberately pastes a PAT without sending it through
chat, command arguments, ordinary stdin, environment variables, files, stdout,
stderr, or parent-process IPC. WOM and the helper AI do not call a clipboard
API; a human paste into the isolated masked console is console input only. The
same saved credential must then be reused instead of
being requested for every later task.

Second, `staged-cleanup-check` must not say that a folder is safe to remove just
because a staged path was deferred or because one manifest row happens to
exist. A safe result needs a complete, still-current preservation chain for
every staged byte sequence.

## Separate visible credential console

- `credential-adopt` is for first enrollment or an explicitly reviewed
  `--replace-existing` operation. Before a matching authenticated registration is reused
  without another input window, WOM authenticates its receipt, reads only the
  exact saved Windows entry inside the worker, verifies its secret fingerprint,
  and rechecks access to the currently reviewed Notion anchor. Missing,
  unreadable, or fingerprint-mismatched saved entries fail closed and require
  a fresh, separately reviewed replacement plan. A current-anchor/provider
  check failure keeps the saved entry and asks the operator to review the page,
  sharing, and connection before retrying without a prompt. Account/workspace
  labels are display copy only; changing them does not create a second
  credential or open another prompt.
- The helper AI supplies two reviewed, public-safe sentences: `--task-summary`
  describes the actual current task, and `--connection-reason` explains why
  that task needs the Notion connection. They are part of the approval digest.
- WOM supplies the fixed, non-overridable security, masking, cancellation,
  persistence, and reuse wording. The helper AI cannot replace that notice.
- Approval starts one separate visible Unicode Windows console. Korean text is
  written with Windows Unicode APIs, input echo is disabled, and empty Enter or
  Ctrl+C cancels safely. The console closes before the Credential Manager write
  begins.
- Raw secret bytes remain inside the spawned worker. A successful transaction
  writes one exact Generic Credential, verifies the provider identity and the
  currently reviewed page, and commits an authenticated non-secret v0.2
  receipt with an explicit workspace-identity basis. Internal integrations use
  Notion's returned `bot.workspace_id`. A person PAT does not expose that field,
  so WOM uses a token-scoped witness derived from the archive-keyed fingerprint
  of the exact saved PAT and also rechecks `/v1/users/me` plus current-page
  access. The same saved PAT can therefore be reused for another reviewed page
  without another prompt. Different PATs are deliberately not collapsed into
  one scope, even when a human knows they belong to the same workspace.

Start with a new dry-run. Do not reuse a request digest made before v0.3.317,
because the public task context and replacement intent are now part of the
request:

```powershell
archive credential-adopt <archive-root> --account-label <safe-label> --workspace-label <safe-label> --task-summary "<public-safe current task>" --connection-reason "<public-safe reason>" --reviewed-anchor-page-id <uuid> --interactive --dry-run --format json
archive credential-adopt <archive-root> --account-label <same-safe-label> --workspace-label <same-safe-label> --task-summary "<same public-safe current task>" --connection-reason "<same public-safe reason>" --reviewed-anchor-page-id <same-uuid> --interactive --expected-request-sha256 <request-sha256> --approve --format json
```

Use `--replace-existing` in both the dry-run and approval only when a human has
separately reviewed credential rotation or repair. Do not use it for ordinary
reuse.

## Evidence-complete staged cleanup

`staged-cleanup-check` remains a report-only command. It never deletes or moves
staged data.

- Ordinary objet preservation requires the exact staged bytes in the canonical
  object store, one strict canonical manifest row, and one valid linked capture
  receipt item whose official envelope, action, exact boolean fields, and byte
  size agree. An aborted, unreviewed, or malformed envelope cannot authorize
  cleanup; a legitimate partial batch can still prove its durable item.
- Exact BOM-free paired text may use the derived-text route only when raw and
  stored SHA-256 agree and the strict derived manifest, independently rehashed
  store bytes, and direct terminal derived-text receipt all agree. An outer
  batch receipt alone is not enough.
- BOM or UTF-16 transcoding preserves a representation, not the original raw
  bytes. Those staged bytes still need ordinary objet preservation.
- Before returning a safe verdict, the verifier rehashes every staged source,
  store, manifest, and receipt authority it used. A same-size change with a
  restored modification time therefore invalidates the result.
- A legacy `--deferred` entry means "keep staged for later." It always makes
  `safe_to_cleanup` false and never authorizes deletion or discard.
- Optional `--output` writes one new result under
  `.wom-scratch/diagnostics/` plus its operation journal. Terminal and
  `operation-control` projections expose only fixed states, reasons, counts,
  and opaque entry references—not paths, names, object ids, hashes, receipt
  names, bodies, or raw messages.

Example:

```powershell
archive staged-cleanup-check <archive-root> --staged <archive-relative-staged-folder> --dry-run --format json --output .wom-scratch/diagnostics/staged-cleanup-v03317.json
```

Exit `0` means the complete current inspection found every entry safe. Exit `1`
means cleanup is not authorized, even when the inspection itself completed
normally. Keep the staged folder and follow the fixed reason codes; do not edit
manifests or receipts by hand to make the check pass.

## Upgrade and compatibility

No canonical-zet rewrite, object-store rewrite, provider write, credential
replacement, or credential-store deletion is automatic in v0.3.317. Existing
staging data remains untouched.

Authenticated credential receipts written by v0.3.311-v0.3.316 are legacy
v0.1 records whose workspace fingerprint was based on the then-reviewed page.
WOM never rewrites those receipts. When there is exactly one compatible
registration, v0.3.317 authenticates the legacy receipt, rereads only its exact
saved credential inside the worker, verifies the secret fingerprint, and
rechecks the current provider identity and reviewed page. It may then append
one authenticated local workspace-scope evolution and, when the old lifecycle
contains one compatible credential, move that lifecycle authority to the new
scope. This compatibility step opens no input console and performs no
Credential Manager write or deletion. A missing lifecycle still needs a human
default decision; duplicate or complex lifecycle state stops for review before
the evolution is first published. An interrupted simple evolution is
idempotent: the old broker binding stays unusable until a retry completes the
authenticated lifecycle transition.

For a person PAT, `notion_pat_token_scope_v1` is a credential-bound witness,
not a provider-returned workspace ID. It supports the same saved PAT across
different reviewed pages. Rotating to another PAT, or reconciling two PATs that
the human knows belong to one workspace, remains a separate reviewed lifecycle
operation rather than an automatic merge.

Install only after the exact v0.3.317 GitHub Release exists and lists the
verified `wom_kit-0.3.317-py3-none-any.whl`. Updating repository files alone
does not replace an older isolated tool installation. Start a new process and
verify `archive --version` before using these corrected paths.
