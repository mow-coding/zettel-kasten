# WOM-kit v0.4.15 — Authenticated Update Recovery And Safe Incident Reporting

v0.4.15 closes the blocked-draft recovery trap while a live update lock or the
original exact unlock-tail transaction remains. The archive-wide write guard
stays strict, and the already-approved update can be resumed without asking a
person to reconstruct internal identifiers within that boundary.

The recovery guarantee is bounded to a live `version-update.lock` or the exact
lockless unlock tail while the original transaction directory still exists.
Its first unsupported boundary is after `completed`, once the original
transaction directory has been successfully renamed to a terminal cleanup
tombstone. A tombstone or cleanup proof is not authenticated outcome or cleanup
authority: v0.4.15 reports `terminal_cleanup_outcome_unknown` with a nonzero
exit and does not infer success, failure, or cancellation, automatically retry,
or delete that evidence. A full authenticated terminal handoff and terminal
cleanup outcome reconstruction remain a v0.4.16 follow-up.

## Why ordinary draft writes were blocked

A project update changes several parts as one transaction: the source mirror,
the versioned runtime, the project launcher, the active version pin, and its
receipt. A hard interruption can leave some parts at the target version while
others still point to the previous version. WOM retains the update lock and
blocks ordinary writers, including approved zet draft creation, because writing
with that mixed runtime could make later evidence ambiguous.

The block was the safe behavior. The defect was that recovery required an
internal locator that ordinary operators were never meant to inspect.

## One locator-free recovery command

`project-version-update --resume` first classifies the exact durable transaction.
Before native approval, it verifies the unchanged preimages and cancels only the
incomplete preparation scaffold, leaving the source, active runtime, launcher,
pin, and update receipt unchanged; the person then starts a fresh approval.
After native approval, WOM derives the prepared target, transaction, reviewer,
and approval context from the exact lock or the single authenticated unlock-tail
transaction and sealed plan, then searches only the bound local approval store.
It accepts exactly one authenticated, checkpoint-valid `started` or `succeeded`
claim for that unchanged context.

- no second native approval window is opened;
- the person supplies no target, transaction, reviewer, approval, or file
  identifier;
- a zero-claim transaction cancels its scaffold without a domain write only
  when durable state proves it is untouched preapproval, then requires a fresh
  approval; zero claims for an approved or indeterminate transaction, multiple
  candidates, changed context, forged evidence, journal drift, or checkpoint
  drift fail closed;
- a `started` claim resumes only its idempotent remaining checkpoints;
- a `succeeded` claim performs only the separately verified finalization; and
- the update lock is released only after source, runtime, launcher, pin, and
  receipt converge and pass independent verification.

The normal recovery command is deliberately small:

```powershell
& <exact-v0.4.15-bootstrap> project-version-update <project-or-archive-root> `
  --resume `
  --affirm-external-writers-quiescent `
  --progress `
  --format json
```

Ordinary recovery requires no caller-supplied `--target`, `--transaction-ref`,
`--approval-id`, or `--reviewed-by`; WOM derives every binding from authenticated
durable state.

After successful recovery, start a new process through the project launcher and
verify project alignment before an ordinary approved write:

```powershell
.\.zettel-kasten\bin\archive.cmd version <project-or-archive-root> --format json
```

If the result says `preapproval_scaffold_cancelled`, no update was applied and
`fresh_approval_required` is true. Run a new preview and request one fresh exact
approval. If an already-approved update was resumed, verify the aligned runtime
as shown above.

For a preapproval cancellation result, `files_written_scope:
project_domain_only` makes the empty `files_written` list explicitly about
project-domain files. It does not hide the recovery transaction's control
effects: a content-free `effect_summary` reports durable control evidence,
cancellation checkpoints or reservation-abort evidence, candidate cleanup or
verified absence, and lock release without exposing paths or identifiers. The
lock fields separately say whether this invocation verified a live lock or
continued from an exact prior binding with verified lock absence.

## Create-only emergency feedback preservation

An interrupted update must not also silence the incident report needed to
explain the blockage. While update recovery is required, v0.4.15 permits only
the exact approved `operator-feedback-compose --intent create` path to append a
new feedback body and its body receipt.

Those are the only domain writes. The crash-safe writer also retains one
bounded cross-process mutex artifact in the feedback-receipt control tree; it
contains no feedback body or lifecycle metadata and is not another domain
record.

This narrow path does not revise or supersede an existing body, register or
change feedback lifecycle metadata, mark anything resolved or delivered, or
unlock another writer. It does not change the update lock bytes, source mirror,
runtime, launcher, version pin, or update receipt. All of those other writes
remain blocked until recovery finishes.

## Updater bootstrap contract

The supported Windows updater bootstrap is a dedicated CPython 3.12 virtual
environment outside the project and archive. Invoke its exact real
`python.exe -m pip` so the installed PEP 610 metadata retains the wheel's
SHA-256. A tool installation whose metadata omits that archive hash is not
accepted as project-update supply evidence; current `uv tool` installation
metadata therefore must not be used as an updater-capable bootstrap.

After the matching GitHub Release exists and lists the exact wheel:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0415-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.15/wom_kit-0.4.15-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.15` from a new process. The versioned URL alone is
not proof that a release or asset exists. Installing the wheel changes no
archive data and does not itself resume an interrupted update.
