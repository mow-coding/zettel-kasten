# v0.3.260 - Cross-Platform Release Verification

v0.3.260 gives the project its first continuous-integration workflow and fixes
the two cross-platform defects that workflow immediately found. Release
verification is no longer evidence that one Windows machine agreed with itself.

## What Changed

- A GitHub Actions workflow runs the existing release readiness gate, packaged
  resource synchronization, and the complete WOM-kit suite on `ubuntu-latest`
  (3.12 and the supported 3.10 floor) and `windows-latest` (3.12). It also
  asserts that the suite left the working tree clean.
- The packaged resource manifest is reproducible across platforms.
  `sync_package_resources.py` sorted `Path` objects, and pathlib compares
  Windows paths case-insensitively and POSIX paths case-sensitively, so the
  emitted order depended on the generating machine.
- Path-traversal detection for `--prompt-boundary-report` normalizes separators
  before checking, so a `..\report.json` argument is refused identically on
  every platform instead of becoming an ordinary POSIX filename.
- Regression coverage pins the manifest's platform-independent ordering, the
  sorting mechanism itself, and one path assertion that had hardcoded a
  backslash separator.

## Why It Matters

The manifest binds 91 packaged resources to exact byte counts and SHA-256
values, and the four hygiene checkers are the project's pre-release gate. Both
ran only on the maintainer's Windows machine. On Linux — the platform of the
project's own documented Docker runtime — `sync_package_resources.py --check`
failed with `resource manifest does not match source resources`, so the
release gate could not complete there at all.

The workflow is deliberately **not** a required status check. This is Stage 3
of the staged path already written down in
[Main Branch Protection Readiness](https://github.com/mow-coding/zettel-kasten/blob/main/wom-kit/docs/main-branch-protection-readiness.md):
introduce and observe CI first, then decide separately about required checks
and branch protection.

## Compatibility And Migration

- No archive, zettel, index, receipt, or schema migration is required.
- The regenerated manifest contains the same 91 entries with identical `bytes`
  and `sha256` values; only their order changed.
- Command names, arguments, output shapes, and exit codes are unchanged.
- A `..\report.json` style argument to `--prompt-boundary-report` now returns
  the fixed traversal message on Linux and macOS instead of a raw file error.
  Windows behavior is unchanged.

## Privacy And Safety Boundary

- The workflow uses `permissions: contents: read`, declares no secrets, and
  publishes no artifact.
- No product CLI, MCP, archive, provider, or network behavior changes. The
  built wheel's contents are unaffected apart from the version and release
  note.
- The workflow file itself is scanned by the public privacy and link gates it
  runs, and passes them.

## Provenance And Verification

CI was added because an independent audit could not verify any release claim:
release verification was entirely local and self-attested, with no artifact
binding test execution to a release commit.

Its first run justified itself. Four read-only investigators had reviewed the
runtime for platform branches and returned a GO verdict; none of them found the
manifest ordering defect, because it lived in the release tooling rather than
in the product. The first ubuntu run failed the gate immediately. The following
run then failed both ubuntu legs on the two hardcoded-separator defects while
the Windows leg stayed green — the exact class of drift the maintainer's
machine cannot observe.

Local verification: the complete WOM-kit suite passed 1,532 tests with 9 skips
under `python -m unittest discover -s wom-kit/tests`, the readiness gate passed
all four checkers, and packaged resource synchronization reported 91 files.
Publication closure additionally requires the clean-wheel install and a fresh
installation from the published GitHub asset.
