## v0.3.316 Letter 129 Complete Collision-Set Recovery

- The CLI-only `project-version-update-collision --action inspect-all` action
  inspects every opaque collision from one unchanged materialization plan. It
  reports evaluated content-free kind and remediation truth in one result; no
  per-entry loop or local path disclosure is required.
- A bytecode-repair route appears only when the exact complete collision set
  consists entirely of supported ignored Python bytecode files and plain cache
  directories. Exact private path-set equality is verified internally; counts
  alone do not authorize repair. Unsupported and mixed sets return
  `inspected_remediation_unavailable`.
- `project-bytecode-repair-plan` and the reviewed approval bind the exact
  target, materialization-plan digest, collision set, file identity and bounds,
  and a separate repair-plan digest. Repair shares the updater lock, requires
  external-writer quiescence, and retains honest evidence for partial or
  uncertain outcomes.
- Repair removes only reproducible cache artifacts. It does not fetch, change
  `HEAD` or a pin, retry an updater, or grant update approval. A fresh updater
  preview and separate update approval are mandatory afterward.
- Source tests do not prove merge, CI, tag, Release, wheel, fresh install,
  real-project execution, beta-client success, or human acceptance. See
  `docs/project-version-update.md`, `docs/operation-control.md`, and
  `docs/releases/v0.3.316.md`.

## v0.3.314 Letter 126 Long Operations And Generated-Index Recovery

- Project target-tree materialization uses one bounded `git cat-file --batch`
  stream per tree instead of one child per file. The controlled four-tree
  reproduction used eight Git children rather than 11,184 and completed its
  four batch loads in 2.538 seconds. Strict object id/type/size/hash/framing and
  byte caps remain enforced; this local benchmark is not a universal latency
  guarantee.
- Generated SQLite rebuild and incremental writers require rollback `DELETE`
  mode. Public and private inspection validates the header and absence of
  `-wal`, `-shm`, and `-journal` sidecars before opening SQLite. A blocked
  legacy/invalid state performs no public row comparison and emits no invented
  missing-row claim.
- One ordinary explicit `archive index` rebuild converts a legacy generated
  cache and rebuilds the private projection. Canonical zets, durable private
  metadata authority, and the database schema are not migrated. Unmanaged
  external SQLite writers must still be quiescent because preflight is not an
  operating-system-wide lock.
- `project-version-update`, `index`, and `index-health` create a content-free
  operation journal only when the caller explicitly uses a fresh `--output`.
  The early opaque reference supports later CLI-only `status`, a 1-60 second
  bounded `wait`, or read-only `recovery-plan` with exact-root and saved-result
  binding verification.
- `deadline_reached` is not cancellation or command failure. Cancel always
  returns nonzero `operation_cancel_not_supported` and writes nothing; resume,
  MCP control, daemon, queue, background launch, force kill, lock deletion, and
  automatic rollback are not implemented. The journal hash chain is not a MAC,
  signature, or authority receipt.
- Source tests and controlled benchmarks do not prove merge, CI, tag, Release,
