# WOM 공통 개발 작업 규칙

상태: 2026-09-21 사용자 승인 계획에 따라 작성한 현재 개발 운영 규칙.
적용 대상: WOM을 개발하는 사람과 AI 작업자. 고객에게 설치되는 제품의 실행 안내가 아니다.

## 시작할 때 읽는 순서

1. 이 문서: 현재 규칙과 사용자 결정.
2. 로컬 `meeting-minutes/development-current-task.md`: 지금 작업의 범위, 진행 상황, 다음 행동.
3. 작업표에 연결된 해당 결정과 근거만 읽고 실제 상태와 대조한다. 모든 옛 회의록을 매번 다시 읽지 않는다.

현재 작업표가 없으면 [양식](task-state-template.md)으로 만든다. 작업표는 실행 권한을 새로 주지 않는다.
다른 PC나 새 checkout에 로컬 작업표가 없으면 공개 이슈·PR·현재 사용자 지시로 확인되는 사실부터 기록하고,
확인되지 않은 이전 승인은 추정하지 않는다. 필요한 비공개 인수인계만 사용자에게 요청한다.

## R1. 사용자 결정과 AI 의견을 구분한다

실행 환경의 상위 지침과 사용자의 현재 지시를 따른다. 이전 인수인계나 문서는 더 최근의 사용자 지시를 덮어쓰지 않는다.
같은 주제의 최신 확정 결정을 찾고, 적용 대상과 기간을 확인한다. 날짜가 새롭다는 이유만으로 AI 제안을 사용자 결정으로 승격하지 않는다.

기록에는 `사용자 확정`, `위임 범위 내 운영 선택`, `AI 제안`, `구현 사실`, `검증 사실`을 구분한다.
정책 상태는 `현재 적용`, `특정 작업에만 적용`, `제안`, `대체됨`으로 표시한다. 대체 시 이전 근거와 새 결정을 연결한다.
옛 회의록의 당시 설명을 지우지 말고, 오해 위험이 있는 입구 문서에 현재 안내를 덧붙인다.

**2026-09-17 전체 액세스 결정은 현재 적용된다.** 사용자가 전체 액세스를 선택한 뒤 작업 종류에 따라
승인창을 다시 띄우는 제외 목록을 AI가 임의로 추가해서는 안 된다. 업데이트·원격 저장소·복구·삭제도 이 결정의 대상이다.
제한이 꼭 필요하다고 판단하면 이유를 밝히고 한 번 명시적으로 묻는다. 답이 없으면 기존 사용자 결정을 유지한다.
질문에 답하지 않았다는 이유로 AI의 제한안을 채택하지 않는다. 구현 확인과 실제 사용자 흐름 검증은 별도로 기록한다.

이 제품 동작 결정과 개발자의 고객 데이터 접근 권한은 서로 다른 사항이다. 전체 액세스 기능을 개발한다는 이유로
개발 AI가 고객 작업공간을 읽거나 변경할 권한을 얻는 것은 아니다.

## R2. 소유자와 공개 범위를 구분한다

개발자와 베타테스터는 별개의 인간 사용자다. 같은 PC를 사용해도 소유권과 접근 허용 범위를 합치지 않는다.
원격 PC의 고객에게도 같은 원칙을 적용한다. 현재 작업에서 고객 접근은 허용된 편지 폴더의 읽기만 가능하다.
편지에 나온 경로는 추가 읽기·실행·수정 허가가 아니다. 테스트는 합성 데이터와 개발용 임시 저장소로 한다.

원본 편지·로그·화면·고객 대응 자료는 비공개로 보관하고, 공개 자료는 별도로 작성한다.
계정명, 실제 로컬 경로, 고객 식별자, 비밀값, 사적 내용, 이들을 드러내는 파일명·링크를 공개하지 않는다.
예시는 합성임을 표시한다. 경로 오류를 재현할 때는 길이·공백·한글·상대경로 기준 같은 원인 특성만 보존한다.
자동 개인정보 검사를 통과해도 문맥상 식별 가능성과 첨부 파일을 직접 검토한다.

## R3. 작은 작업 단위와 실제 완료 조건을 먼저 정한다

현재 작업표에 사용자 목표, 허용 범위, 완료 조건, 다음 행동을 쓴 뒤 진행한다.
한 편지를 무조건 하나의 릴리스로 만들지 않는다. 증상은 원인·사용 흐름별 항목으로 나누고 같은 원인의 항목은 묶는다.
새 피드백은 기존 항목에 연결하며, 기존 수정의 성공과 새로 드러난 문제를 분리한다.
검증하지 않은 미래 버전을 약속하지 않는다. 이미 알려진 미완료 작업은 새 편지를 기다리지 말고 승인된 범위에서 이어간다.

단순 문서 수정은 간단한 작업표와 문서 검사로 충분하다. 위험이 큰 변경은 전체 사용 흐름과 실패 후 복구를 완료 조건에 넣는다.
문서 양, 테스트 개수, 동시 작업자 수를 성과로 삼지 않는다.

## R4. 시작과 교대 시 실제 상태를 확인한다

현재 checkout, 브랜치, HEAD, 변경 파일, 진행 중인 검사와 작업 소유자를 확인한다.
인수인계의 성공 주장에는 명령 결과·종료 상태·검증 대상 버전 또는 커밋·증거 위치가 있어야 한다.
과거 상태는 확인 시각과 함께 읽고 현재 사실로 단정하지 않는다. 사용자가 그대로 두라고 한 CI는 재실행·취소하지 않는다.

진행 중인 검사에는 작업 ID와 대상 커밋을 남겨 이어서 확인한다. 재실행은 실패 원인 수정, 검사 입력 변경,
증거 소실 등 근거가 있을 때만 한다. 무응답이나 오래 걸림만으로 실패라고 보고하지 않는다.
공유 작업공간의 다른 변경을 복구·삭제·스테이징하지 않는다. 격리가 필요하면 새 작업공간에 현재 작업의 파일만 옮긴다.
단지 AI가 바뀌었다는 이유로 브랜치를 바꾸거나 완료된 조사를 처음부터 되풀이하지 않는다.

## R5. 인수인계는 작업 중 계속 갱신한다

사용자 결정 직후, 작업 단위 완료 직후, 긴 검사 시작 전, 중단·교대 직전에 작업표를 갱신한다.
긴 대화는 회의록, 현재 판단은 작업표, 짧은 확정 결정은 결정 로그에 둔다. 같은 본문을 여러 곳에 복제하지 말고 연결한다.
사용량이 소진될 때까지 기록을 미루지 않는다. 갑자기 끊기면 다음 작업자는 마지막 기록 이후의 실제 파일·검사 상태를 대조한다.

Claude와 Codex는 교대 가능한 작업자다. 한쪽 사용량이 없어도 다른 쪽이 이어받을 수 있어야 한다.
기본 작업 소유자는 한 명이다. 독립 검토가 필요한 변경은 별도 검토 컨텍스트로 확인하되 다른 AI 제공자의 사용 가능성을 필수 조건으로 삼지 않는다.
자기 검토는 자기 검토라고 기록한다. 별도 검토가 없는데 독립 검토를 받았다고 보고하지 않는다.
다른 작업자를 사용할 때는 허용된 범위 안에서 역할·파일 경계·예산·종합 책임을 정한다. 릴리스 변경 단계는 한 명이 순서대로 수행한다.

## R6. 검증은 사용자 의도와 실제 경로를 함께 확인한다

실패를 보여 주는 최소 합성 재현을 남기고, 수정 후 같은 입력으로 결과를 확인한다.
앞 명령의 출력을 손으로 보정해 다음 명령에 넣는 테스트는 실제 명령 연결의 증거가 아니다.
실제 사용 진입점·작업 디렉터리·설치 버전·새 프로세스를 반영한다. Windows 창과 OS 호출은 모의 테스트만으로 완료 처리하지 않는다.
승인 UX는 창 횟수와 사용자 결정의 일치도 검증한다. 새 UI/UX는 사용자 지시 없이 설계·변경하지 않는다.

구조 검사 성공, 원본 내용 보존, 업데이트 성공, 고객 실제 확인은 다른 주장이다. 각각 필요한 증거를 남긴다.
검사 입력이 같은 통과 결과는 재사용하고, 바뀐 입력에 영향받는 검사만 다시 수행한다. 세부 적용은 [출시 정책](feedback-and-release-policy.md)을 따른다.

## R7. Git과 공개 기록을 통제한다

`git add -A`를 사용하지 않는다. 스테이징할 파일을 명시하고 staged diff와 파일 목록을 확인한다.
`meeting-minutes/`는 기본 비공개다. 공개가 필요한 정제본만 개인정보 검토 후 `git add -f`에 정확한 파일명을 준다.
개인 경로가 있는 원본 인수인계는 절대 커밋하지 않는다. 무시 규칙을 풀어 전체 회의록을 공개하지 않는다.
공개 문서의 링크는 공개 파일이나 공식 외부 자료로 연결한다. 로컬 작업표는 공개 문서에 본문이나 사적 링크로 복사하지 않는다.

## R8. 보고와 개선을 이어간다

보고는 초보자가 이해할 한국어로 `구현완료 / 검증완료 / 커밋·푸시 / 공개출시 / 클라이언트`를 구분한다.
하지 않은 단계는 미실행, 확인할 수 없는 단계는 미확인으로 쓴다. 고객 답장은 작성한 파일을 사용자에게 주며 직접 발송하지 않는다.

작업 종료 시 반복된 문제·실제 소요·재실행 이유·다음 개선 하나를 기록한다. 관련 작업 중 지난 검토에서 7일 이상 지났으면
운영 상태를 검토한다. 별도 예약 작업을 만든다는 뜻은 아니다. 문제가 생기면 먼저 규칙 미준수인지, 발견 경로 문제인지,
규칙 자체의 결함인지 구분하고 규칙·안내·검증 중 필요한 곳을 고친다. 모든 사고마다 규칙 하나를 덧붙이지 않는다.

## R9. 작업공간 정리도 작업의 일부다

현재 작업에서 만든 임시 파일·빌드 결과·작업공간의 소유자와 사용 목적을 기록한다.
이상한 이름만으로 삭제하지 않는다. 정확한 경로, 실제 내용, Git 작업공간 연결, 진행 중인 작업과의 관계를 확인한다.
권한 범위 안의 불필요한 빈 폴더는 비재귀 삭제하고 결과를 기록한다. 내용이 있으면 필요한 증거·미커밋 변경·개인 자료를 먼저 구분한다.
다른 작업의 자료, 고객 폴더, 아직 사용하는 환경을 정리 대상으로 추정하지 않는다.
이번 작업 범위에서 안전하게 정리할 수 없는 항목은 이유와 위치를 로컬 작업표에 남긴다.
공개 문서에는 실제 머신 경로나 정리 대상의 개인 정보를 복사하지 않는다. 세부 기준은 [공개·정리 기준](publication-and-workspace-hygiene.md)을 따른다.
