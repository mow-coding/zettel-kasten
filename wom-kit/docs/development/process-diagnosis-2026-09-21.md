# 개발 방식 문제 진단과 조사 근거

작성: 2026-09-21. 범위: 선택한 과거 개발 기록과 현재 소스의 조사 결과.
모든 편지를 전수 감사했다거나 모든 실패가 같은 원인이라고 주장하지 않는다.
고객 원문과 개인 경로는 포함하지 않는다. 비공개 기록의 세부 대조 위치는 로컬 회의록에만 둔다.

## 1. 진단

기록과 검증을 중시하는 원칙은 이미 있었다. 반복된 문제는 사용자 결정·실제 사용 흐름·회귀 검사·출시물·다음 행동이
항상 연결되지 않았다는 것이다. 문서를 늘리는 것만으로 해결하지 않고 시작 안내와 현재 작업표, 검증 기준을 연결한다.

| ID | 관찰한 사실과 근거 | 분류 | 고칠 작업 방식 |
|---|---|---|---|
| D01 | [전체 액세스 수정 기록](../archive-infra-decision-log-2026-09-21-v0436-letter-168.md)은 사용자 미승인 제외 목록이 배포됐음을 명시한다. | 결정 미준수 | 사용자 결정과 AI 제안을 분리하고 승인 UX의 실제 결과를 결정에 대조한다. |
| D02 | 수정 전 개발 시작 안내에는 기록 의무가 있었지만 현재 공통 운영 규칙과 작업표로 이어지는 경로가 없었다. 날짜별 규칙이 흩어져 있었다. | 규칙 발견 경로 미비 | 얇은 시작 안내 → 공통 규칙 → 현재 작업표. 특정 작업 규칙의 적용 범위를 표시한다. |
| D03 | [업데이트 진입점 수정](../archive-infra-decision-log-2026-09-18-v0425-archive-root-update-hotfix.md): 프로젝트 루트 재현은 통과했지만 실제 아카이브 루트 호출에는 수정이 더 필요했다. | 검증 기준 미비 | 정확한 진입점과 작업 디렉터리를 합성 재현에 포함한다. |
| D04 | [업데이트 복구 공백](../../../meeting-minutes/2026-08-12-letter129-update-collision-remediation-gap.md): 충돌 탐지는 됐지만 공식 복구 경로가 없어 업데이트가 끝나지 않았다. [후속 수정](../archive-infra-decision-log-2026-08-12-v03316-letter129.md)이 필요했다. | 완료 기준 미비 | 탐지뿐 아니라 해소·갱신·새 프로세스 확인을 연결한다. 앞선 탐지 수정의 성공은 인정한다. |
| D05 | [Windows 승인창 수정](../archive-infra-decision-log-2026-08-24-v045-task-dialog-native-abi.md): 실제 OS 구조체 ABI 문제는 모의 결과로 잡히지 않았다. | 검증 환경 미비 | 실제 지원 OS에서 해당 경로를 확인하고 mock 성공과 구분한다. |
| D06 | [현재 CI](../../../.github/workflows/ci.yml)는 main/tag에는 빠른 gate, PR에는 전체 행렬을 둔다. 문서 전용 분기는 없다. | 규칙·자동화 미비 | 문서 전용 분류와 정직한 결과 집계를 먼저 구현한다. 이미 존재하는 main/tag 최적화를 다시 만들지 않는다. |
| D07 | 같은 workflow는 파일 크기 기준 분할의 한계와 큰 CLI 테스트 모듈·프로세스 테스트의 긴 실행을 설명한다. | 측정·분할 미비 | 실제 소요로 병목을 측정한다. 조각 수 증가만으로 절반 시간 달성을 약속하지 않는다. |
| D08 | 과거 로컬 검증 기록에는 과도한 작업자 분산 뒤 사용량 소진으로 최종 종합이 끝나지 않은 사례가 있다. 수치는 당시 자기 보고이며 이번에 계량 재검증하지 않았다. | 작업 구성 미비 | 하나의 종합 책임, 작은 독립 단위, 필요한 검토만 운영한다. 대량 작업자 투입을 품질 증거로 삼지 않는다. |
| D09 | 기존 인수인계의 제품 기능 버전 약속과 이후 운영 개선 중심 범위가 충돌했다. | 인수인계·추적 미비 | 사용자 범위 수정 시 현재 작업표와 답장 약속을 함께 대조한다. 이슈 ID와 실제 출시 버전을 분리한다. |
| D10 | 같은 PC의 두 인간 사용자를 한 개발 환경으로 취급할 위험을 사용자가 명시적으로 교정했다. 이번 조사에서 실제 유출을 새로 확인했다는 뜻은 아니다. | 경계 정의 보완 | 소유자·접근 허용·공개 범위를 분리한다. 비공개 원본에서 공개용 합성 이슈를 만든다. |

## 2. 잘 작동했던 점도 유지한다

- [독립 검토 수정 기록](../archive-infra-decision-log-2026-09-19-v0431-letter-163-remainder.md)에는 검토로 발견한 문제를 수정한 근거가 있다. 검토를 없애는 것이 목표가 아니다.
- [과거 내용 변경 검토](../archive-infra-decision-log-2026-07-13-v03230-digest-bound-content-change-review.md)는 앞 단계 성과를 이어 받은 기능이다. 새로운 불편의 보고를 곧바로 앞선 수정 실패로 분류하지 않는다.
- 설치된 wheel, 공개 다운로드, 합성 재현, 결정 로그는 기존 자산이다. 유지하되 반복 수작업과 중복 검사를 줄인다.
- 과거 특정 통합 작업의 '중간 베타 요청 금지' 같은 규칙은 당시 범위에 적용됐다. 이를 영구적인 베타 채널 금지로 확대하지 않는다.

## 3. 같은 범주의 오픈소스에서 확인한 방식

확인일: 2026-09-21. 아래는 공식 프로젝트 자료다. 외부 방식과 WOM의 채택 판단을 분리한다.
현재 웹페이지와 main 브랜치는 변할 수 있으므로 후속 구현 때 실제 설정을 다시 확인한다.

| 공식 자료 | 확인한 방식 | WOM에 적용할 판단 |
|---|---|---|
| [pip 이슈 분류](https://pip.pypa.io/en/stable/development/issue-triage/) | 실행 가능한 문제 설명과 상태 분류를 통해 조사와 수정으로 연결한다. | 원본 편지를 정제한 재현 항목으로 만들고 PR·검증·배포와 연결한다. |
| [rclone 버그 안내](https://rclone.org/bugs/) | 버전·환경·실행 정보와 민감 정보 제거를 안내한다. | 재현에 필요한 특성은 보존하되 고객 원본을 공개하지 않는다. |
| [pip 실제 CI](https://github.com/pypa/pip/blob/main/.github/workflows/ci.yml) | 경로 분류로 PR 검사 실행을 나누고 문서·패키징 등 작업을 구분한다. | 현재 WOM 검사 집계와 경로 분류를 함께 설계한다. 파일 확장자만으로 생략하지 않는다. |
| [rclone 베타](https://rclone.org/downloads/#beta-releases) | 개발 커밋의 베타를 배포하고 정식판의 전체 통합 검증과 구분한다. | main 베타와 안정판을 분리하되 통과한 검증 범위를 정직하게 표시한다. |
| [pip 출시 절차](https://pip.pypa.io/en/stable/development/release-process/) | 정기 릴리스와 긴급 수정, 변경 없는 경우의 생략을 구분한다. | 주 1회 출시 필요성 검토는 WOM의 선택이다. pip의 주기를 그대로 따른다는 뜻이 아니다. |
| [restic 배포물 검증](https://restic.readthedocs.io/en/stable/developer_information.html#verifying-the-official-binaries) | 공개 바이너리·checksum·서명·소스 대응을 검증하고 릴리스 준비를 자동화한다. | 소스와 실제 wheel의 연결을 보존하면서 공통 증거 생성기를 만든다. WOM이 이미 재현 빌드나 서명 검증을 제공한다고 주장하지 않는다. |
| [Borg 개발 안내](https://borgbackup.readthedocs.io/en/stable/development.html) | 변경과 검토, 테스트와 릴리스 준비를 문서화한다. | 관련 없는 리팩터링을 결함 수정과 섞지 않고 검토 가능한 단위로 진행한다. |

## 4. 개선 효과 확인 방법

다음 실제 작업들에서 인수인계 재설명 횟수, 중복 검사 이유, 문서 전용 CI 소요,
공개 후 같은 사용 흐름의 추가 차단, 고객 성공 확인의 유무를 기록한다.
취소된 CI를 결함으로 집계하거나 여러 동시 run의 합계를 사람의 대기 시간으로 보고하지 않는다.
기준 자료가 없으면 수치 개선을 주장하지 않고 다음 작업부터 측정한다.

정책은 [공통 규칙](README.md)과 [피드백·출시 정책](feedback-and-release-policy.md)에,
도입 상태와 사례 대입 결과는 [도입 계획](adoption-plan.md)에 둔다.
