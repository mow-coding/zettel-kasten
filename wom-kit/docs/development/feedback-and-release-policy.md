# 피드백 접수, 검증, 배포와 출시 정책

상태: 2026-09-21 운영 자동화 구현 후보. 기록·범위·증거 구분은 지금 적용한다.
CI 분류, 자동 베타, 증거 생성기, GitHub 이슈 폼의 코드를 추가했다. 원격에서 성공한 실행 근거가 없으면 적용 완료라고 보고하지 않는다.
현재 원격 필수 검사는 실제 저장소 설정대로 통과해야 한다. 이 문서가 검사를 생략할 권한을 주지 않는다.
기본 규칙: [공통 작업 규칙](README.md). 구현 순서: [도입 계획](adoption-plan.md).

## 1. 비공개 접수에서 공개 이슈로

1. 허용된 경로에서 원본을 읽고 비공개 보관한다. 고객별 원본과 공개 항목의 대응표는 로컬 기록에만 둔다.
2. [접수 양식](feedback-issue-template.md)에 기대 동작, 실제 결과, 버전, OS, 합성 재현과 업무 영향만 정제해 적는다.
3. 한 보고에 여러 원인이 있으면 항목을 나누고, 같은 원인의 중복 보고는 기존 항목에 연결한다.
4. 현재 버전에서 이전 수정이 성공했는지, 같은 결함이 재발했는지, 다른 단계가 막혔는지 구분한다.
5. 실제 사용 흐름을 완료 조건으로 정하고 수정·검증·출시·고객 확인 근거를 항목에 연결한다.

이슈 번호 또는 로컬 `DEV-YYYYMMDD-NN`을 추적 ID로 사용한다. 번호는 고객 식별자가 아니다.
주 작업 상태는 `접수 → 재현/분류 → 구현 → 검증 → 병합 → 배포`이며, 재현 불가·중복·철회는 이유를 남긴다.
고객 확인은 별도 상태 `미요청 / 확인 대기 / 성공 확인 / 추가 문제`로 유지한다.
배포된 수정의 개발 항목은 근거가 있으면 닫을 수 있지만 고객 성공까지 확인했다고 쓰지 않는다.
고객 답장은 설치 대상·개선 사항·알려진 한계·확인 요청을 담은 파일로 제공하고 사용자가 발송한다.

## 2. 작은 수정도 사용자 흐름으로 검증한다

수정 전 실패하는 최소 합성 사례와 수정 후 통과하는 같은 사례를 연결한다.
새 코드가 필요 없는 문서 작업에는 문서 링크·용어·개인정보·지침 일관성 검사를 사용한다.

| 변경 성격 | 필요한 증거 |
|---|---|
| 명령 간 데이터 전달 | 앞 명령 출력 그대로 다음 명령 입력으로 사용; 프로젝트 루트/아카이브 루트/별도 작업 디렉터리 |
| 업데이트·설치 | 이전 공개 버전으로 만든 합성 환경에서 갱신; 새 프로세스의 실제 버전·pin·출처 확인 |
| 저장·삭제·복구 | 실패 또는 강제 중단 뒤 상태·재시도·복구; 기대 원본 바이트와 결과 비교 |
| Windows 창·입력 | 지원 Windows에서 실제 OS 경로 확인; mock 결과와 구분; 승인 모드별 창 횟수 |
| 오류 안내 | 원인 코드와 다음 행동이 사용자 진입점까지 전달; 내용·비밀값 노출 없음 |
| 성능 | 같은 합성 규모·입력·측정 방식의 전후 소요와 호출 횟수; 측정 도구 자체의 비용도 확인 |

관계없는 모든 테스트를 매 수정마다 반복하지 않는다. 반대로 내부 함수의 성공만으로 설치된 제품의 성공을 주장하지 않는다.
위 표는 해당 변경에 필요한 검증을 선택하는 기준이지 모든 작업에 모든 항목을 강제하는 목록이 아니다.

## 3. CI 층 나누기 — 구현 계약

현재 기준은 `.github/workflows/ci.yml`이다. 2026-09-21 확인 시 main/tag push에는 빠른 gate가 있고,
PR와 수동 실행에는 전체 행렬이 있다. main/tag 전체 검사 생략을 새로 구현해야 한다는 과거 설명은 현재와 다르다.

| 제안 단계 | 실행 대상 | 통과 조건 |
|---|---|---|
| 문서 전용 PR | 허용한 개발 문서만 변경 | 링크·개인정보·용어·지침 정합; 분류 결과 기록 |
| 제품·의존성·빌드·검사 설정 PR | 실행이나 검증에 영향 있는 변경 | 빠른 gate, 관련 회귀, 현재 필수 플랫폼 검사; 검증 범위 축소는 별도 근거 필요 |
| main 병합 | 정확한 병합 결과 | 후보 증거와 소스 대응 확인, 리소스·패키징 검사; 일치 근거 없으면 필요한 검사 수행 |
| 안정판 후보 | 출시할 정확한 소스와 배포물 | 지원 플랫폼 전체 회귀, 설치·갱신·복구 흐름, 패키지 내용과 개인정보 검사 |
| 공개 후 | 실제 공개 다운로드 | 익명 다운로드 해시·크기, 깨끗한 환경 설치와 새 프로세스 확인 |

문서 전용 허용 목록의 시작 범위는 `wom-kit/docs/development/**`, `CONTRIBUTING.md`, 개발 시작 안내,
개인정보 검토를 마친 운영 회의록·결정 로그다. 후속 구현 시 정확한 경로 목록을 코드로 명시한다.
모든 `.md` 파일을 문서 전용으로 취급하지 않는다. 패키지에 포함되는 지침·템플릿·버전 계약·리소스,
의존성, 소스, 테스트, 도구, CI 설정, 알 수 없는 경로가 바뀌면 실행 영향이 있는 변경으로 분류한다.

필수 결과 집계는 의도한 생략과 실패·취소·결과 누락을 구분해야 한다. 경로 분류 결과와 각 필수 job의 상태를 대조한다.
단순히 모든 `skipped`를 성공으로 처리하지 않는다. 이를 검증하기 전에는 문서 전용 생략을 활성화하지 않는다.

검증 결과 재사용은 소스뿐 아니라 workflow, 의존성 잠금, 빌드 입력, 플랫폼·Python 조건이 같은지 확인한다.
표현이 같거나 버전 번호만 같다는 이유로 재사용하지 않는다. 취소된 run은 통과 근거가 아니다.
문서만 다른 tree의 코드 검증을 재사용하려면 실행·검증 입력이 같다는 별도 증거가 필요하며,
실제 공개 wheel의 검증은 계속 해당 wheel의 해시를 기준으로 한다.

작업 분할은 실제 테스트 소요를 측정한 뒤 바꾼다. 큰 모듈 하나가 한 조각에 남으면 조각 수를 두 배로 늘려도 병목이 남는다.
문서 검사 5분 이내는 초기 측정 목표이며 보장이나 기존 검사 면제 기준이 아니다. 전체 검사 목표 시간은 병목 측정 후 정한다.

## 4. 베타와 안정판을 분리한다 — 구현 계약

main 병합마다 베타 wheel을 자동 생성·공개하는 것을 목표로 한다. 각 대상 커밋이 필수 조건을 통과한 경우에만 공개한다.
실패한 빌드는 실패 상태와 원인을 남기며 정상 베타인 것처럼 공개하지 않는다.
베타는 GitHub prerelease로 표시하고 안정판 `latest`를 바꾸지 않는다. 고객은 베타 사용을 명시적으로 선택한다.
고객 PC에 자동 설치하거나 안정판 사용자를 베타로 바꾸는 기능을 이 작업에 포함하지 않는다.

버전 표기는 Git tag `vX.Y.ZbN`, Python wheel `X.Y.ZbN`으로 맞춘다. 초기 제안의 별칭 변환을 없애 설치 파일·업데이트 대상·공급 잠금의 식별자가 일치하도록 했다.
현재 main의 안정판 형식 버전에서 다음 패치 버전을 베타 대상으로 정하고, N은 베타 workflow의 run number다. 베타 생성용 커밋과 태그만 만들며 main의 제품 버전은 자동 변경하지 않는다.
N은 대상 안정판 버전 안에서 충돌 없이 증가하며, 재시도는 같은 소스의 기존 결과를 확인하고 덮어쓰지 않는다.
공개된 tag나 wheel을 다른 바이트로 교체하지 않는다. 새 바이트는 새 식별자로 공개한다.

자동 배포 전에 다음을 한 번에 검증해야 한다:

- 버전 파서·정렬·최신 버전 선택·CLI 표시·wheel metadata·리소스 버전의 일치.
- 업데이트 대상과 공급 잠금, 소스 커밋, 다운로드 주소의 일치.
- 안정판 → 베타 → 다음 베타 → 안정판의 합성 설치·갱신 흐름.
- 중복 실행, 중간 실패, 동시 병합, 공개 실패 뒤 재시도의 일관성.

updater는 명시적인 정규 베타 번호를 처리하고 안정판 최신 검색에서는 베타를 제외한다. 전환 회귀 시험과 정확한 베타 wheel의 Windows 설치 검증이 성공해야 자동 공개한다. 시험용 작은 wheel의 실제 설치·전환 증거와 완제품 wheel 설치 증거는 구분한다.
베타는 통과한 검사 범위를 명시하며 안정판 전체 검증을 받았다고 표현하지 않는다.

## 5. 안정판 출시 판단

주 1회 **출시 필요성 검토**를 기본 운영 선택으로 한다. 작업 중 마지막 검토에서 7일 이상 지났을 때 검토하고 기록한다.
고정 요일의 무조건 배포나 예약 작업을 만들지 않는다. 변경이 없거나 준비가 안 되면 출시하지 않는다.
이 주기는 WOM의 운영 선택이며 오픈소스 전체가 따르는 표준이라고 주장하지 않는다.

다음이 갖춰졌을 때 승인된 출시 범위 안에서 진행한다:

1. 완성된 사용자 가치 또는 필요한 결함 수정이 있고 릴리스에 포함할 항목이 확정됨.
2. 대상 소스·패키지의 필수 검사와 관련 실제 사용 흐름이 통과함.
3. 알려진 차단 문제, 업그레이드 방법, 실패 시 복구 방법, 남은 한계가 정리됨.
4. 출시 담당자가 소스·tag·배포물·공개 후 확인을 순서대로 수행할 수 있음.

실제 사용을 막는 결함은 정기 검토를 기다리지 않고 앞당긴다. 보안·데이터 손상 문제는 최우선으로 처리하되
필요한 검증을 생략해 긴급성을 충족했다고 하지 않는다. 의존 관계 없는 기능은 묶기 위해 기다리지 않는다.
범위 밖 기능이나 자동화가 미완료여도 해당 안정판의 완료 조건을 충족하면 독립적으로 판단한다.

릴리스 변경은 단일 담당자가 `후보 확인 → 병합 결과 확인 → tag → 배포물 검증 → 공개 → 공개물 재검증 → 증거·답장` 순서로 수행한다.
기존에 승인된 세부 릴리스 절차가 있으면 이를 따른다. 베타 자동 공개는 안정판 자동 승격 권한이 아니다.

## 6. 증거 자동화 — 구현 계약

매번 새 수작업 증거 스크립트를 만드는 대신 공통 생성기가 다음 사실을 모으도록 한다:

- 항목 ID, PR, 후보/병합 commit과 tree, tag 대상.
- CI run과 attempt, job 결과, 실제 검증 범위, 검사 입력의 식별 정보.
- wheel 이름·버전·바이트 크기·SHA-256, 빌드 출처와 공개 URL.
- 익명 다운로드 비교, 깨끗한 설치 환경, 새 프로세스 결과.
- `미실행 / 실행 중 / 통과 / 실패 / 취소 / 오래된 증거`와 남은 한계.

없는 값은 비워 두고 미확인으로 표시한다. 추정값으로 성공 영수증을 완성하지 않는다.
기계 결과를 저장하는 구조화 파일과 이를 읽기 쉽게 보여주는 요약을 함께 만든다. 원본 고객 로그는 포함하지 않는다.
회의록은 사용자 의도·결정·수정 이유를 보존하고 기계 출력 전체를 중복 복사하지 않는다.
공개 노트의 근거는 공개 증거를 가리키고, 로컬 자료 경로나 고객 식별자를 노출하지 않는다.

## 7. 검토와 피드백

한 작업이 끝날 때 인수인계에 소요된 재조사, 중복 검사, 사용 흐름 누락, 공개 후 차단을 기록한다.
CI wall time에는 대기·동시 실행이 포함될 수 있으므로 이를 사람의 손실 시간이나 결함률로 바꾸어 표현하지 않는다.
개선은 같은 종류의 이전 작업과 비교한다. 고객 확인이 없는 항목은 개발 검증의 성과로 대체하지 않는다.

외부 근거와 WOM에 적용한 판단은 [조사표](process-diagnosis-2026-09-21.md)에 분리해 두었다.

## 구현 파일과 운영 확인

- `.github/workflows/ci.yml`: 정확한 변경 분류, 의도한 생략 검증, CI 결과 JSON 보존.
- `.github/workflows/beta-delivery.yml`: main의 CI 완료 뒤 동일 tree의 최신 PR 검사 증거 확인, 베타 생성·설치 검사·순차 공개.
- `wom-kit/tools/delivery_source_proof.py`: workflow와 잠금을 포함하는 전체 tree 일치만 재사용. 근거가 없으면 임의로 배포하지 않고 실패 원인을 표시.
- `wom-kit/tools/publish_beta.py`: draft 다운로드, SHA/크기, 공개 후 익명 다운로드와 새 환경 설치를 실제 수행. 공개 자산 덮어쓰기 금지.
- `.github/ISSUE_TEMPLATE/feedback.yml`: 합성 재현과 확인 범위를 구분하는 공개 접수. GitHub의 필수 필드는 형식 확인이며 내용 검증이나 고객 성공을 보장하지 않는다.

배포는 GitHub의 `queue: max`로 직렬 실행한다. 대기열의 100건 제한에 걸리면 취소를 완료로 세지 않고 작업표에서 복구 대상으로 관리한다.
동시성 근거: [GitHub 공식 문서](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
