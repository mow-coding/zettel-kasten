# 작업 방식 공개와 작업공간 정리

상태: 2026-09-21 사용자 추가 요청을 반영한 운영 규칙.
목적은 AI와 협업하는 방법을 설명하고, 실제로 수행한 범위를 근거와 함께 보여 주는 것이다.
공개 가능한 문서를 작성했다는 사실과 GitHub에 게시했다는 사실은 별도로 기록한다.

## 공개할 것과 로컬에 둘 것

| 자료 | 공개 원칙 | 이유 |
|---|---|---|
| 공통 작업 규칙과 정제된 AI 시작 안내 | 공개 가능 | 기여자와 다음 AI가 같은 절차를 찾고 협업 방식을 이해할 수 있음 |
| 비어 있는 인수인계·피드백 양식 | 공개 가능 | 다른 환경에서 재사용할 수 있음 |
| 개발 과정의 판단과 사례 | 개인정보 제거 후 공개 가능 | 문제·선택·한계·검증을 설명; 고객 원문을 전시하지 않음 |
| 합성 재현·테스트·공개 배포물 증거 | 민감 정보 검사 후 공개 가능 | 재현과 검증의 근거 |
| 진행 중인 작업표와 상세 대화 | 기본 로컬 | 사적 작업 위치, 미완료 상황, 고객 대응 관계가 섞일 수 있음 |
| 고객 원본 편지·로그·첨부·비밀값·개인 경로 | 공개 금지 | 개발 방법 공개와 고객 데이터 공개는 별개 |
| 원본 비공개 인수인계 | 공개 금지 | 사용자 지정 보호 자료; 정제본이 필요하면 별도로 작성 |

공개 레포의 README에서는 공통 규칙과 도입 상태를 연결한다. '완벽한 자동화' 같은 주장 대신
지금 있는 수동 절차와 미구현 자동화를 구분한다. 자기 검토를 독립 검토라고 쓰지 않는다.
각 AI의 내부 추론이나 원본 대화를 공개할 필요는 없다. 사람이 이해할 결정 이유와 확인 가능한 결과를 남긴다.

## 이번 문서 묶음의 저장·공개 상태

2026-09-21 문서 작성 단계에서 신규 규칙은 로컬 파일이며 커밋·푸시하지 않았다.
기존 CONTRIBUTING과 README는 추적 파일이지만 이번 추가 내용은 미커밋 변경이다.
root AGENTS는 기존 ignore 정책에 따라 로컬에 남아 있다. CLAUDE와 공통 문서는 공개 가능한 후보로 작성했다.
따라서 다음 AI가 이 checkout에서 읽을 수 있는 것과 새 clone에서 받을 수 있는 것은 아직 다르다.

향후 문서 공개 시에는 공유할 정제된 시작 안내도 함께 포함해 두 AI의 입구가 어긋나지 않게 한다.
AGENTS를 포함하려면 원래 무시된 파일이라는 점을 인지하고 개인정보 확인 후 정확한 경로만 force-add한다.
회의록도 공개할 정제본만 개별 force-add한다. ignore 규칙을 일괄 해제하지 않는다.
현재 작업표와 원본 비공개 인수인계는 포함하지 않는다.
공개 링크 검사·개인정보 검사·직접 diff 검토 후 별도 문서 변경으로 커밋한다.
이를 제품 버전 변경이나 보류된 릴리스에 섞지 않는다.

## 정리 작업 순서

1. 사용자 지시 또는 현재 작업 소유 범위를 확인한다. 저장소 밖의 정리는 지정된 대상에만 적용한다.
2. 정확한 절대 경로를 로컬에서 확인하고, 링크·junction 여부와 실제 내용·숨김 파일을 살핀다.
3. Git worktree 등록과 진행 중인 작업을 확인한다. 오래된 시각이나 이상한 이름만으로 미사용을 단정하지 않는다.
4. 빈 일반 폴더로 확인된 경우 비재귀 삭제를 사용한다. 내용이 새로 생기면 실패하도록 한다.
5. 내용이 있으면 현재 작업의 버릴 수 있는 산출물과 보존할 코드·증거·개인 자료를 구분한다.
   불확실한 항목은 보존하고 필요한 판단만 요청한다. 다른 shell에 경로 문자열을 전달해 일괄 삭제하지 않는다.
6. 삭제·이동한 정확한 대상, 전후 확인, 보존한 항목과 이유를 로컬 기록에 남긴다.

검증에 필요한 빌드 결과나 재개할 검사의 로그는 아직 쓰임이 있으므로 단순한 쓰레기로 취급하지 않는다.

## 반복해서 쌓이는 찌꺼기와 정리 시점

출시나 병합이 끝나면 그 작업이 만든 아래 항목을 바로 확인하고 정리한다. 다음 작업으로 미루지 않는다.

| 항목 | 정리 방법 |
|---|---|
| 병합된 Git worktree와 로컬·원격 브랜치 | 변경 0을 확인한 뒤 worktree를 제거하고 브랜치를 삭제한다 |
| 설치 검증용 가상환경 | 검증 스크립트가 실패해도 스스로 지우게 하고, 남은 것은 삭제한다 |
| 출시 작업 폴더의 wheel 사본 | 공개 자산과 같은 사본은 삭제하고 검증 JSON만 보존한다 |
| 넘겨받은 다른 AI의 작업 폴더 | 고유한 기록만 보존한 뒤 삭제한다. Windows에서 경로가 너무 길면 긴 경로 접두어를 붙여 지운다 |
| 작업이 만든 Docker 자원 | 아래 절차 |

### Docker

Docker의 이미지, 멈춘 컨테이너, 빌드 캐시는 쓰지 않아도 디스크를 계속 차지하며 수십 GB까지 쌓일 수 있다.

1. 재현용 컨테이너는 가능하면 끝나면 사라지는 방식(`docker run --rm`)으로 실행한다.
2. 그 작업을 위해 받은 이미지, 만든 컨테이너와 빌드 캐시는 작업이 끝날 때 이름을 정확히 지정해 지운다.
3. 다른 프로젝트나 다른 세션의 이미지·컨테이너·볼륨은 WOM 작업의 소유가 아니므로 건드리지 않는다.
   일괄 정리 명령(`prune`)은 소유를 가리지 않으므로 쓰지 않는다.
4. 명령 예시가 들어간 글을 파일에 넣을 때는 셸 명령줄의 따옴표 안에 넣지 않는다. 역따옴표가 명령으로 실행될 수 있으므로 파일 쓰기 도구를 쓴다.
원인 추정과 사실을 분리한다. 잘못 만들어진 폴더라는 정황만으로 특정 AI가 만들었다고 단정하지 않는다.
