# 개발 피드백 접수 양식

상태: 수동 작성용. GitHub 이슈 폼은 후속 구현이다. 기본 흐름은 [접수·출시 정책](feedback-and-release-policy.md)을 따른다.
원본 편지를 그대로 공개 이슈로 붙이지 않는다. 정제한 아래 항목만 공개할 수 있다.

## 공개용 본문

```text
제목: [증상 또는 요청을 한 문장으로]
추적 ID: [이슈 번호 또는 DEV-YYYYMMDD-NN]
분류: 결함 / 개선 요청 / 질문
업무 영향: 사용 차단 / 불편하지만 진행 가능 / 표현·문서
버전과 설치 방식: [공개 버전, 안정판/베타, 설치된 실행 파일의 버전 확인 결과]
환경: [OS, Python 버전 등 원인 분석에 필요한 값만]
기대했던 동작:
실제로 일어난 동작:
이전 수정과의 관계: 이전 수정 성공 / 같은 결함 재발 / 새 문제 / 아직 미확인

합성 재현 단계:
1. [합성 데이터 준비]
2. [실제 사용한 진입점과 같은 방식으로 실행]
3. [기대 결과와 차이]

합성 경로의 필요한 특성: [공백·한글·길이·상대경로 기준 등]
내용을 제거한 오류 코드와 진행 상태:
현재 가능한 우회 방법과 한계:
완료 조건: [사용자의 작업이 어디까지 성공해야 하는가]
관련 개발 항목 / PR / 공개 증거:
개발 상태: 접수 / 재현·분류 / 구현 / 검증 / 병합 / 배포
고객 확인: 미요청 / 확인 대기 / 성공 확인 / 추가 문제
목표 버전: 미정 [결정 전에는 약속하지 않음]
```

## 개발자가 로컬에만 남길 대응 정보

- 비공개 원본 위치와 해당 보고를 찾을 참조. 접근 허용 범위를 함께 기록한다.
- 여러 보고와 공개 항목의 대응 관계. 공개 이슈에 고객 식별자를 넣지 않는다.
- 공개 요약에서 제거한 정보의 종류와 재현에 필요한 특성을 보존한 방법.
- 요청한 추가 정보와 실제 답변. 고객 PC에서 임의로 수집하지 않는다.

## 공개 전 확인

원본 파일명·이미지·로그·링크에도 계정명, 실제 경로, 사적 내용, 비밀값이 남아 있지 않은지 확인한다.
합성 재현은 실제 고객 자료를 복사한 것이 아니어야 한다. 자동 검사와 사람이 읽는 검토를 함께 수행한다.
개인정보 제거로 원인 특성을 잃었다면 더 적절한 합성 사례를 만든다. 원문 공개로 해결하지 않는다.
