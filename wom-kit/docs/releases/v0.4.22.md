# WOM-kit v0.4.22 — Project-Update Failure Truth And Started-Claim Abandon

v0.4.22 answers beta letters 161 and 162. A reviewed `project-version-update`
to v0.4.21 reached the native dialog, published its one-use claim and then
failed about nineteen seconds later without saying which gate refused; the
claim stayed `started`, the version-update lock and reservation stayed in
place, `--resume` failed in the same preflight, `version` reported a
misconfigured origin under disk contention, `operation-control` from the
archive root could not find the run, and `upgrade-check --dry-run` printed
nothing for twenty-three minutes. This release makes that failure say where it
stopped, gives the operator one reviewed way to close the stuck claim and
release the reservation, and stops the two unrelated observations from
lying. No writer, approval binding, receipt or schema changes; the one-dialog
contract and the one-use claim are unchanged.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.22-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification. In particular, the gate that refused the letter-161 update is
not known from the v0.4.21 diagnostics; v0.4.22 makes the next run name it.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0422-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.22/wom_kit-0.4.22-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.22` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## What the letter-161 run looked like, reproduced

The failure was reproduced on synthetic projects only: an existing v0.4.20
project runtime updating to v0.4.21 from a local bare remote. The approved
writer raises between the claim publication and the `approval_bound`
checkpoint, inside the post-claim revalidation of the approved snapshot; every
boundary on that path re-raised `from None`, so the diagnostics carried only
the outer `ExactHumanApprovalWorkflowError` and the fixed
`project_version_update_command_failed` result. The claim stays `started` by
the one-use contract (a non-success after the writer boundary must never be
read as clean), the lock and `private/version-updates/update_*` transaction
stay for a resume, and `--resume` reopened the same transaction and failed
in the same preflight. Nothing in v0.4.21 could close that claim without a
domain write, so the project stayed reserved.

## Failure truth (letter 161)

- A failure after the claim now carries a content-free cause: `cause_code`,
  `cause_stage` (`domain_writer` for the approved writer, `key_or_claim` for
  the claim broker) and `cause_code_source: fixed_literal_allowlist` in the
  CLI result and the diagnostics record. Only fixed codes from the
  `project_version_update_`, `project_update_`, `project_runtime_`,
  `project_git_` and `exact_human_approval_` families are carried; free text,
  paths and exception messages never travel, and exception chaining stays
  `from None`.
- The operation journal names the stages after `verify-release`:
  `materialize-runtime-candidate` (every candidate substage), `native-approval`,
  `post-claim-revalidate`, `approval-bound` and `durable-write`. A journal
  that ends in `result_unavailable` now says which stage it stopped in.

## Started-claim abandon and claimless cancellation (letter 161)

`project-version-update <project-root> --resume --abandon-started-approval
--affirm-external-writers-quiescent` closes a stuck `started` claim without a
domain write and without a second dialog; like every resume it takes no
`--target` and no reviewer id, because the transaction already binds them.
It is allowed only when the transaction journal proves no component write
started: journal state `exact`, verified phases exactly `["lock_backlinked"]`
and live classification `prewrite_exact`. It marks every started claim of that exact context `failed`
with `operator_abandoned_before_domain_write`; any other state returns
`project_version_update_abandon_unavailable` and writes nothing, the flag
without `--resume` returns `project_version_update_abandon_requires_resume`,
and a `succeeded` claim for the context refuses with
`exact_human_approval_resume_claim_invalid`.

A following plain `--resume` treats the operator-abandoned claim as absence
and runs the existing claimless cancellation: the lock and the transaction
directory are removed, the version pin is unchanged, and the result is
`preapproval_scaffold_cancelled` with `files_written: []`. A fresh `--approve`
then opens one new dialog. A claim that failed for any other reason still
blocks resume discovery; it must never be read as absence.

## Version and operation-control truth (letters 161 and 162)

- `version` shares one Git probe budget across its reads; that budget is now
  45 seconds instead of 12. When a probe is skipped because the budget is
  exhausted, `runtime_alignment.reason_code` is
  `project_git_probe_budget_exhausted` instead of `project_origin_not_configured`,
  `project_source_tag_not_reachable_from_origin_main` or
  `project_source_observation_unavailable`, so a slow disk is never reported
  as a misconfigured origin.
- `operation-control --action status|wait|recovery-plan` started from an
  archive root whose only blocker is `operation_not_found` retries once with
  the parent project root that owns the archive and reports
  `inspection_root_resolved_to_parent_project: true`. It writes nothing.
- `upgrade-check --dry-run` without `--progress` prints one content-free
  stderr line before it starts: it runs the full deep Doctor scan, may take
  many minutes on a large archive, and is not required before
  `project-version-update`.

## Not in this release

A session-scope pre-approval for the update (letter 161, request 6) changes
the one-dialog approval contract and waits for the maintainer's decision. The
operation journal schema is unchanged; the exception class is not persisted
into the journal because it is not a fixed public code, only the cause code
and the named stage are. LR-06 session integration, LR-02 through LR-05,
LR-07, the byte-hash fidelity mode for binary evidence originals (letter 160
②) and letter 160 ④ carry to v0.4.23 and later.

## Compatibility and privacy

- Existing controls, approvals, receipts, schemas and the operation journal
  format keep their exact bytes and validators; `cause_code`, `cause_stage`,
  `cause_code_source` and `inspection_root_resolved_to_parent_project` are
  additive result fields, and the new journal stage names are additions to
  the same stage set.
- Every new value is a fixed code, a stage name or a boolean; no path,
  message, reviewer id, claim content or archive content is introduced into
  results, journals, diagnostics, tests or release artifacts.
- The abandon path finalizes a claim only when its own authenticated
  checkpoint guard passes under the production key; it cannot be used to
  finish, replay or bypass a write.

## Verification boundary

The release candidate must pass the focused hotfix, approval, project-update,
operation-control, privacy, package-resource, installed-wheel and full
supported-platform CI checks. The exact reviewed merge commit must be tagged,
and the public wheel must be downloaded anonymously, rehashed, installed in a
fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result.
