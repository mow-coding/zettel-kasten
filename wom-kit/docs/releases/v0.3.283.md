# WOM-kit v0.3.283: Activity-Group Retained-Journal Isolation

Release date: 2026-07-30

## Retained-Journal Isolation

The approved activity-group membership-add writer now performs one bounded,
content-free direct-child scan across both private request roots:

```text
.wom-scratch/private/activity-groups/
.wom-scratch/private/activity-group-removals/
```

A retained add journal or a journal using the reserved future-removal suffix
blocks the writer before it attempts the shared writer lock. The same scan is
repeated after that lock is acquired and before snapshots or canonical writes,
so evidence appearing between preflight and lock acquisition also blocks.

The scan reads no journal body. It examines at most 5,000 direct entries across
the two roots, never recurses into nested material, and fails closed when a
root is unsafe or the scan cannot complete. Public results contain fixed
blocker codes rather than private journal filenames or content.

## Filesystem Identity Binding

Every private transaction path is now bound from the resolved archive root to
its leaf directory instead of trusting one earlier pathname check.

- POSIX holds a root-to-leaf directory-descriptor chain, opens each component
  with `O_DIRECTORY | O_NOFOLLOW`, and creates or removes entries relative to
  the bound parent descriptor.
- Windows holds every ancestor with non-delete-shared directory handles opened
  with `FILE_FLAG_OPEN_REPARSE_POINT`, checks the opened file identity and
  reparse attributes, and keeps that chain alive through the transaction.

The writer creates its lock and prepared journal beneath the held private-root
chain. It separately binds the receipt parent before creating the immutable
receipt. A junction, symlink, or directory replacement therefore becomes a
refusal rather than redirecting a reviewed write.

Recovery now keeps that same private-root binding alive while it creates and
removes its exclusive guard. If a complete journal has lost its writer lock,
the recovery claim is also created beneath that already-held binding. Public
success metadata therefore never claims bound-only evidence changes after a
pathname was redirected elsewhere.

## Compare-And-Swap Canonical Writes

The final authority to change a participant is no longer a separate check
followed by an unconditional pathname replacement. WOM performs one OS-level
compare-and-swap that atomically preserves the file occupying the canonical
name at the swap instant:

- Linux exchanges two names beneath the same held parent descriptor with
  `renameat2(RENAME_EXCHANGE)`.
- Apple platforms use `renameatx_np(RENAME_SWAP)` when available.
- Windows uses `ReplaceFileW` with a deterministic sibling backup.

WOM then verifies both the captured prior bytes and the installed replacement
before deleting the captured copy. If another participant changed the
canonical name after the earlier plan/classification, WOM atomically restores
or retains those unknown bytes and refuses the transaction. It never writes
the reviewed before-state over an unknown external edit.

The sibling swap/backup names are content-free and deterministic from the
request digest and canonical filename. A hard exit after the atomic swap can
therefore be classified as a known complementary before/after residue. Normal
completion or an approved recovery deletes only that verified residue.
Unexpected or ambiguous residue enters `manual_forensic_hold`. A POSIX
platform without a working supported atomic exchange primitive fails before
the canonical name is changed. A prepared sibling entry may remain as private
evidence when the libc symbol exists but the kernel or filesystem refuses the
actual exchange.

## Exact Completion Binding

A completed receipt must now match the evidence that says how its transaction
ran.

When the retained journal exists, receipt and journal projections must agree
exactly on their shared transaction fields and every ordered participant:

- archive, request, review-plan, and write-plan bindings;
- event anchor, reviewer, affirmation, and deterministic receipt location;
- item count and ordered row indexes;
- canonical participant locations and before/after file hashes;
- complete before-snapshot evidence; and
- the shared privacy contract.

New write locks use the internal
`wom-kit/activity-group-membership-write-lock/v0.2` shape. In addition to the
request/review/write values and deterministic journal name, the lock commits
to the SHA-256 of the receipt/journal's full semantic projection: anchor,
ordered participants, reviewer affirmation, before/after evidence, receipt
location, and privacy contract. When only completed lock residue remains, the
receipt is recomputed and rebound to that commitment rather than trusting an
opaque write-plan string.

A legacy v0.1 lock remains compatible while its complete journal is present,
because the journal supplies the full semantic evidence. A legacy v0.1
lock-only completed residue does not: it enters `manual_forensic_hold` instead
of authorizing cleanup.

Even for a verified v0.2 lock, automatic journal-free completed cleanup is
Windows-only. Windows can hold the receipt without write/delete sharing while
the lock is removed and the receipt is revalidated. POSIX read descriptors do
not freeze a pathname against replacement, so deleting the only semantic lock
would create an irreversible two-file check/use gap; that state remains
`manual_forensic_hold` on POSIX.

## Recovery Cleanup Revalidation

The read-only recovery plan now binds:

- the immutable receipt's raw SHA-256;
- the exact receipt-to-journal or receipt-to-lock transaction-binding SHA-256;
- the existing journal and lock evidence hashes; and
- the classified participant state.

The approved recovery executor regenerates the plan under its guard, re-reads
the receipt and retained evidence, and verifies the raw receipt and transaction
binding again immediately before cleanup. A mismatch present during planning
becomes non-executable `manual_forensic_hold`. Evidence that changes after
review is retained and the cleanup fails instead of deleting uncertain
history.

Cleanup now deletes only the exact evidence bytes that were reviewed. On
POSIX, WOM first atomically moves the current pathname into a fresh quarantine
under the globally scanned private activity-group transaction root. It keeps
the captured descriptor open, performs a second complete read/hash plus
size/mtime/ctime and identity comparison immediately before unlink, and
deletes only after both observations match. The quarantine directory itself
uses the retained-journal suffix, so a hard exit after capture is discovered
by the next bounded inventory and blocks further cleanup/writes. A same-name
replacement remains public, and an observed mismatch is restored without
overwrite when possible or retained in quarantine for review. If an archive
submount makes the move cross-filesystem, POSIX fails before moving the source.
Windows opens the evidence with READ and DELETE access, rejects directories
and reparse entries, verifies its file identity and SHA-256, and marks that
exact handle for deletion.

POSIX has no portable hash-conditional unlink and cannot revoke an
uncooperative same-UID process's already-open writable descriptor. The capture
algorithm closes pathname-replacement races and detects in-place mutations
observed before its final unlink, but it does not claim protection from a write
that lands after that final check. Operators must keep external editors
quiescent during approved cleanup.

Normal rollback and approved recovery use the same terminal evidence order:

1. delete the exact writer lock;
2. revalidate the receipt state and every canonical participant;
3. prove the writer's journal is the only retained transaction;
4. delete that exact journal last; and
5. require the final transaction inventory to be clean.

Approved recovery then runs one final common cleanup verification immediately
before returning success. This final phase also covers a lock-only
interruption. A receipt or reserved journal that appears after lock deletion
changes the result to retained recovery evidence instead of
`cleanup_completed`.

The normal writer performs the same final inventory check. If foreign
transaction evidence appears, or exact lock/journal cleanup or its
revalidation fails after the receipt is committed, the valid canonical result
and immutable receipt remain intact. The command returns
`applied_evidence_conflict` instead of falsely reporting a clean `applied`
transaction.

## Compatibility

This release deliberately keeps:

- every public activity-group request, plan, write, receipt, journal,
  recovery-plan, and recovery-result artifact schema at v0.1;
- the existing CLI commands and aliases;
- `wom-kit/ai-command-path-routing/v0.5`;
- the existing CLI-only write boundary and no MCP writer.

The private write-lock document advances from v0.1 to v0.2 so a lock-only
completion can carry the full transaction commitment. The reader continues to
recognize v0.1 under the restricted compatibility rule above.
No new schema file is added. No command, MCP method, route version, canonical
mutation field, provider/model/network/database access, or membership
inference is added.

## Explicit Remaining Boundary

v0.3.283 does not implement membership removal. The reserved removal-journal
suffix only makes future removal evidence participate in the existing shared
serialization boundary.

The separately approved removal writer and its hard-interruption recovery are
deferred to v0.3.284. Until then, use only the read-only removal plan and never
edit canonical zets or delete private transaction evidence by hand.
