# WOM-kit v0.4.23 — Binary Fidelity Sources And Session-Bound Drafts

v0.4.23 carries the work left open after v0.4.21 and v0.4.22: a binary
original may be the fidelity source of a summary or derivative draft (beta
letter 160 ②), `create-draft` can be bound to the caller's claimed work
session (the first native writer of LR-06), the letter 160 ④ wrapper report
was reproduced on its exact shape and not confirmed, and the carried rows
LR-02 through LR-05 and LR-07 were revalidated against their existing domain
cohorts. No new approval system, no fixed-closed migration, and every
existing plan digest, receipt and schema id keeps its bytes.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.23-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0423-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.23/wom_kit-0.4.23-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.23` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## Binary originals as the fidelity source (letter 160 ②)

`create-draft --fidelity-source-object-id` accepts a PDF, spreadsheet, image
or any objet that is not UTF-8 text for a `faithful_summary` or
`sanitized_derivative` draft. Such a source is bound on a second comparison
basis, `bytes`: the receipt records the raw digest as the normalized digest,
no newline transformation, and the same absent-source-text and
absent-locator facts. Nothing is extracted or transcribed and no mechanical
verification is claimed; the human review is required exactly as for a text
source. `verbatim` still requires a UTF-8 text objet (only a text region can
be compared mechanically) and its `source_fidelity_source_not_utf8` answer
now names the two modes that accept a binary original. Every validator that
checked the basis accepts both with consistency, both draft receipt schemas
relax the basis const to a two-value enum without changing ids, and the
fidelity policy projection lists `comparison_bases` and
`binary_source_modes`. Text sources keep the `utf8_newlines_lf` basis byte
for byte.

## Session-bound drafts (LR-06a)

`create-draft --client-app-ref <app> --task-route-ref <route>
--work-session-ref <session>` binds one AI-assisted or AI-generated draft to
the caller's claimed work session. The command runs under the session
service's held archive writer lane; the registered app, the retained task
route and the currently claimed session are verified read-only, frozen into a
content-free scope digest (session binding, task route, claim ref), and that
digest is part of the reviewed fidelity plan and therefore of the native
dialog's plan binding. After the dialog and before the claim is published the
scope is re-verified; the actor records the operation as pending
(`kind: create_draft`) and, after the write, as completed; the draft receipt
carries `work_session_binding` and `work_session_scope_sha256`, and results
carry a content-free `work_session` block. Refusals happen before any
dialog: a missing session ref, a session of another task, a pending
operation on the actor, or a non-AI draft. Sessionless `create-draft` and
every existing plan digest are unchanged; an exact replay reproduces the
reviewed plan. The reusable `work_session_native_write` module is the
template for the other native single writers; the writer-session coverage
gate now reports 6 integrated, 29 pending and 20 exempt paths of 56.

## Letter 160 ④: not reproduced

On Windows PowerShell 5.1 with the letter's exact wrapper
(`function Approve([scriptblock]$cmd){ & $cmd > $out 2>&1 }`) an AI-authored
`create-draft --approve` replay reached the native approval dialog both
directly and inside the wrapper, and the human route returned the same
fixed-closed answer both ways. No code changes. Since v0.4.20 a blocked
text-mode `--approve` prints its reason codes, so the client's next
occurrence carries its own diagnosis.

## Carried rows revalidated

LR-02 (source-property backfill), LR-03 (identifier-like title proposals),
LR-04 (locator, anchor and markup outcomes), LR-05 (already captured object
linking) and LR-07 (filename/metadata lookup, paired original/derived intake,
display projection) were revalidated at this release against their existing
domain cohorts; the acceptance register records the counts. They stay open
for client closure, which only a client run can provide.

## Not in this release

Session integration of the 29 remaining pending writer paths (LR-06 beyond
create-draft), MCP exposure of the create-draft session refs, and the
session-scope pre-approval of letter 161 (held for the maintainer's decision)
carry to v0.4.24 and later.

## Compatibility and privacy

- Existing controls, approvals, receipts and schema ids keep their exact
  bytes and validators; the `bytes` basis, the receipt's session attribution
  pair and the result's `work_session` block are additive.
- No label, reviewer id, path, source text or archive content is introduced
  into results, receipts, tests or release artifacts; the session scope is a
  digest over content-free refs.

## Verification boundary

The release candidate must pass the focused fidelity, session, approval,
privacy, package-resource, installed-wheel and full supported-platform CI
checks. The exact reviewed merge commit must be tagged, and the public wheel
must be downloaded anonymously, rehashed, installed in a fresh CPython 3.12
environment and checked in a new process. Those steps prove the public
artifact; they do not prove any client result.
