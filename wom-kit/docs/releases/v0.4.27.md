# WOM-kit v0.4.27 — Client Follow-Ups From The v0.4.25 Run

v0.4.27 answers the small requests in the client's 2026-09-18 v0.4.25
success report. The archive-root recovery and update of v0.4.25 worked on
the client's project and the session permission mode cut eleven writes to
two dialogs; what remained were rough edges around messages and inputs. No
approval contract, plan digest, receipt schema or journal schema changes.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.27-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0427-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.27/wom_kit-0.4.27-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.27` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## What changes

1. **Usage refusals name their code.** `project-version-update --approve`
   without `--affirm-external-writers-quiescent`, `--target` or
   `--reviewed-by` stops at stage `starting` with a bare usage error; the
   redacted diagnostics artifact and stderr now carry it as `cause_code`
   (`project_version_update_quiescence_required`,
   `..._target_required`, `..._reviewer_required`,
   `..._abandon_requires_resume`) with `cause_stage: starting`. The v0.4.25
   reply draft had omitted the quiescence flag from its approve command; the
   maintainer's error, corrected in the reply.
2. **A file-installed bootstrap is told what to do.** When the running
   distribution is not the verified public wheel (a bootstrap installed with
   `pip install <local .whl>`), the blocked result's `next_safe_actions`
   say to reinstall from the exact public release URL and rerun the dry-run
   from that bootstrap; the blocker
   `project_runtime_exact_public_wheel_required` is unchanged.
3. **A refused permission grant says what was wrong.**
   `work_session_permission_operation_not_grantable` now comes with
   `reason_detail`: the position of the refused entry
   (`rejected_operation_index`), the fixed list of grantable operation names
   and the fixed list of always-dialog names. The refused value itself is
   never echoed (`discard_draft` was typed; the grantable name is
   `draft_discard`).
4. **A UTF-8 byte-order mark is not content.** `source-intake-record`,
   `source-intake-batch` and `source-intake-chain` accept a plan or request
   file that PowerShell's `Out-File` wrote with a UTF-8 BOM; a UTF-16 or
   UTF-32 mark is named (`source_intake_record_plan_encoding_invalid`,
   `source_intake_batch_request_encoding_invalid`) instead of
   `..._invalid`.
5. **Discard previews put `plan_sha256` where every other preview does.**
   `discard-draft --dry-run` and `discard-draft-restore --dry-run` expose
   `plan_sha256` at the top level as well as under `summary`; the value is
   the same and `summary.plan_sha256` stays.

The "대상 자세히 보기" failure the report also mentions is fixed by v0.4.26
and included here. The index-rebuild block after several intakes is asked
back with the client's exact sequence rather than changed blindly.

## Compatibility and privacy

- Existing plans, claims, receipts, journals and schema ids keep their exact
  bytes and validators; `reason_detail`, the top-level `plan_sha256` and the
  two encoding codes are additive.
- No path, label, reviewer id, request value or archive content is
  introduced into results, diagnostics, tests or release artifacts.

## Verification boundary

The release candidate must pass the focused session, intake, discard,
approval, privacy, package-resource, installed-wheel and full
supported-platform CI checks. The exact reviewed merge commit must be tagged,
and the public wheel must be downloaded anonymously, rehashed, installed in
a fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result.
