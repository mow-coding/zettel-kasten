# WOM-kit v0.3.280

v0.3.280 adds a read-only plan for an explicit set of canonical zets that a
human has selected as members of one event.

## Added

- `archive activity-group-membership-plan <archive-root> --request
  .wom-scratch/private/activity-groups/<reviewed>.json --dry-run --progress
  --format json`
- alias `event-group-membership-plan`
- request schema `wom-kit/activity-group-membership-request/v0.1`
- plan schema `wom-kit/activity-group-membership-plan/v0.1`
- AI action-routing schema `wom-kit/ai-command-path-routing/v0.3` with the
  official event-membership planning route and an explicit unimplemented
  writer/removal route that forbids direct canonical edits
- `event_start` and `event_end` in the base facet vocabulary
- navigation-facet interpretation for `activity_group`, `event_start`, and
  `event_end`

## Event contract

One canonical `record_note` is the event anchor. Its zettel id is the group
identifier, its title is the event name, and its facets declare
`record_type: event` plus an ISO 8601 `event_start` and optional compatible
`event_end`.

Member zets use `facets.activity_group`. A scalar represents one event; a list
supports more than one.

Membership is neutral co-membership. It does not imply sequence, continuation,
source, derivation, or containment.

## Safety

The plan validates only ids explicitly supplied in the private request. It
does not infer members from search results, titles, dates, or nearby records.
Each id must resolve through its standard `zettels/<id>.md` canonical path;
the command does not scan unrelated zet frontmatter as a fallback.
Duplicate JSON request keys and duplicate YAML frontmatter mapping keys fail
closed instead of selecting one ambiguous value.

It is bounded to a 2 MiB request, 5,000 members, 16 MiB per canonical file, and
256 MiB total canonical bytes. It returns row indexes, state buckets, blocker
codes, and hashes without returning request paths, zettel ids, zettel paths,
titles, facet values, or body text.

The command writes nothing and calls no model, provider, network, index,
database, or credential store.

## Deferred

v0.3.280 does not write or remove memberships. The future writer must require
human approval, bind exact request and plan evidence, revalidate live bytes,
use a lock and journal, write an immutable receipt, and provide recovery.
