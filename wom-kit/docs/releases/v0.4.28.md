# WOM-kit v0.4.28 — Object-Storage Restore (OB-01 / OB-03)

v0.4.28 builds the first half of the long-requested "upload the originals,
then free local disk" feature: the way back. `archive object-storage-restore`
downloads WOM-verified remote objet bytes into the local objet store only when
a full authenticated GET reproduces the object id, never overwriting a local
file and never deleting the remote object; `--verify-only` records the same
proof without writing local bytes. The 2026-09-04 decision log (decision 6)
and the acceptance rows OB-01/OB-02/OB-03 had scheduled this for v0.4.23; the
v0.4.22 through v0.4.27 hotfix train pushed it aside, and the register now
says so. The offload writer itself (OB-02, removing local bytes after that
proof) is the v0.4.29 scope; its manifest state is decided here and already
read by this release.

Publishing or installing this release does not read or modify a client
archive. A client chooses when to run the exact public bootstrap and one
reviewed `project-version-update` to the public wheel
`wom_kit-0.4.28-py3-none-any.whl`. The release is not evidence that a client
result was repaired; that requires the client-run result and a new-process
verification.

## Conditional public artifact contract

Use this bootstrap only after the exact GitHub Release exists and lists the
wheel. The versioned URL alone is not proof that the asset is public.

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0428-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.28/wom_kit-0.4.28-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.28` from a new process. Installing this external
bootstrap does not replace a shared PATH tool or silently update any project.

## What changes

1. **`object-storage-restore` (alias `objet-storage-restore`).** Dry-run
   scans `objects/manifests/files.jsonl` once, hashes any local candidate,
   calls no provider, reads no credential value and echoes counts and
   `plan_sha256` only. Candidates are objects with a WOM-verified
   `wom_uploaded` location for the requested `--provider-kind` /
   `--store-ref` (or a v0.4.13 `bytes_preserved` / `already_remote_verified`
   preservation receipt for that store) whose canonical
   `objects/sha256/<2>/<64>` file is absent or whose local location is
   `offloaded`. A local file that already reproduces the object id is
   `already_present`; one that does not is a `local_conflict` and is never
   touched. `declared_uploaded` claims are never restored from.
2. **One dialog, one GET per object, two hashes before the bytes count.**
   `--approve --reviewed-by <id> --expected-manifest-sha256 <plan_sha256>`
   opens one native dialog (`오브제 원격 바이트 되찾기`, always-dialog, never
   grantable to a session permission mode) with the count-first target list.
   Credential values are read only inside the approved write. Each remote
   body is streamed into a private create-only sink under
   `profiles/local/exact-operations/restore-sinks/`, kept only when its byte
   count equals `size_bytes` and its sha256 equals the object id, re-hashed
   from disk, moved no-replace into the objet store, and the destination is
   re-hashed once more. One immutable receipt per object
   (`receipts/providers/object-storage-restore/`, schema
   `wom-kit/object-storage-restore-receipt/v0.1`: `bytes_restored`,
   `already_present_verified`, `remote_verified`, or `review_required` with
   `remote_absent` / `remote_size_mismatch` / `remote_checksum_mismatch`),
   then one manifest projection that adds or reactivates the local location
   for restored objects only. A corrupt or absent remote copy never blocks
   the other objects; a transport failure leaves the item resumable with
   `--resume-approval-id` / `--resume-execution-sha256`, and a finished
   object is never downloaded twice.
3. **`--verify-only` is the OB-01 general proof.** The same full GET and
   receipt for every WOM-verified remote object of the store, without
   writing local bytes or touching the manifest; bound it with `--only` and
   `--max-objects` because it costs a full download per object.
4. **The transport gains one primitive and one timeout.**
   `ObjectStorageTransport.get_object(key, sink_path, expected_size,
   expected_sha256)` streams a GET into a sink through the sole live egress;
   only the restore passes the two sink keywords, so every existing
   HEAD/PUT/multipart/verification GET keeps the five-keyword injected-sender
   contract. A 120 s per-operation socket idle timeout now applies to every
   object-storage HTTP call, so a silent socket is a retryable transport
   error instead of a hang; a slow but progressing transfer is never cut.
5. **`resolve-objet-ref` names the way back.** An object with a WOM-verified
   remote location and no local bytes resolves to
   `remote_verified_local_absent`, carries `restore_workflow:
   "object-storage-restore"` and a `next_safe_actions` line; each external
   candidate reports `remote_verified_by_wom_kit`. Declared-only objects
   stay `external_declared`.
6. **Never.** No `PutObject`, no `DeleteObject` (unreachable from the restore
   module), no overwrite of an existing local file, no presigned URL, no
   provider body, URL, key or path in any result or receipt.

## Compatibility and privacy

- Existing plans, claims, receipts, journals and schema ids keep their exact
  bytes and validators. New: the receipt schema
  `object-storage-restore-receipt-v0.1`, the approval kind
  `object_storage_bytes_restore`, the resolver state
  `remote_verified_local_absent` and the additive resolver keys.
- The `offloaded` local-location availability (with `offload_receipt_ref`,
  `offloaded_at`) is decided for v0.4.29 and only read (and reactivated) by
  v0.4.28; no writer produces it yet.
- No path, label, reviewer id, remote key, URL or archive content is
  introduced into results, diagnostics, tests or release artifacts.

## Verification boundary

The release candidate must pass the focused object-storage, approval,
resolver, privacy, package-resource, installed-wheel and full
supported-platform CI checks. The exact reviewed merge commit must be tagged,
and the public wheel must be downloaded anonymously, rehashed, installed in
a fresh CPython 3.12 environment and checked in a new process. Those steps
prove the public artifact; they do not prove any client result. OB-01 and
OB-03 close for the client only on the client's own restore run.
