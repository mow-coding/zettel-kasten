# WOM-kit v0.4.55 — WOM's own byproducts are deleted

WOM itself, not the person or their AI, left files on the operator's PC with every update: a runtime for each version (35-50 MB), a bootstrap environment for each install under `%LOCALAPPDATA%\WOM` (40-56 MB), and an update result, handoff capsule and operation journal for each run. Nothing deleted them, and past 4096 journals the update's delivery scan fails. Installing the tool alone does not change a customer archive; every write still goes through the reviewed approval path.

## Automatic pruning after an update

After a successful update whose result delivery was acknowledged, WOM deletes its own superseded project files: runtimes other than the pinned version and the one before it (each must carry WOM's runtime receipt; the running interpreter is never touched), and update results, handoff capsules and operation journals older than seven days beyond the newest few. A pending delivery, an update lock or an open update transaction keeps everything. The update result reports what was deleted under `system_cleanup`.

## system-cleanup

`archive system-cleanup <archive-root> --dry-run` lists what would be deleted by kind, with counts and bytes and never paths: the items above plus bootstrap environments in `%LOCALAPPDATA%\WOM` that are not newer than the pinned version, WOM temporary files and abandoned restore downloads older than a day, and archive operation results older than seven days. `--approve --reviewed-by <person:...> --expected-plan-sha256 <plan_sha256>` deletes exactly that plan in one approval (one window, or the session grant) and writes a content-free receipt. Receipts, approval claims, credential records, manifests, ledgers and locks are never deleted. Deleted items cannot be recovered; all are rebuildable or finished.

## Boundaries

Validated with a synthetic project holding every kind of byproduct, the CLI with an injected window, and a read-only plan against the developer PC's real `%LOCALAPPDATA%\WOM` (22 bootstrap environments, about 1 GB, found). Work-session registry generations and source-intake contexts also grow and need a format change; they are the next step. The customer's PC is not inspected.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0455-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.55/wom_kit-0.4.55-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.55` from a new process, then follow the reviewed `project-version-update` flow for an existing project. Bootstrap environments left by earlier installs are removed by `system-cleanup`.
