# v0.3.265 - Durable Abstract Batch Journals

v0.3.264 made each canonical zet write atomic and durable where the operating
system permits it. It deliberately left the next failure boundary open: an
approved abstract batch that edits several zets could stop between files, leaving
no durable record of the intended before/after states.

This release closes the evidence gap. It does not yet perform automatic
recovery.

## What Changed

Approved abstract apply and revert operations now publish a private transaction
journal before their first canonical mutation. The journal is created with the
same durable create-new writer used for receipts and binds:

- archive id;
- operation (`apply` or `revert`);
- exact proposal or source-receipt SHA-256;
- exact deterministic final receipt path;
- plan digest, reviewer, and required human affirmation;
- ordered participant ids and canonical paths;
- every participant's before, after, body, and abstract SHA-256.

The journal is schema-validated before it is written. When read back by the
audit, duplicate JSON keys, a wrong self-digest, a mismatched archive,
operation/basis/filename disagreement, a wrong final receipt path, duplicate
participants, unsafe or non-canonical paths, and equal before/after hashes all
make it invalid.

Apply locks and journals now use one shared digest namespace directly under
`.wom-scratch/abstract-backfill/`. Previously the lock lived beside the supplied
proposal path, so two byte-identical proposal copies in different nested
directories had different locks even though they targeted the same deterministic
receipt. If both ran, the process that lost the receipt-creation race could roll
the winner's canonical changes back. One proposal SHA now means one apply lock,
one journal, and one receipt regardless of proposal filename or nesting.

## What Happens At Each Interruption Point

The existing lock remains the concurrency brake. The order is:

```text
validate full batch
create lock
publish transaction journal
write and verify canonical participants
write and verify immutable receipt
remove journal
remove lock
```

A process stopped after the lock but before the journal has changed no canonical
zet. A process stopped after the journal can be diagnosed from the participant
hashes:

- `prepared`: every participant still has its before hash;
- `partially_applied`: some participants have before hashes and some after;
- `fully_applied_receipt_missing`: every participant has its after hash but the
  final receipt is absent;
- `divergent`: at least one participant is missing or has neither hash;
- `stale_completed`: the final receipt exists but cleanup did not finish.

The names describe evidence, not authority to modify the archive.

## Cleanup And Rollback

Normal success writes and verifies the final immutable receipt before it removes
the journal. The lock is removed only after the journal is gone. If journal
cleanup fails, both journal and lock remain and the command returns a warning.

A caught in-process exception still attempts the existing byte-for-byte rollback.
It removes the journal and lock only when every attempted canonical participant
was verified restored and any partial receipt was removed. If either check
fails, the journal and lock remain so the evidence is not destroyed to make the
command look clean.

## Privacy Boundary

The journal stores no abstract text and no body text. It does store private zet
ids, archive-relative paths, and reviewer identity because later recovery must
know the exact participants and authority basis. For that reason it remains
under the private `.wom-scratch/abstract-backfill/` working area.

The archive-wide audit reads that private metadata and canonical bytes for hash
validation but emits only operation, state, participant counts, and fixed issue
codes. It does not emit journal or receipt paths, zet ids or paths, reviewer,
body or abstract text, journal digest, proposal filename, or absolute local
paths.

The journal digest detects inconsistent or accidentally damaged content. It is
not a signature and does not prove who created the file.

## Compatibility And Migration

- No existing archive, zet, index, or receipt needs migration.
- No new operator command or approval flag is required.
- The existing apply/revert JSON results add transaction-journal evidence, and
  the receipt audit adds journal counters and problem states.
- New apply/revert receipts set the existing
  `crash_recovery_journal_written` field to `true`. The shipped v0.1 receipt
  schemas now accept both the historical `false` and new `true` value, so
  v0.3.265 verifies old receipts without rewriting them.
- The new journal schema is packaged in the wheel. Journals are created only by
  approved operations run with v0.3.265 or later.

## Limits, Stated Rather Than Implied

- **No automatic recovery.** The command and audit do not resume, finish,
  finalize a receipt, or roll back an interrupted batch. Retain the journal and
  lock for a later recovery release or manual forensic review.
- **One batch family only.** The journal covers abstract backfill apply and
  revert. Other multi-zet mutation paths do not inherit it.
- **No external-editor lock.** The private lock coordinates cooperating WOM
  operations for the same basis. Another program can still edit a participant;
  the audit then reports `divergent`.
- **No cross-basis participant lock.** One proposal SHA, or one revert source
  receipt SHA, has one lock. Two different bases that happen to name overlapping
  zets are not serialized by participant set. Immediate hash checks and the
  receipt lifecycle expose many resulting drifts, but basis-scoped journals do
  not make every cross-basis race detectable because a completely caught
  rollback removes its own journal. Global/per-participant arbitration is a
  separate concurrency design.
- **Windows power-loss durability remains limited.** File creation and canonical
  replacement are atomic, but Windows cannot perform the directory `fsync` used
  on POSIX. A process kill is covered by the journal tests; a sudden Windows
  power loss can still lose the newest directory entry.
- **The journal is consistency evidence, not authentication.** Someone able to
  edit private archive files can also recompute its digest.

## Verification

Regression coverage includes:

- successful apply and revert create the journal before mutation, record
  `crash_recovery_journal_written: true`, and remove journal plus lock only after
  the receipt verifies;
- journal creation failure blocks before any canonical write;
- child processes use `os._exit` immediately after the first apply and first
  revert mutation, leaving a real partial batch that the audit classifies;
- the apply hard-exit fixture places its proposal several directories below
  `.wom-scratch/abstract-backfill/`, proving its lock/journal still use the
  shared digest namespace and the audit finds both;
- byte-identical proposal copies in two nested directories contend on the same
  digest lock and the loser performs zero canonical write attempts;
- journal-create failure releases the just-created apply/revert lock before
  returning without a canonical write;
- caught runtime failures remove evidence after a complete verified rollback;
- incomplete apply and incomplete revert rollbacks retain journal plus lock;
- an externally created deterministic final receipt is never claimed as removed:
  canonical bytes are restored, the external file is preserved, rollback is
  reported incomplete, and journal plus lock remain;
- prepared, partial, fully-applied-without-receipt, divergent, completed-residue,
  invalid-name, wrong-receipt-binding, and ambiguous-participant states for
  apply and revert;
- completed residue is a warning only after the final receipt lifecycle verifies;
  an empty or invalid receipt remains a blocker rather than hiding journal or
  lock state;
- no body, abstract, zet id/path, reviewer, journal digest, proposal filename, or
  absolute path is echoed by the audit.
