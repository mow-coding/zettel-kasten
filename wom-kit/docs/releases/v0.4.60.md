# WOM-kit v0.4.60 — the last cleanup item, letter revisions, and Git status

This release answers the v0.4.59 follow-up in beta letter 180. On v0.4.59 the customer's reconcile ran in about 94 seconds instead of 61 minutes and finished item B, but item A remained. They also found a defect in revising a letter, a stale Git status at session start, and Git runs with no time breakdown. Installing the tool alone does not change a customer archive.

## Item A: an upload started long ago that could not resume

The v0.4.58 tests cut the upload *after* the remote write, where checking the remote copy completes the item. This case is different, and it is now reproduced with the real CLI:

- the upload's approval claim started;
- the process stopped *before* anything was written remotely;
- the object's manifest row changed afterwards, for example through a later version or a second file with the same bytes.

The original upload then failed its own precondition every time and showed only `exact_human_approval_state_unknown`.

Now, the upload runs again under the reconcile approval when all three hold:

- the original upload cannot resume;
- the remote copy is absent;
- the local object still has exactly the right bytes.

The old claim is closed as failed, never as succeeded, and the full remote bytes are checked afterwards. In any other case the file is kept.

`--reconcile --dry-run` now shows `original_resume_check` and the route `upload_complete_after_remote_proof_or_upload_again_from_local_bytes`.

## Revising a letter

An approved `operator-feedback-compose --intent revise` rewrote the letter but left its record pointing at the old text. Body-check then blocked with no next step.

Now:

- the same approval also moves the draft record to the new text (`draft_record_update`), and the letter stays "전달 전";
- if the record still points at older text, body-check names the exact record update command.

## Git status at session start

After WOM's own Git backup had pushed and verified commits, the session-start notice still called them "not pushed" and the remote "11 days old". The backup pushes to the remote's address directly, so Git never updated its local copy of the remote branch, and that copy is what the notice reads. A verified push now updates it, as a normal `git push` does. The notice also says that its numbers come from that local copy, not a live check.

## Where Git time goes

`git-backup-plan` and the approved Git backup now return `work_timing`, with the time split into categories that do not overlap:

- remote transport
- local Git processes
- snapshot
- receipt inventory
- changed-file hashing
- staging proof
- push and requery

## Boundaries

The exact change to item A's manifest row on the customer's PC is not confirmed; the reproduction covers the failure class. The customer's own run is not verified.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0460-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.60/wom_kit-0.4.60-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.60` from a new process, then follow the reviewed `project-version-update` flow for an existing project.
