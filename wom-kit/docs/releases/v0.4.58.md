# WOM-kit v0.4.58 — the two cleanup items that never finished

This release answers beta letter 180, sent from v0.4.56. An `activity-cleanup --reconcile` ran about 61 minutes and finished 51 of 53 remaining items, but the same two items as in letters 174 and 179 stayed. Both conditions were reproduced with the real CLI on Windows and are now recovered by the official reconcile. Installing the tool alone does not change a customer archive.

## The two items

- **A — upload finished, claim left open.** When the remote copy of the object is fully verified, the reconcile treats the upload as done, closes the old child claim as failed (never as succeeded) and continues.
- **B — offload started, control file never written.** The reconcile no longer tries to rebuild the original plan, which could never match because the archive had changed. It works by case:
  - If the offload claim succeeded, the item completes after the remote proof.
  - If the local bytes are provably untouched, the offload runs again under the new approval.
  - Otherwise the file is kept with `activity_cleanup_child_control_missing_effects_unproven`.
- **Read-only diagnosis.** `--reconcile --dry-run` now shows `pending_item_diagnosis`: the step each unfinished item reached, whether its child control file and claims exist, and the route the approved run will take. It contains no paths and makes no remote requests.
- **Clearer failures.** A failed item names its child step and cause code.
- **Repeat approvals.** Approving the same reconcile again no longer conflicts.

## Also

- **Recovery plans.** `operation-control --action recovery-plan` for activity-cleanup shows that command's state, counts and next steps instead of the index-health text. Other storage commands get their own guidance. `command_outcome` says separately whether the command succeeded.
- **Progress display.** The heartbeat no longer dies on a non-number progress value. Display failures are reported in `progress_reporting`, apart from the result.
- **Speed.** Each cleanup item no longer recomputes the archive-wide storage cost estimate. That estimate is display-only and took about half of each item's time on a large synthetic archive.

## Boundaries

The customer's own run and the original cause of their two interrupted steps are not confirmed. The deeper performance work follows in v0.4.59: index projection, manifest parsing, separate timings and an ETA that leaves out skipped items.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0458-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.58/wom_kit-0.4.58-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.58` from a new process, then follow the reviewed `project-version-update` flow for an existing project.
