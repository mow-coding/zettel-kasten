# v0.3.264 - Durable Canonical Writes

A canonical zet overwritten during a forced shutdown could be left half-written.
That gap was split out of the v0.3.257 batch and deferred twice. This release
closes it, and closes the two smaller holes that closing it exposed.

## What Changed

- `write_text_atomic` now creates the parent directory, writes to a hidden
  `.{name}.{random}.tmp` temp file, flushes, `fsync`s, and replaces. It
  previously renamed without any flush, so a rename could become durable while
  the data behind it was not.
- **Both** writers now retry the rename. Windows `MoveFileEx` refuses to replace
  a file anyone holds open, so a virus scanner or search indexer reading a zet
  failed the write outright. The retry is bounded, backs off, retries only
  `PermissionError`, and re-raises afterwards.
- The directory entry is flushed after the rename, so the rename itself is
  durable and not only atomic. POSIX only — see the limits below.
- `write_json_new_file`, which writes every receipt, now flushes and `fsync`s.
- `zettel_edge_write`, `zettel_edge_revert`, `restore_zettel_edge_batch_snapshots`,
  `create_draft_zettel`, and the operational-context write route through the
  atomic writers instead of overwriting a file in place.

## What Was Not True In The First Draft

Three claims in this release's first implementation were wrong, and a pre-release
review caught all three. They are recorded because the corrections are the
substance of the release.

**The byte writer this release "fixed" was dead code.** `archive_services.py`
defined `write_bytes_atomic` twice; the later definition shadowed the earlier one,
so the edited function never executed and the 15 byte-writing call sites —
including the abstract backfill write and the revision apply and revert paths,
which this release's own notes named as flagship examples — inherited nothing.
The dead definition is removed. The live one already reserved its temp with
`O_EXCL` and already `fsync`ed; what it actually lacked was the retried rename and
the parent-directory creation, and it now has both. The lesson is recorded in the
decision log: in an 86,000-line module, "I edited the function" is not evidence
that the function runs. Two regressions now enforce this: an AST sweep asserting no top-level name in
`archive_services.py` is defined twice, and a check that each writer binds to the
definition the source file actually contains.

**A unique temp name did not fix the concurrent-writer race.** It removed the
*temp file* collision, but the contended resource was the *destination*. With
unique temps in place, `os.replace` still failed in roughly five runs out of six.
The retry is what fixes it; measured after the change, ten runs of the same race,
zero failures.

**Making the zet durable without the receipt made things worse.** The canonical
zet became durable while the receipt proving the mutation stayed in the page
cache. That converts a symmetric loss — both gone, archive consistent — into an
asymmetric one: the archive changed and nothing records why. Receipts are now
durable too.

## Byte-Neutral By Construction

The text temp file is opened with `encoding="utf-8"` and **no** `newline`
argument, so output is byte-identical to before, platform newline translation
included. A regression asserts that against a plain `Path.write_text`, and
against `Path.write_bytes` for raw bytes. It is a no-change guard, not evidence
that anything was fixed -- it passes against the previous writer too, which is
the point -- and it pins the translation explicitly so it also bites on POSIX,
where `os.linesep` makes a naive comparison vacuous.

Making canonical writes durable and making canonical bytes identical across
platforms are two decisions, and only the first is in this release. The project
already anticipates newline drift: `bytes_normalized_for_content_compare` folds
BOM and CRLF/CR to LF and is the one normalized-equality definition reused by
reconcile, the doctor format-drift branch, and retire's snapshot tolerance, and
its docstring states the raw sha mismatch is intended so drift stays visible.

## Limits, Stated Rather Than Implied

- **Windows gets atomicity, not durability.** Windows cannot open a directory to
  flush it, so the directory-entry flush is POSIX-only and fails soft. On Windows
  a power cut immediately after a successful write can still leave the previous
  content. It can never leave a torn file.
- **Every write now costs one extra disk flush.** Measured locally: roughly
  +1 to +2 ms per write versus the previous writer on NVMe, hardware dependent, and materially more on
  spinning or network storage. The one place this is felt is a bulk frontmatter
  migration, which issues one flush per changed zet with no batching. That is the
  price of not losing a zet, and it is paid per write.

## Compatibility And Migration

- No archive, zettel, index, receipt, or schema migration is required.
- No command changes its output shape or its success/failure result. No file
  content changes.
- Two mechanical changes are worth naming: a write to a missing parent directory
  now creates it rather than failing, and a locked destination is retried briefly
  before the same error surfaces.
- An atomically replaced file is a new inode, so hard links to a canonical zet
  are not preserved and the file takes fresh default permissions. Replacing
  rather than following also means a symlinked zet is replaced, which closes a
  write-through-symlink path the module's own comments flag.
- Interrupted temp files are not swept. They are hidden dotfiles named
  `.{name}.{random}.tmp`; deleting files next to a canonical zet on a name
  pattern is a bigger decision than this release earns.

## What This Release Deliberately Does Not Do

It does not add a resume record for an interrupted multi-zet batch. When a write
that edits several zets stops partway, nothing records how far it got, so the
operator can neither resume nor revert cleanly. That is the second half of the
same deferred work, it needs its own design, and it is a prerequisite for any
approved write rung in the title remap ladder.

It does not batch the new flushes, and it does not make canonical bytes
platform-independent.

## Provenance And Verification

Local verification covers the reproduced concurrent-writer race, byte-identity
against a plain write for both text and raw bytes, parent-directory creation with
no temp file left behind, and a guard asserting that an approved edge write never
opens a canonical zet through any truncating path — `write_text`, `write_bytes`,
or `open` in a write, append, or update mode — alongside the full WOM-kit suite,
the four hygiene checkers, and packaged resource synchronization.
