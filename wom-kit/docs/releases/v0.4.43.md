# WOM-kit v0.4.43 — Project update approval hotfix

A beta tester's v0.4.38 to v0.4.42 project update stopped at the approval step. The official `--resume` and `--resume --abandon-started-approval` stopped the same way. The update lock stayed, so every new work session was refused with `project_update_recovery_required`. This release fixes the cause and the stranding. Installing the tool alone does not change a customer archive; use the reviewed `project-version-update` flow for a project.

## What went wrong

- `--reviewed-by` accepted a bare actor id such as `alex`, but the approval context accepted only `person:<id>` or `human:<id>`. The reviewed plan therefore failed while the approval context was built, before any window opened, with `exact_human_approval_context_invalid`. A resume rebuilt the same context and failed the same way.
- The failure reached the result only as an exception family (`project_version_update_failure_family_windows_approval_error`), so the tester's AI could not tell which check failed.
- Only a human cancel released the reserved update, so the lock stayed behind.

## Fixed

- A bare reviewer id is read as `person:<id>` everywhere an approval context is built. Other kinds, such as `agent:`, are still refused.
- A failure while the approval context or its binding is built releases the reserved update and its lock. No window was opened and no claim exists at that point.
- The result names the fixed approval sub-code and stage, for example `exact_human_approval_context_invalid` at `native-approval`. Before, it showed only the family.
- A crash on one `--resume` path of a cancelled legacy update (an undefined key provider) is fixed.

## If your update is stuck

With this version's bootstrap, run `project-version-update <project-root> --resume --affirm-external-writers-quiescent`. Because the stopped attempt never reached the approval window, no approval claim exists, and the resume closes it without any project change (`preapproval_scaffold_cancelled`) and releases the lock; `--abandon-started-approval` ends the same way. Then run the update again: `--dry-run`, then `--approve --reviewed-by person:<you>` (a bare name now works too). Check the source, pin and runtime from a new process. Do not delete lock files by hand.

Validation used synthetic data and a simulated approval; the customer's own update and resume must be confirmed separately.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0443-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.43/wom_kit-0.4.43-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.43` from a new process, then follow the reviewed `project-version-update` flow for an existing project. A bootstrap installation alone does not update its pinned runtime.
