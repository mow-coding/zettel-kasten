# WOM-kit v0.4.0 — Exact Human Control And Operator Friction

v0.4.0 opens the custom human-control line with one narrow rule: an actor
label, an AI assertion, or `--approve` alone is not authority for a high-impact
archive write. Supported single operations now require a native Windows review
of the exact content-free operation binding, followed by one authenticated and
durable claim before the writer can run.

## Exact human approval

The local approval sequence is fixed:

```text
dry-run and exact binding
-> native Windows TaskDialog
-> authenticated durable claim in started state
-> writer re-derives and checks the same binding
-> workflow finalizes only a well-formed successful result as succeeded
```

There is no separately issued approval receipt with a time-to-live. A claim is
one-use and does not expire. The workflow publishes it in `started` state
immediately after the human confirms the live dialog and before the writer
runs. The workflow is the only finalization owner. Any writer-level
non-success, including a well-formed `ok: false`, exception, malformed result,
interruption, partial durable effect, or finalization ambiguity leaves
`started`; the fixed `approval_claim_reconciliation_required` result requires
reconciliation and must not be retried automatically. This prevents a
canonical write or immutable receipt followed by an index/update failure from
being falsely recorded as a clean failed approval.

The dialog shows only safe operation, archive-identity, plan, target-set,
warning-set, and checklist bindings. It never shows or records document text,
titles, labels, paths, source locators, provider values, credentials, or raw
exceptions. Test-only synthetic intent cannot issue live authority. Non-Windows
hosts and native dialog ambiguity fail closed before a claim is created.
The Windows Python host must provide a Comctl32 v6 activation context;
Microsoft documents `TaskDialogIndirect` as requiring
[Comctl32.dll version 6](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-taskdialogindirect).
The runtime calls `DllGetVersion` immediately before constructing the dialog
and requires Comctl32 major version 6 or newer. Missing, older, or unverifiable
activation returns `exact_human_approval_activation_context_required` before
dialog display and before claim creation.

The exact boundary now covers supported single-operation routes for:

- AI-assisted draft creation and private source-fidelity session evidence;
- mint, promotion, one zettel-edge write, and one draft retirement;
- warning-bearing promotion through a separately bound warning override;
- private human-artifact root registration and lifecycle transition;
- byte-identical duplicate object-manifest reconciliation; and
- append-only approval-integrity overlay repair.

Every writer re-derives the operation-specific plan and target binding directly
before its first mutation. Drift after the dialog therefore fails before the
write. MCP may expose the matching read-only plans, scans, and audits, but it
cannot perform a local exact-human write or accept caller-supplied approval.

## Approval links and integrity

Operation receipts that can safely carry the exact-human reference do so
directly. Strict historical source-fidelity evidence stays immutable and uses
a separate create-only, HMAC-authenticated approval-link receipt. A link is
valid only with its archive authentication key, its matching authenticated
`succeeded` claim, and exact source-operation receipt bytes.

Only `effect=created` proves that the approved invocation created the original
effect. `effect=already_present_exact` records a later exact review without
rewriting or silently upgrading history.

`approval-integrity-audit` classifies a bounded receipt set without reading
artifact bodies. `approval-integrity-guard` checks one opaque affected target.
`approval-integrity-overlay --dry-run|--approve` can append a reviewed
quarantine, supplementation, withdrawal, or repair state. It never edits the
historical receipt or canonical artifact to manufacture cleaner history.

## Human artifacts and duplicate objects

The earlier human-artifact surface preview remains read-only. v0.4.0 adds a
private registry around explicitly selected external roots:

- `human-artifact-register-root --dry-run|--approve` binds exactly one root as
  `external_project` (scan only `<root>/.wom-scratch`) or `external_delivery`
  (scan the reviewed root itself);
- `human-artifact-scan` performs bounded metadata-only discovery and never
  opens artifact bodies; and
- `human-artifact-transition --dry-run|--approve` appends one reviewed
  lifecycle receipt without changing or deleting the artifact.

The provider-neutral registry does not start OAuth, call a note service,
publish content, or make an external application authoritative for WOM. It
never auto-scans Downloads or a home directory. Only an exact-human-approved
registration contributes scan and closeout authority.

`duplicate-object-reconcile --dry-run` distinguishes byte-identical repeated
manifest rows from identity conflicts. Approval may remove only unchanged,
byte-identical repeats and writes an immutable reconciliation receipt. A
conflict, manifest drift, missing authentication key, or incomplete exact
approval remains blocked.

## Source fidelity and everyday operation

Private session evidence can now be approved as exact bytes with producer,
role, time, and optional input-provenance bindings. The receipt remains
content-free, and source paths and raw session references are not returned.
AI draft creation carries an authenticated exact-human approval link after the
source-fidelity receipt is verified.

The CLI also adds read-only facet vocabulary discovery; clearer archive-root,
project-scratch, operator-feedback request, and generated-index recovery
guidance; approval-handoff lookup; replay identity; and explicit instruction-
conflict policy. These changes reduce guesswork without searching unrelated
folders, reading private feedback prose, or turning an index miss into a global
absence claim.

## Letter 138 data-integrity scope guard

Historical Notion typed-property loss detection and backfill are not part of
v0.4.0. The current Notion recovery surfaces recover page bodies or locations;
they are not a complete source mirror and do not prove typed-property
preservation. A read-only loss audit and an exact-approved, idempotent backfill
are an urgent follow-on release track.

## Packaged Python authority boundary

The command boundary is also enforced at the packaged-module layer. Concrete
claim minting, authentication-key retrieval, native credential access,
credential/provider brokers, lifecycle and evidence committers, recovery
storage/execution, Tiro and Notion network calls, and object-storage transport
engines are private implementation details. Their former public module names
and exports are absent in v0.4.0, and production reaches them only behind the
operation-specific exact workflow, the real first-enrollment/replacement popup,
or an already fixed-closed public wrapper.

Public callers retain content-free plans, safe projections, schema validation,
and read-only audits. Constructing a digest document, reviewer label, callback,
synthetic native object, caller key, or injected adapter cannot mint live
authority. Private cores remain directly testable by explicit underscore names
so atomicity, retry, rollback, and tamper invariants are not replaced by
blocker-only tests; those test seams are not supported public execution APIs.

## Standards boundary

The native confirmation follows the Windows `TaskDialogIndirect` platform
contract rather than a terminal prompt:
[Microsoft TaskDialogIndirect](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-taskdialogindirect).
The one-use, replay-resistant, verifier-bound design is also consistent with
the general authentication principles in
[NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html), without
claiming that a desktop confirmation identifies a legal person or implements
the complete NIST standard.

## Evidence and release boundary

Local tests, schema validation, source resource synchronization, and a built
wheel are implementation evidence only. They do not prove merge, required
external CI, the exact annotated tag, GitHub Release publication, anonymous
download, fresh installation, live provider behavior, real native human
acceptance, or a real-archive repair.

Install only after the exact v0.4.0 GitHub Release exists and lists the verified
`wom_kit-0.4.0-py3-none-any.whl`:

uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.0/wom_kit-0.4.0-py3-none-any.whl"
