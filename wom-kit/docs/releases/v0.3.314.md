# WOM-kit v0.3.314

Letter 126 long-operation recovery and generated-index inspectability.

Status: v0.3.314 implementation and release scope. The source implementation
and local tests may be complete in this worktree, but this note does not prove
merge, external CI, exact tag, GitHub Release, packaged wheel publication,
fresh installation, real-archive execution, provider behavior, or human
acceptance.

## Project update performance

- Complete target-tree materialization now uses one bounded
  `git cat-file --batch` stream per tree instead of one Git child for every
  file.
- The reproduced four-tree workload fell from 11,184 Git processes to eight:
  four `ls-tree` children plus four batch children. The four batch loads took
  2.538 seconds in the local controlled benchmark.
- Batch framing verifies the requested object id, `blob` type, declared size,
  computed Git object id, per-file and total byte caps, and exact stream
  termination. It keeps Git lazy fetch and replacements disabled.
- This is an implementation benchmark, not a guarantee for every disk,
  repository, antivirus configuration, or network approval path.

## Generated SQLite index

- Full rebuild and incremental writers now require the disposable generated
  index to use SQLite rollback `DELETE` mode.
- Public and private health checks reject a legacy WAL header, invalid header,
  or any `-wal`, `-shm`, or `-journal` sidecar before opening SQLite. The
  blocked result does not invent public row-difference claims.
- One ordinary explicit `archive index` rebuild converts a legacy generated
  cache and rebuilds the private projection in the same transaction. It does
  not migrate canonical zets, durable private authority, or the schema.
- `index-health` remains read-only except for an explicitly requested private
  diagnostic `--output` file. Operators must still quiesce unmanaged external
  SQLite writers; the preflight is not an operating-system-wide lock.

## Bounded operation control

When `project-version-update`, `index`, or `index-health` starts with a fresh
`--output`, stderr prints an opaque `operation_ref`. The complete saved result
also embeds that reference and follow-up command templates. A later process can
use the exact starting root and reference:

```text
archive operation-control <project-or-archive-root> --operation-ref op:sha256:<digest> --action status --dry-run --format json
archive operation-control <project-or-archive-root> --operation-ref op:sha256:<digest> --action wait --timeout-seconds 60 --dry-run --format json
archive operation-control <project-or-archive-root> --operation-ref op:sha256:<digest> --action recovery-plan --dry-run --format json
```

`wait` is bounded to 1 through 60 seconds. `deadline_reached` is not failure or
cancellation. A completed result is accepted only after its output binding,
size, SHA-256, and embedded operation/run/root/command/result/exit evidence are
revalidated. The content-free journal hash chain detects ordinary drift and
torn records; it is not a MAC, signature, authority receipt, or same-user
adversary boundary.

Cancel and resume are deliberately unsupported. Cancel always returns nonzero
`operation_cancel_not_supported` with `cancel_supported: false`,
`cancel_requested: false`, `resume_supported: false`, and `writes: false`.
There is no daemon, queue, background launcher, force kill, MCP method, lock
deletion, or automatic rollback.

## Upgrade

1. Install the exact v0.3.314 wheel only after the matching GitHub Release
   exists and lists it.
2. Start a new process and verify `archive version`.
3. Stop other archive/SQLite writers, then run one explicit `archive index`
   with a fresh `.wom-scratch/diagnostics/*.json` output.
4. Run a fresh `archive index-health --dry-run` with a different output file.
5. For future long project-update/index operations, retain the early
   `operation_ref`; after a caller timeout, inspect the same operation instead
   of starting a duplicate writer.
