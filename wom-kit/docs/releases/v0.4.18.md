# WOM-kit v0.4.18 — Terminal Original Cleanup For A Superseded Update

v0.4.18 closes the last dead end in the identifier-free
`project-version-update --resume` recovery loop. A completed transaction directory can outlive its own cleanup:
the predecessor updater wrote its cleanup plan inside the original directory
and then never renamed that directory to its tombstone, or a later resume
restored a complete tombstone and stopped before deleting it. If the project
then moved on to another version, every earlier release routed that directory
into approval-claim rediscovery, found no checkpoint-valid claim, tried to
cancel it as a pre-approval scaffold, and reported only a generic command
failure while the dry-run kept pointing back to `--resume`.

The public command surface is unchanged. The person still decides only whether
other writers for the same project are paused and whether to run a new
reviewed update afterwards. WOM verifies the journal, the plan, the tree, the
archive claim, and the cleanup; it asks for no transaction ref, approval id,
file count, digest, or private path.

Approved project-update mutation, same-version repair, and mutation-bearing
resume remain Windows-only. POSIX supports preview and read-only inspection;
those mutation paths fail closed without writing.

## One completed original whose project moved on

A transaction whose journal is exact, forward, and terminal (`completed`)
carries its approval reference digest on `approval_bound` and on every later
checkpoint. The predecessor cleanup plan names that same digest as its
cleanup authority. v0.4.18 classifies a still-present completed original as
`terminal_original_exact` only when all of the following hold read-only:

- no live project lock, and neither a tombstone nor a canonical proof exists
  for the same transaction;
- the transaction opens with full sealed-state verification and its journal
  is exact, forward, and terminal;
- a retained cleanup plan is present, is either the predecessor legacy schema
  or the current identity-bound schema bound to this exact directory, and
  names the journal approval reference as its cleanup authority; and
- the plan's file list and directories equal the current tree exactly.

A completed original that this contract does not own keeps its existing
route: a cancellation or rollback journal, a plan-less completed original, or
a current plan whose authority is a terminal-handoff digest still follows the
v0.4.16 replay and cancellation contracts unchanged. Only positive
contradicting evidence, such as a plan authority that is not the journal
reference, a member that differs from the plan, a directory identity drift, a
live lock, or a sibling tombstone or proof, becomes
`project_version_update_terminal_cleanup_outcome_unknown`.

## Read-only classification and parity

Fresh dry-run and approval reuse the same classifier. For
`terminal_original_exact` both return `terminal_cleanup_required` with
`project_version_update_terminal_cleanup_required`, the content-free basis
`exact_terminal_transaction_cleanup_requires_resume`, and
`terminal_transaction_cleanup_required: true`. Identifier-free `--resume`
recognizes the same shape, so the dry-run instruction is now one that resume
can actually finish. If the read-only inspection refuses, dry-run, approval,
and resume all report the same cleanup-outcome-unknown result instead of one
surface pointing at another.

## Claim-reference cleanup authority

When the live active pin still equals the transaction's post-image, resume
keeps the v0.4.16 contract: claim rediscovery, terminal handoff, and the bound
result. When the pin has moved on, that contract's live-component guard can
never pass again, so resume finishes only the private control cleanup. It
holds the project terminal guard from the final read-only observation through
cleanup, re-reads the archive claim store with the production key, and
requires exactly one MAC-verified `succeeded` claim whose public reference
digest reproduces the journal approval reference. No approval context is
rebuilt, no live component is classified, no key or claim is created, and no
domain writer, source, runtime, pin, or archive content is touched. The
retained plan is historical evidence; the authenticated claim is the
authority. If the generic route refuses through its fixed candidate-missing
gate while the pin still matches, the same cleanup runs as a fallback in the
same invocation.

The completed result is `terminal_transaction_cleanup_completed`. It reports
`update_completed: false`, `past_update_success_attributed: false`,
`fresh_approval_required: true`, `project_domain_effects: none`, an empty
project-domain `files_written` list with `files_written_scope:
project_domain_only`, `approval_key_accessed` and
`approval_claim_store_accessed` as true, one cleanup proof written, and the
content-free `cleanup_authority_basis`. A canonical proof produced this way
attributes nothing and grants no retry, cleanup, or fresh approval authority; a
new update still needs a new preview and one new exact approval.

## Re-entrant and fail-closed

The cleanup reuses the existing exact primitive: it writes the identity-bound
sidecar beside the legacy plan, moves the directory to a no-replace
tombstone, deletes only plan-bound members, and retains one proof. If the
rename fails after the sidecar is durable, the directory is still
`terminal_original_exact` and the next resume finishes it. If the process
stops after the rename, the tombstone is restored, re-classified, and finished
by the same route without claim rediscovery. An unverified authority, an
incomplete cleanup, or an observation that changed under the guard returns
`terminal_cleanup_outcome_unknown` with a fixed basis and preserves all
evidence. Off Windows, resume returns
`terminal_cleanup_platform_unsupported` with zero writes.

## Fixed inner reason in the redacted failure artifact

When the exact-human workflow masks a service failure as
`exact_human_approval_state_unknown`, the redacted `--output` artifact may now
carry a fixed inner `cause_code`, the fixed `cause_stage` that wrapped it, and
`cause_code_source: fixed_literal_allowlist`. Only a single-argument,
code-shaped service reason on the CLI allowlist qualifies; today that is
`project_version_update_preapproval_recovery_failed` at
`candidate_missing_handler`. Raw exception text, paths, values, and
identifiers are never copied, the public workflow code and the generic
`project_version_update_command_failed` blocker are unchanged, and stderr adds
one fixed line naming the same code.

## marker.json is an identity anchor

A transaction's `marker.json` keeps `state: reserved` for its whole life. It
is re-validated on every open as an identity anchor and is not a lifecycle
record. The verified prefix of `checkpoints.jsonl` is the authority for
progress: `completed:verified` with no remaining events means the transaction
is terminal, and the public summary reports `lifecycle: terminal`. A retained
cleanup plan, tombstone, or proof describes the cleanup stage, never success.

## Updater bootstrap contract

Install the exact public wheel only after the matching GitHub Release and
asset exist, using a dedicated external CPython 3.12 environment and its real
`python.exe -m pip`:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0418-$womBootstrapNonce"
if (Test-Path -LiteralPath $womBootstrapRoot) {
  throw "WOM bootstrap path must be new."
}
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.18/wom_kit-0.4.18-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require exactly `archive 0.4.18` from a new process. Publishing or installing
v0.4.18 does not inspect or modify a client archive, project source mirror,
runtime, launcher, version pin, credential, provider, or remote service. The
client chooses whether and when to run identifier-free recovery and one
reviewed project update; the person is not asked to count files, compare
hashes, or select private identifiers.
