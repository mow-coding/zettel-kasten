# WOM-kit v0.4.10 — Bounded Batch Intake and Capture

v0.4.10 turns the safe single-file intake path into a bounded batch pipeline.
WOM derives and checks the exact files, receipts, counts, hashes, and archive
identity. A person makes only two meaningful decisions: preserve this intake
batch, then capture the resulting local bytes.

## What changed

- **One reviewed intake batch needs one native decision.**
  `source-intake-batch` accepts 1–1,000 strictly validated items, creates each
  canonical intake receipt through `ExactOperationManifest v1`, and prepares
  the exact capture request in the same checkpointed operation. Duplicate
  physical files and sources that are not archive-relative are rejected before
  approval, so a successful batch always leaves both N receipts and one
  generated request. The native dialog says that the decision covers the whole
  reviewed batch rather than describing a single file. An interrupted intake
  resumes with the same unchanged manifest and reviewer through `--resume`;
  WOM authenticates the only unambiguous claim without asking the person to
  find an approval id, execution digest, or private receipt path.
- **The capture handoff is generated, not copied by hand.**
  The completed intake execution returns one content-free execution digest.
  `objet-capture-batch` uses that digest to derive the prepared request and
  revalidates the current request, intake receipts, staged bytes, archive
  identity, authenticated approval claim, checkpoint chain, and final receipt.
  A forged, copied, stale, incomplete, or cross-archive completion document
  grants no capture authority.
- **One reviewed capture batch needs one native decision.**
  The capture writer preserves the selected local bytes and publishes its
  existing per-item and batch evidence without adding a new top-level command.
  Its native dialog explicitly covers the verified batch, and that batch
  operation identity stays bound through the lower writer and durable receipt.
  It does not mint zets, infer links, publish drafts, call a provider, upload,
  or turn byte preservation into content approval.
- **Interrupted state is authenticated and project-scoped.**
  Intake checkpoints and succeeded completion evidence are HMAC-authenticated.
  Read-only reconciliation creates no lock, directory, or key. Publication is
  create-only, rechecks the approved canonical target, and reports an uncertain
  outcome truthfully if a write may have started. Both automatic and expert
  resume paths are blocked when the running WOM version does not match the
  target project's active version.
- **Capture recovery is deliberately fresh.**
  The existing capture service has no honest per-item external checkpoint
  boundary. After an interrupted or partial attempt, WOM therefore requires a
  fresh exact dry-run against current state and a new native decision. It does
  not automatically retry or claim same-approval resume. Existing verified
  bytes and manifest rows converge without duplication.
- **Batch planning no longer rereads the request for every item.**
  Synthetic Windows runs planned 508 items in 33.995 seconds and 1,000 items in
  42.926 seconds. The post-decision request reread stayed near 0.012 seconds;
  per-item revalidation took 31.505 seconds for 508 and 30.094 seconds for
  1,000. The request-read path is linear rather than quadratic. The CLI emits
  its first state before planning and a content-free heartbeat at least every
  10 seconds during long work.

## Deliberate limits

The remaining per-item Windows path, configuration, provider-metadata, and
manifest reconstruction cost is not presented as solved. Its caching and
profiling work is deferred to v0.4.11. This two-decision batch route accepts
only archive-relative local sources because it must always generate the exact
capture handoff. The v0.4.9 single-file metadata-intake route remains available
for a separately reviewed external source. Ambiguous, unmapped, or
weak-evidence links remain review work rather than automatic capture or
publication. Filesystems that cannot provide safe create-only hard-link
publication block instead of falling back to overwrite behavior; broader
generic exact-operation ancestor-handle portability remains future hardening.

## Client execution boundary

Publishing or installing v0.4.10 does not modify a client archive. Development
proved this release with synthetic archives and an isolated installed-wheel
three-file flow, and did not install it into or write recovery data for a
client archive. The client installs the verified wheel in that project's
isolated runtime, reviews the two plain-language decisions, and runs the
project-scoped commands.

## Install contract

After the matching GitHub Release exists and lists the wheel, install that exact
public artifact in the client's isolated tool or project runtime:

```powershell
uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.10/wom_kit-0.4.10-py3-none-any.whl"
archive --version
```

The new process must report exactly `archive 0.4.10`. A version string or URL by
itself is not proof that the release asset was published and verified.
