# WOM-kit v0.4.61 — closing out old cleanups, and safer letter revisions

This release answers beta letter 181, sent from v0.4.60. The customer's cleanup was actually finished, but the session closeout still blocked. Their agent also revised a letter that had already been delivered, and could not restore it. Installing the tool alone does not change a customer archive.

## Closing out cleanups made by older versions

A cleanup request written by WOM v0.4.38–v0.4.46 records nothing about Windows alternate data streams (extra data attached to a file). The closeout check accepted such items only with a recorded empty stream list, so a finished request of 1,070 items counted 2.

The check now says how each item's stream state is proven:

- `bound_delete_guard_no_streams`: the item was deleted by WOM's bound delete under that exact request. That delete refuses any file that carries an alternate stream, so the item had none.
- `recorded_inventory_empty` and `recorded_inventory_with_stream_backup`. Before this release, items whose streams were backed up with them were wrongly rejected.
- Anything that cannot be proven is counted as `legacy_stream_state_unknown`, with a plain summary. It is never assumed empty. Examples are a run that was interrupted before it wrote its record, and an item already gone before its delete.

The official restore now accepts the proven items. If the only remaining gap is that unknown count, the session handoff names it. After the person agrees, `session-handoff-checkpoint ... --accept-legacy-stream-boundary` records the boundary and completes the closeout. The count stays in the report, and nothing is run again.

## Letters

- **Delivered letters stay as delivered.** The operator guide now says that "전달하고 올게" or "보냈어" counts as delivered: mark the letter delivered at once and write later observations as a new letter. The revise preview repeats this check.
- **Restoring the delivered text works.** Restoring a letter's earlier text through revise used to fail after approval with `feedback_body_existing_receipt_conflict`. The approval receipt that already exists for exactly that text is now reused. Any other existing receipt is still a conflict, and the preview now reports it before you approve.

## Closing stale approval records

`exact-approval-claim-finalize` used to rescan every receipt before saying a reviewed plan was out of date. If receipts changed after the dry-run, it now refuses at once and asks for a new dry-run. If nothing changed, the approve no longer rescans before the dialog.

## Boundaries

The slow processing in the letter (28 small items taking about 26 minutes) is being investigated at the customer's scale and follows in the next release. The customer's own run is not verified.

## Install after publication

Use the exact public release asset after its hash and size are reported:

```powershell
$womBootstrapNonce = [guid]::NewGuid().ToString("N")
$womBootstrapRoot = Join-Path $env:LOCALAPPDATA "WOM\bootstrap-v0461-$womBootstrapNonce"
py -3.12 -m venv $womBootstrapRoot
$womBootstrapPython = (Get-Item -LiteralPath (Join-Path $womBootstrapRoot "Scripts\python.exe")).FullName
& $womBootstrapPython -m pip install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.61/wom_kit-0.4.61-py3-none-any.whl"
& "$womBootstrapRoot\Scripts\archive.exe" --version
```

Require `archive 0.4.61` from a new process, then follow the reviewed `project-version-update` flow for an existing project.
