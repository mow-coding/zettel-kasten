# WOM-kit v0.3.316

Letter 129 project-update collision recovery.

Status: v0.3.316 implementation and release scope. The source implementation
and local tests may be complete in this worktree, but this note does not prove
merge, external CI, exact tag, GitHub Release, packaged wheel publication,
fresh installation, real-project execution, beta-client success, or human
acceptance.

## What v0.3.315 left unfinished

A reported v0.3.315 update correctly detected 25 ignored Python runtime-cache
collisions, but inspecting them one at a time exposed no usable remediation.
Detection without an official recovery path left the project unable to update.
v0.3.316 closes that product gap without adding a separate graphical UI.

## One bounded inspection

- `project-version-update-collision --action inspect-all` reuses one exact
  `materialization_plan_sha256` and inspects the complete opaque collision set
  in one operation. Operators do not pass 25 separate entry references.
- The result distinguishes derived bytecode files, plain `__pycache__`
  directories, and unsupported entries. It reports whether classification and
  remediation eligibility were actually evaluated instead of presenting an
  unevaluated false value as a verified negative fact.
- Public JSON remains content-free: fixed classifications, counts, blocker
  codes, and opaque references are exposed; local paths, names, bytes, byte
  hashes, and private identity values are not.
- A repair route is offered only when the inspected set is the exact complete
  collision set and every entry is a supported ignored Python cache artifact.
  Counts alone are never repair authority.

## Exact-set-bound cache repair

`project-bytecode-repair-plan` can bind its proposed files and cache
directories to the same target and materialization-plan digest returned by
`inspect-all`. Approval rechecks that exact set and the repair-plan digest.
Unignored, tracked, reparse, linked, special, changed, oversized, incomplete,
or otherwise unsupported entries block instead of being deleted.

The repair uses the same exclusive project-version-update lock as the updater,
requires an attributed reviewer and explicit external-writer quiescence, and
records private intent/completion evidence. File removal is bound to the exact
reviewed open-file identity. Empty supported cache directories have an
official route. Partial or uncertain outcomes return structured evidence and
never invent an all-clean result.

The updater's existing final pre-write HEAD and tracked-byte drift check remains
in force. v0.3.316 adds the cache-repair route under that same update lock; it
does not weaken or replace the updater's last no-write-on-drift boundary.

This repair removes only reproducible Python bytecode/cache artifacts. It does
not delete user-authored source, fetch or materialize a target, change `HEAD`,
change an installed-version pin, retry an updater, or grant update approval.

## Required recovery sequence

Use the digest from a fresh blocked updater preview:

```powershell
archive project-version-update-collision <project-or-archive-root> --target v0.3.316 --expected-plan-sha256 sha256:<materialization-digest> --action inspect-all --dry-run --format json
archive project-bytecode-repair-plan <project-or-archive-root> --target v0.3.316 --expected-materialization-plan-sha256 sha256:<materialization-digest> --dry-run --format json
archive project-bytecode-repair <project-or-archive-root> --target v0.3.316 --expected-materialization-plan-sha256 sha256:<materialization-digest> --expected-plan-sha256 <repair-plan-sha256> --approve --reviewed-by <actor> --affirm-external-writers-quiescent --format json
```

Then discard the old updater approval context. Run a fresh
`project-version-update --dry-run`, review its new plan, and approve the update
separately. Repair success is not update success, and source/pin/version
alignment must be verified from a new process after the update.

Unsupported or mixed collision sets intentionally remain
`inspected_remediation_unavailable`. Resolve the fixed blocker without guessing
private paths, then start again from a fresh updater preview.

## Install and verify

1. Confirm that the exact v0.3.316 GitHub Release exists and lists the verified
   `wom_kit-0.3.316-py3-none-any.whl`.
2. Replace the isolated older tool environment with that exact artifact;
   updating repository files alone does not update an installed wheel.
3. Start a new process and run `archive --version` or `archive version`.
4. Run the complete preview, inspect-all, repair-plan, reviewed repair, fresh
   preview, and separately approved update sequence. Do not reuse any old
   updater approval.
