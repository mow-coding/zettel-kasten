# WOM-kit v0.4.13 — Exact Setup Evidence and Create-Only Byte Preservation

v0.4.13 closes two object-storage safety gaps without turning a public release
into a client-data operation. It makes local setup evidence exact and
privacy-safe, then makes emergency byte preservation create-only at the remote
key for both single-part and multipart objects.

## What changed

- **Local setup evidence is exact-first.** WOM derives the canonical binding
  identity and expected setup receipt before it considers any legacy evidence.
  A malformed, unreadable, disabled, orphaned, case-colliding, replaced, or
  cross-namespace receipt cannot silently become a ready storage setup.
- **Public setup status stays content-free.** Normal results expose fixed reason
  codes and digests, not profile values, resource names, account references,
  endpoints, credential references, receipt filenames, or local paths. A valid
  receipt owned by a different provider namespace remains private to that
  namespace.
- **Preservation is create-only.** A single-object PUT carries
  `If-None-Match: *`. Multipart upload applies the same condition to the final
  completion request, which is the publish point. WOM never falls back to an
  unconditional overwrite after a conditional conflict.
- **Every terminal state has independent byte evidence.** A new upload becomes
  `bytes_preserved` only after HEAD plus a complete GET rehash. Matching bytes
  that were already present become `already_remote_verified`. A proven size or
  checksum conflict becomes `review_required` without overwriting the remote
  object. Unknown size, incomplete response, authorization failure, throttling,
  server failure, transport failure, and uncertain multipart cleanup remain
  nonterminal and resumable rather than becoming false receipts.
- **Resume authority is durable and exact.** The private ledger is bound to the
  exact operation manifest. Immediately before each provider mutation, it
  durably reserves and charges one unit from the manifest-bound call ceiling.
  A charged reservation is not the same as an observed transport attempt: if a
  crash leaves that distinction unknowable, the unit remains charged. Resume
  first queries the exact remote target. Only independently verified matching
  bytes allow no-PUT verification or receipt finalization. Proven absence,
  provider unavailability, incomplete evidence, and uncertain multipart
  cleanup remain nonterminal and grant no automatic retry authority.
- **Preservation is not formal adoption.** A `bytes_preserved` receipt does not
  add a `wom_uploaded` manifest location, satisfy formal-adoption skip logic,
  merge conflicting definitions, or claim that the complete archive is backed
  up.
- **Windows project-runtime preparation tolerates only brief scanner locks.**
  When Windows Defender or an indexer briefly holds a newly generated launcher,
  WOM retries only that owned-file removal for a short bounded interval. It
  binds removal to a retained Windows file handle plus the exact identity,
  bytes, size, timestamp, single-link state, and stream inventory. A same-name
  replacement can therefore never become the deletion target. WOM still stops
  on a replacement, reparse point, alternate stream, persistent lock, or
  semantic verification error. If preparation remains incomplete, the durable
  structured update lock and partial private candidate stay preserved instead
  of being misreported as a removed or replaced legacy lock.

## Human and client boundary

The AI and WOM compute inventory, hashes, exact targets, drift, provider
responses, call budgets, verification, checkpoints, and receipts. The person
reviews only the plain operation effect and chooses the operation-specific
action or safe cancel; the person is not asked to count records or compare
digests.

Publishing or installing v0.4.13 does not read a client archive, access a
credential, call a storage provider, upload bytes, or change a manifest. A
client result exists only after the intended project runtime is updated and the
client explicitly runs or delegates the exact approved operation with its own
private setup and credential capability. Provider-specific live success must
be proved by that run's durable receipt and an independent remote verification;
the public release and synthetic transport tests are not that proof.

## Install contract

After the matching GitHub Release exists and lists the exact asset, install it
in an isolated tool or project runtime:

```powershell
uv tool install "https://github.com/mow-coding/zettel-kasten/releases/download/v0.4.13/wom_kit-0.4.13-py3-none-any.whl"
archive --version
```

Require exactly `archive 0.4.13` from a new process. The versioned URL alone is
not proof that the release or asset exists.
